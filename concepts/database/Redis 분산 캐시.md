# Redis 분산 캐시

## 한 줄 정의
Redis는 여러 애플리케이션 서버가 함께 사용할 수 있는 빠른 인메모리 데이터 저장소로, 반복적인 DB 조회를 줄이기 위한 분산 캐시로 자주 사용된다.

## 핵심 내용
캐시는 특정 제품의 이름이 아니라 자주 사용하는 데이터를 빠른 공간에 임시로 보관하는 방식이다.

Redis는 캐시를 구현할 때 사용할 수 있는 대표적인 도구 중 하나다.

```text
API Server A
API Server B -> Redis Cache -> DB
API Server C
```

여러 애플리케이션 서버가 하나의 Redis를 함께 사용하면 서버마다 같은 데이터를 별도로 조회할 필요가 없다.

### Cache Hit와 Cache Miss
Redis에 필요한 데이터가 있는 경우를 Cache Hit라고 한다.

이때는 DB를 조회하지 않고 Redis 데이터를 바로 반환한다.

Redis에 필요한 데이터가 없는 경우를 Cache Miss라고 한다.

이때는 DB에서 데이터를 조회하고 Redis에 저장한 뒤 반환한다.

```text
Redis 조회
  -> 데이터 있음: Cache Hit -> 바로 반환
  -> 데이터 없음: Cache Miss -> DB 조회 -> Redis 저장 -> 반환
```

### 로컬 캐시와 분산 캐시
| 구분 | 로컬 캐시 | Redis 분산 캐시 |
| --- | --- | --- |
| 저장 위치 | 각 애플리케이션 서버 내부 | 별도의 Redis 서버 또는 서비스 |
| 공유 여부 | 서버끼리 공유하지 않음 | 여러 서버가 함께 사용 가능 |
| 앱 서버 종료 시 | 해당 서버의 캐시가 사라짐 | Redis가 정상이라면 유지됨 |
| 예시 | Caffeine | Redis |

Spring Cache는 특정 캐시 제품이 아니라 캐시를 편리하게 적용하기 위한 추상화다.

실제 저장 위치로 로컬 캐시나 Redis를 선택할 수 있다.

### TTL
TTL은 Time To Live의 약자로, 데이터를 캐시에 얼마나 오래 보관할지 정하는 값이다.

```text
상품 상세 정보 -> 10분 보관
카테고리 목록 -> 1시간 보관
```

TTL이 지나면 데이터가 삭제되고, 다음 요청에서 DB를 다시 조회해 Redis에 저장할 수 있다.

## 예시
여러 사용자가 같은 인기 상품을 반복해서 조회한다고 가정한다.

```text
첫 번째 요청 -> Redis에 없음 -> DB 조회 -> Redis 저장 -> 반환
다음 요청들  -> Redis에 있음 -> Redis에서 바로 반환
```

DB 조회 횟수가 줄어들기 때문에 DB 부하와 응답 시간을 줄일 수 있다.

## 주의할 점
- Redis가 모든 DB 데이터를 자동으로 저장하는 것은 아니다.
- 자주 조회되고 조회 비용이 크며, 잠시 오래된 값이 보여도 괜찮은 데이터를 우선 검토한다.
- 결제 금액, 계좌 잔액, 실시간 재고처럼 정확성이 중요한 데이터는 신중하게 적용한다.
- Redis는 기본적으로 메모리에 데이터를 저장한다. Redis 자체가 종료되면 설정에 따라 데이터가 사라질 수 있다.
- DB 조회 결과를 캐싱한다면 Redis 데이터가 사라져도 DB에서 다시 채울 수 있도록 설계한다.
- Redis를 세션이나 임시 카운터 등에 사용할 때는 데이터 유실 영향과 영속성 설정을 별도로 검토한다.
