# 데드락(Deadlock, 교착 상태)의 이해와 예방

## 1. 데드락(Deadlock)이란?
**데드락(교착 상태)**은 두 개 이상의 트랜잭션이 서로가 점유하고 있는 자원(락, Lock)을 얻기 위해 무한히 대기하는 상태를 말합니다.

### 💡 쉬운 비유 (펜과 공책)
* **철수**는 **펜**을 쥐고 있고, 글을 쓰기 위해 **공책**이 필요합니다.
* **영희**는 **공책**을 쥐고 있고, 글을 쓰기 위해 **펜**이 필요합니다.
* 철수와 영희 모두 자기가 가진 자원을 내려놓지 않고, 상대방이 양보하기만을 영원히 기다립니다. 이 상태가 바로 **데드락**입니다.

---

## 2. 데이터베이스에서의 데드락 예시
동일한 두 개의 계좌(A, B) 간에 송금이 동시에 일어나는 상황을 가정해 봅시다.

| 시간 | 트랜잭션 1 (A -> B 송금) | 트랜잭션 2 (B -> A 송금) |
| :--- | :--- | :--- |
| **T1** | 계좌 A에 Update 수행 (**A의 쓰기 락 획득**) | 계좌 B에 Update 수행 (**B의 쓰기 락 획득**) |
| **T2** | 계좌 B에 Update 시도 (**B의 락을 대기**) | 계좌 A에 Update 시도 (**A의 락을 대기**) |
| **결과** | **무한 대기 발생 (데드락)** | **무한 대기 발생 (데드락)** |

> [!NOTE]
> 데이터베이스 관리 시스템(DBMS)은 데드락 감지기(Deadlock Detector)를 통해 이를 주기적으로 확인하며, 데드락이 발생하면 한쪽 트랜잭션을 강제로 롤백(Rollback)시켜 문제를 해결합니다.

---

## 3. 데드락이 발생하는 4가지 필수 조건 (OS/DB 공통)
데드락은 아래 4가지 조건이 **동시에 충족**될 때 발생합니다. 반대로 말하면, 이 중 하나라도 예방하면 데드락은 발생하지 않습니다.

1. **상호 배제 (Mutual Exclusion)**: 한 번에 한 트랜잭션만 자원을 점유할 수 있음 (쓰기 락은 독점적).
2. **점유와 대기 (Hold and Wait)**: 자원을 가진 상태에서 다른 자원을 추가로 요구하며 대기함.
3. **비선점 (No Preemption)**: 다른 트랜잭션이 쥐고 있는 락을 강제로 빼앗을 수 없음.
4. **순환 대기 (Circular Wait)**: 대기 중인 트랜잭션들이 고리(Cycle) 형태로 서로를 기다림 (A -> B -> A).

---

## 4. 실무에서 데드락을 줄이는 예방 및 해결 전략

### ① 자원 접근 순서 일관되게 맞추기 (순환 대기 예방)
* **원인**: 트랜잭션마다 자원에 접근하는 순서가 다르면 순환 대기가 발생합니다.
* **해결**: 모든 트랜잭션이 테이블 로우에 접근할 때 **항상 동일한 순서**로 접근하도록 개발 규칙을 세웁니다.
  * 예: 항상 `계좌 ID`가 작은 순서대로 락을 획득하도록 정렬(Order) 후 쿼리 수행.
  * 트랜잭션 1, 2 모두 `A -> B` 순서로 정렬하여 요청한다면, 트랜잭션 2는 처음부터 A 락을 기다려야 하므로 데드락이 발생하지 않고 단순 순차 대기만 발생합니다.

### ② 트랜잭션 범위를 최소화하기 (점유 시간 단축)
* **원인**: 트랜잭션 내부에서 오랜 시간 연산을 하거나 외부 API를 호출하면, 락을 쥐고 있는 시간이 길어져 데드락 확률이 높아집니다.
* **해결**: 
  * 트랜잭션 안에는 **오직 DB 데이터 변경과 직접 관련된 로직만** 둡니다.
  * 무거운 비즈니스 로직 연산이나 네트워크 I/O(외부 API 호출, 파일 쓰기 등)는 트랜잭션 시작 전이나 종료 후에 처리합니다.

### ③ 인덱스 설계 및 활용 (락 범위 최소화)
* **원인**: 인덱스가 없으면 조건에 맞는 로우를 찾기 위해 테이블 전체를 스캔(Full Scan)해야 하므로, 불필요하게 넓은 범위(여러 로우 또는 테이블 전체)에 락이 걸립니다.
* **해결**: 
  * `WHERE` 조건절에 사용되는 컬럼에 적절한 **인덱스(Index)**를 생성합니다.
  * 인덱스를 타게 만들면 딱 타겟이 되는 레코드(Row)에만 락이 걸리므로 동시성이 증가하고 데드락 가능성이 줄어듭니다.

### ④ 재시도(Retry) 로직 구현 (애플리케이션 레벨 해결)
* **원인**: 동시 요청이 고도로 발생하는 환경에서는 완벽한 예방이 불가능할 수 있습니다. DBMS는 결국 데드락 감지 시 에러(`Error Code: 1213 - Deadlock found...`)를 뱉으며 트랜잭션을 롤백시킵니다.
* **해결**:
  * 애플리케이션 코드(예: Spring의 `@Retryable`, DB 커넥션 풀 설정 등)에서 데드락 예외를 캐치합니다.
  * 아주 짧은 시간(예: 몇 ms) 대기 후 **자동으로 트랜잭션을 재시도**하도록 구현합니다. 대부분의 경우 재시도하면 앞선 트랜잭션이 끝났기 때문에 성공합니다.

## ✍️ 요약 노트 (노션 복사용)

1. **정의**: 서로가 점유한 락을 기다리며 무한 대기하는 현상.
2. **원인**: 비일관된 접근 순서, 긴 트랜잭션, 인덱스 부재로 인한 락 범위 확장.
3. **해결 전략**:
   * **접근 순서 일관화**: 자원 접근 순서 통일 (`A -> B`).
   * **트랜잭션 단축**: 네트워크 I/O 등 무거운 로직은 트랜잭션 외부로 분리.
   * **인덱스 설정**: 정밀하게 락을 걸도록 인덱스 튜닝.
   * **Retry 로직**: 데드락 예외 발생 시 잠시 후 다시 시도.
