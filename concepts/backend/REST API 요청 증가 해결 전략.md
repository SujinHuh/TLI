# REST API 요청 증가 해결 전략

## 한 줄 정의
REST API 요청이 많아졌을 때는 무조건 비동기로 처리하기보다, 병목 지점을 먼저 파악하고 서버, 캐시, DB, API 설계, 트래픽 제어, 비동기 처리 등 여러 계층에서 대응해야 한다.

## 핵심 내용
REST API는 기본적으로 요청을 보내면 응답을 기다리는 동기적인 요청/응답 구조다. 하지만 요청이 많아졌다고 해서 반드시 비동기로만 해결해야 하는 것은 아니다.

먼저 병목 지점을 확인해야 한다.

- 애플리케이션 서버 처리량 부족
- 반복 조회로 인한 DB 부하
- 느린 쿼리 또는 잘못된 인덱스
- DB 커넥션 부족
- 너무 큰 데이터 조회
- 비정상적으로 많은 API 호출
- 비효율적인 API 호출 구조
- 즉시 처리하지 않아도 되는 무거운 작업

## 주요 해결 방법

### 서버 확장
수직적 확장은 서버 한 대의 성능을 높이는 방식이다.

- CPU 증가
- RAM 증가
- 디스크 성능 향상

수직적 확장은 단순하지만 장비 비용이 커지고, 한 대가 감당할 수 있는 한계가 있다.

수평적 확장은 서버 여러 대를 두는 방식이다.

```text
Client
  -> Load Balancer
    -> API Server 1
    -> API Server 2
    -> API Server 3
```

로드밸런서가 요청을 여러 서버에 나눠주기 때문에 전체 처리량을 늘릴 수 있다.

### 캐시
읽기 요청이 많고 같은 데이터를 반복 조회한다면 Redis 같은 캐시를 사용할 수 있다.

```text
Client -> API Server -> Cache
                     -> DB
```

캐시에 데이터가 있으면 DB까지 가지 않고 바로 응답할 수 있다.  
다만 DB 데이터가 변경되면 관련 캐시를 삭제하거나 갱신해야 한다.

### DB 병목 대응
DB가 병목이라면 다음 방법을 고려할 수 있다.

- 인덱스 최적화
- 쿼리 튜닝
- Read Replica
- Connection Pool 조정
- Pagination

### API 구조 개선
클라이언트가 너무 자주 API를 호출한다면 API 설계 문제일 수 있다.

```text
GET /users/1
GET /users/2
GET /users/3
```

위와 같은 호출은 아래처럼 개선할 수 있다.

```text
GET /users?ids=1,2,3
```

또는 대량 조회는 pagination을 적용한다.

```text
GET /orders?page=1&size=50
```

### 비동기 처리
즉시 응답하지 않아도 되는 작업은 Queue 기반 비동기 처리로 분리할 수 있다.

```text
API Server -> Queue -> Worker
```

REST에서는 먼저 `202 Accepted`를 응답하고, 내부 작업은 나중에 처리할 수 있다.

## 예시
```http
POST /reports

202 Accepted
{
  "jobId": "abc-123",
  "status": "PENDING"
}
```

클라이언트는 이후 작업 상태를 조회한다.

```http
GET /reports/abc-123/status
```

## 주의할 점
- 요청이 많아졌다고 무조건 비동기로 해결하지 않는다.
- 먼저 서버, DB, API 구조 중 어디가 병목인지 확인한다.
- 캐시는 읽기 부하를 줄이는 데 효과적이지만, 데이터 변경 시 무효화 전략이 필요하다.
- 수평 확장을 하려면 서버가 상태를 직접 들고 있지 않도록 설계하는 것이 좋다.
- 비동기 처리는 즉시 응답이 필요 없는 작업에 적합하다.
