# 로드밸런서와 Health Check

## 한 줄 정의
로드밸런서는 사용자 요청을 여러 서버에 분산하고, Health Check를 통해 요청을 처리할 수 있는 서버에만 트래픽을 전달하는 구성 요소다.

## 핵심 내용
사용자가 도메인으로 접속하면 DNS는 일반적으로 개별 애플리케이션 서버가 아니라 로드밸런서의 주소를 안내한다.

```text
사용자
  -> DNS
    -> Load Balancer
      -> API Server A
      -> API Server B
      -> API Server C
```

각 애플리케이션 서버는 서로 다른 주소를 가진 별도의 서버다.

로드밸런서는 요청을 여러 서버에 나누어 한 서버에만 부하가 몰리지 않도록 한다.

서버를 여러 대로 늘리는 방식을 수평 확장 또는 Scale-out이라고 한다.

### ALB와 NLB
AWS에서 자주 사용하는 로드밸런서에는 ALB와 NLB가 있다.

| 종류 | 의미 | 주요 용도 |
| --- | --- | --- |
| ALB | Application Load Balancer | HTTP, HTTPS 기반 웹 서비스와 REST API |
| NLB | Network Load Balancer | TCP, UDP, TLS 기반 네트워크 트래픽과 고정 IP가 필요한 경우 |

일반적인 REST API 서비스에서는 요청 경로나 호스트 같은 HTTP 정보를 기준으로 라우팅할 수 있는 ALB를 우선 고려할 수 있다.

### Health Check
로드밸런서는 각 서버가 요청을 처리할 수 있는지 주기적으로 확인한다.

```text
Load Balancer
  -> API Server A: 정상 응답 -> 요청 전달
  -> API Server B: 연속 실패 -> 요청 전달 중단
  -> API Server C: 정상 응답 -> 요청 전달
```

ALB는 일반적으로 `/health` 같은 경로에 HTTP 또는 HTTPS 요청을 보내고 응답 상태를 확인한다.

```http
GET /health

200 OK
```

## 예시
서버 B의 애플리케이션이 중단되었지만 서버 컴퓨터 자체는 켜져 있을 수 있다.

단순 ping은 성공할 수 있지만 `/health` 요청은 실패한다.

이 경우 ALB는 서버 B를 비정상 대상으로 판단하고 정상 서버에만 요청을 전달한다.

## 주의할 점
- 로드밸런서는 전체 부하를 없애는 도구가 아니라 여러 서버에 부하를 나누는 도구다.
- 로드밸런서가 서버를 자동으로 여러 대 만들어 주는 것은 아니다.
- 서버 수를 늘려도 DB가 병목이라면 별도의 대응이 필요하다.
- Health Check는 단순히 장비가 켜져 있는지가 아니라 실제 요청을 처리할 수 있는지를 확인해야 한다.
