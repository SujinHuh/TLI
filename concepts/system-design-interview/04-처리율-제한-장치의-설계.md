# 4장 처리율 제한 장치의 설계

## 한 줄 정의
처리율 제한 장치는 클라이언트나 서비스가 보내는 트래픽의 처리율을 제어하여 일정 기간 동안 허용되는 요청 수를 제한하는 장치이다.

## 핵심 내용
- HTTP API에서는 특정 기간 내 클라이언트 요청 횟수를 제한하는 방식으로 동작한다.
- DoS 공격으로 인한 자원 고갈을 방지하는 데 도움이 된다.
- 불필요한 요청 처리를 줄여 서버 비용을 절감할 수 있다.
- 우선순위가 높은 API에 더 많은 자원을 할당할 수 있다.
- 제3자 API 사용료를 지불하는 서비스에서는 비용 통제 측면에서도 중요하다.

## 설계 요구사항
- 설정된 처리율을 초과하는 요청은 정확하게 제한해야 한다.
- 처리율 제한 장치가 HTTP 응답 시간에 나쁜 영향을 주면 안 된다.
- 가능한 적은 메모리를 사용해야 한다.
- 여러 서버나 프로세스에서 공유할 수 있는 분산형 처리율 제한이 가능해야 한다.
- 요청이 제한되었을 때 사용자에게 그 사실을 명확히 알려야 한다.
- 제한 장치에 장애가 생겨도 전체 시스템에 영향을 주지 않아야 한다.

## 처리율 제한 장치를 둘 수 있는 위치
처리율 제한 장치는 클라이언트 측에도 둘 수 있고, 서버가 통제하는 여러 계층에도 둘 수 있다.

```text
Client
 -> CDN
 -> WAF
 -> Load Balancer
 -> Reverse Proxy
 -> API Gateway
 -> Application Middleware
 -> Controller / Service
```

각 위치의 의미는 다음과 같다.

- 클라이언트 측: 웹 프론트엔드, 모바일 앱, 데스크톱 앱처럼 사용자가 직접 실행하는 영역이다. 버튼 연타 방지나 중복 요청 방지 같은 UX 목적에는 사용할 수 있지만, 사용자가 우회하거나 조작할 수 있으므로 보안 목적의 처리율 제한 위치로는 안정적이지 않다.
- CDN: 사용자와 가까운 엣지 위치에서 요청을 먼저 받는 계층이다. 정적 리소스 캐싱뿐 아니라 특정 경로로 몰리는 대량 요청이나 단순 반복 요청을 애플리케이션 서버에 도달하기 전에 줄이는 데 사용할 수 있다.
- WAF: 웹 공격 패턴을 탐지하고 차단하는 계층이다. 특정 IP, 비정상 요청 패턴, 과도한 요청량을 기준으로 제한할 수 있어 DoS/DDoS 방어에 도움이 된다.
- Load Balancer: 여러 서버로 요청을 분산하는 계층이다. 특정 서버로 요청이 몰리지 않게 분산하면서, 기본적인 요청량 제한이나 비정상 트래픽 차단 정책을 함께 둘 수 있다.
- Reverse Proxy: API 서버 앞에서 요청을 대신 받아 내부 서버로 전달하는 계층이다. NGINX, Envoy, HAProxy 같은 프록시에서 IP나 경로 기준으로 요청 수를 제한할 수 있다.
- API Gateway: 여러 API 앞단에서 인증, 라우팅, 로깅, 처리율 제한 같은 공통 기능을 담당하는 계층이다. API Key, 사용자, endpoint, 요금제 기준으로 비교적 정교한 처리율 제한을 적용하기 좋다.
- Application Middleware: 애플리케이션 내부에서 Controller나 비즈니스 로직에 도달하기 전에 실행되는 계층이다. Spring Filter, Interceptor, AOP, Gateway Filter 같은 위치에서 사용자 정보나 서비스 정책을 바탕으로 세밀한 제한을 걸 수 있다.
- Controller / Service: 실제 요청을 처리하는 비즈니스 로직 계층이다. 가장 세밀한 정책 판단은 가능하지만, 이 지점까지 요청이 들어온 뒤 제한하면 앞단 서버 자원 보호 효과는 상대적으로 줄어든다.

## 클라이언트 측이 안정적이지 않은 이유
클라이언트는 사용자가 통제할 수 있는 영역이기 때문에 처리율 제한을 신뢰하기 어렵다.

예를 들어 사용자는 공식 앱이나 웹 화면을 통하지 않고 API를 직접 호출할 수 있다. 브라우저 개발자 도구, curl, Postman, 스크립트 등을 사용하면 클라이언트에 들어 있는 요청 제한 로직을 우회할 수 있다. 또한 요청 헤더나 User-Agent를 조작해 정상 클라이언트처럼 보이게 만들 수도 있다.

따라서 버튼 연타 방지 같은 UX 목적의 제한은 클라이언트에서 할 수 있지만, DoS 방어, 비용 통제, API 보호 목적의 처리율 제한은 서버가 통제하는 영역에서 수행해야 한다.

## 서버 측 처리 방식
서버 측 처리율 제한은 크게 API 서버 내부에 두는 방식과 API 서버 앞단 계층에 두는 방식으로 나눌 수 있다.

- API 서버 내부 방식: API 서버 코드 안에서 요청 횟수를 검사한다. 구현 흐름을 애플리케이션 로직과 함께 관리할 수 있지만, 서버가 여러 대라면 Redis 같은 중앙 저장소를 사용해 요청 횟수를 공유해야 한다.
- Application Middleware 방식: Controller에 도달하기 전에 Filter, Interceptor, AOP 같은 계층에서 요청을 제한한다. 사용자 정보나 서비스 정책을 활용하기 쉽다.
- API Gateway 방식: 여러 API 서버 앞에서 공통으로 처리율 제한을 수행한다. API Key, 사용자, endpoint, 요금제별 제한을 적용하기 좋다.
- Reverse Proxy 방식: NGINX, Envoy, HAProxy 같은 프록시에서 IP, 경로, 요청 속도 기준으로 제한한다. API 서버에 요청이 전달되기 전에 차단할 수 있다.
- Load Balancer 방식: 서버 분산 계층에서 비정상적으로 많은 요청을 제한하거나 특정 서버로의 쏠림을 완화한다.
- CDN/WAF 방식: 가장 앞단의 엣지 또는 보안 계층에서 공격성 트래픽과 대량 요청을 먼저 차단한다. 내부 서버까지 요청이 들어오기 전에 막을 수 있어 서버 보호에 유리하다.

## 처리율 제한 알고리즘

처리율 제한 알고리즘은 정해진 시간 동안 요청을 얼마나 통과시킬지 판단하는 규칙이다.

### 토큰 버킷 알고리즘

토큰 버킷 알고리즘은 일정한 속도로 버킷에 토큰을 채워 넣고, 요청이 들어올 때마다 토큰을 하나씩 소비하는 방식이다.

```text
요청 도착
 -> 버킷에 토큰 있음: 토큰 1개 사용 -> 요청 통과
 -> 버킷에 토큰 없음: 요청 제한
```

버킷에 남은 토큰이 있기만 하면 요청은 시스템에 전달된다.

대표적으로 Amazon, Stripe는 API 요청을 통제하기 위해 토큰 버킷 계열의 처리율 제한 방식을 사용한다.

장점은 다음과 같다.

- 구현이 쉽다.
- 메모리 사용 측면에서 효율적이다.
- 짧은 시간에 집중되는 트래픽도 어느 정도 처리할 수 있다.

단점은 버킷 크기와 토큰 공급률이라는 두 인자를 적절하게 튜닝하기 까다롭다는 점이다.

### 누출 버킷 알고리즘

누출 버킷 알고리즘은 토큰 버킷 알고리즘과 비슷하지만, 요청 처리율이 고정되어 있다는 점이 다르다.

보통 FIFO 큐로 구현한다.

```text
요청 도착
 -> 큐에 공간 있음: 큐에 요청 저장
 -> 큐에 공간 없음: 요청 제한

큐
 -> 고정된 처리율로 요청을 하나씩 처리
```

전자상거래 플랫폼 Shopify는 누출 버킷 알고리즘을 사용해 처리율 제한을 구현한다.

장점은 다음과 같다.

- 큐의 크기가 제한되어 있어 메모리 사용량 측면에서 효율적이다.
- 고정 처리율을 갖고 있기 때문에 안정적인 출력이 필요한 경우에 적합하다.

단점은 단시간에 많은 트래픽이 몰리는 경우 큐에 오래된 요청들이 쌓이고, 그 요청들을 제때 처리하지 못하면 최신 요청들이 버려질 수 있다는 점이다.

또한 큐 크기와 처리율이라는 두 인자를 적절하게 튜닝해야 하므로 설정이 까다로울 수 있다.

### 고정 윈도우 카운터 알고리즘

고정 윈도우 카운터 알고리즘은 타임라인을 고정된 간격의 윈도로 나누고, 각 윈도 안에서 요청 수를 세는 방식이다.

```text
00:00 ~ 00:01 -> 요청 수 카운트
00:01 ~ 00:02 -> 요청 수 초기화 후 다시 카운트
```

장점은 다음과 같다.

- 메모리 효율이 좋다.
- 이해하기 쉽다.
- 윈도가 닫히는 시점에 카운터를 초기화하는 방식은 특정한 트래픽 패턴을 처리하기에 적합하다.

단점은 윈도 경계 부근에서 일시적으로 많은 트래픽이 몰려드는 경우, 기대했던 시스템 처리 한도보다 많은 요청을 처리하게 될 수 있다는 점이다.

예를 들어 분당 100개 요청만 허용한다고 해도, 00:59에 100개 요청이 들어오고 01:00에 다시 100개 요청이 들어오면 짧은 시간 안에 200개 요청이 통과할 수 있다.

### 알고리즘 비교

| 구분 | 토큰 버킷 | 누출 버킷 | 고정 윈도우 카운터 |
| --- | --- | --- | --- |
| 핵심 방식 | 토큰이 있으면 요청 통과 | FIFO 큐에서 고정 속도로 처리 | 고정 시간 구간마다 요청 수 카운트 |
| 장점 | 구현이 쉽고 순간 트래픽 흡수 가능 | 출력 처리율이 안정적 | 이해하기 쉽고 메모리 효율적 |
| 단점 | 버킷 크기와 토큰 공급률 튜닝이 까다로움 | 큐가 밀리면 최신 요청이 버려질 수 있음 | 윈도 경계에서 허용량보다 많은 요청이 통과할 수 있음 |
| 주요 튜닝 값 | 버킷 크기, 토큰 공급률 | 큐 크기, 처리율 | 윈도 크기, 윈도별 허용 요청 수 |

## 상세 설계

처리율 제한 장치는 제한 규칙, 카운터, 마지막 요청 타임스탬프를 바탕으로 요청을 통과시킬지 제한할지 판단한다.

처리율 제한 규칙은 보통 디스크에 보관한다. 작업 프로세스는 이 규칙을 수시로 디스크에서 읽어 캐시에 저장한다.

요청 처리 흐름은 다음과 같다.

```text
Client
 -> Rate Limiting Middleware
 -> API Server
```

처리율 제한 미들웨어는 캐시에서 제한 규칙을 가져온다. 그리고 Redis 캐시에서 카운터와 마지막 요청의 타임스탬프를 가져와 현재 요청이 제한 대상인지 확인한다.

요청이 제한 대상이 아니라면 API 서버로 전달한다. 요청이 제한 대상이라면 클라이언트에게 `429 Too Many Requests` 응답을 보낸다.

## 처리율 한도 초과 트래픽 처리

처리율 한도를 초과한 요청은 기본적으로 제한된다.

HTTP API에서는 보통 클라이언트에게 `429 Too Many Requests` 응답을 반환해 요청이 너무 많다는 사실을 알린다.

제한된 요청을 처리하는 방식은 서비스 성격에 따라 달라질 수 있다.

- 요청을 그대로 버린다.
- 나중에 처리하기 위해 메시지 큐에 보관한다.

## 분산 환경에서의 구현 이슈

단일 서버에서 처리율 제한 장치를 구현하는 것은 비교적 단순하다. 하지만 여러 서버와 병렬 스레드를 지원하는 분산 환경에서는 정확한 카운터 관리가 어려워진다.

대표적인 문제는 다음 두 가지이다.

- 경쟁 조건
- 동기화

### 경쟁 조건

처리율 제한 장치는 보통 다음 순서로 카운터를 다룬다.

1. Redis에서 카운터 값을 읽는다.
2. 카운터에 1을 더한 값이 임계치를 넘는지 확인한다.
3. 임계치를 넘지 않으면 Redis에 저장된 카운터 값을 1 증가시킨다.

병행성이 높은 환경에서는 이 과정에서 경쟁 조건이 발생할 수 있다.

예를 들어 Redis에 저장된 `counter` 값이 3이라고 하자. 두 요청을 처리하는 스레드가 동시에 `counter` 값을 읽으면 둘 다 값 3을 읽을 수 있다. 아직 어느 쪽도 변경된 값을 저장하지 않은 상태라면, 두 스레드는 각각 1을 더한 값인 4를 Redis에 저장할 수 있다.

이 경우 실제로는 요청이 2개 처리되었지만 카운터는 1만 증가한 것처럼 보인다. 결과적으로 처리율 제한이 정확하게 동작하지 않을 수 있다.

락을 사용하면 경쟁 조건을 막을 수 있지만, 락은 시스템 성능을 떨어뜨릴 수 있다.

락 대신 사용할 수 있는 대표적인 해결책은 다음과 같다.

- Lua 스크립트
- Redis의 정렬 집합, Sorted Set

### 동기화

분산 환경에서는 처리율 제한 장치가 여러 대일 수 있다.

각 처리율 제한 장치가 자기 서버 내부 메모리에만 요청 카운터를 저장하면, 같은 사용자의 전체 요청 수를 정확히 알기 어렵다.

예를 들어 같은 사용자의 요청이 세 대의 서버로 나뉘어 들어간다고 하자.

```text
Rate Limiter A -> user:123 = 3
Rate Limiter B -> user:123 = 4
Rate Limiter C -> user:123 = 2
```

이 경우 실제 요청 수는 9번이지만, 각 서버는 자기 서버로 들어온 요청 수만 알 수 있다.

고정 세션을 사용하면 같은 사용자의 요청을 항상 같은 처리율 제한 장치로 보낼 수 있다. 하지만 이 방식은 특정 서버에 부하가 몰릴 수 있고, 서버를 늘리거나 줄일 때 유연성이 떨어진다.

더 나은 방식은 Redis 같은 중앙 집중형 데이터 저장소를 사용하는 것이다.

```text
Rate Limiter A
Rate Limiter B -> Redis -> user:123 = 9
Rate Limiter C
```

모든 처리율 제한 장치가 Redis의 같은 카운터를 확인하면, 요청이 어느 서버로 들어와도 같은 기준으로 제한 여부를 판단할 수 있다.

## 성능 최적화

여러 데이터 센터를 지원하는 시스템에서는 사용자와 서버 사이의 물리적 거리가 지연 시간에 영향을 준다.

데이터 센터에서 멀리 떨어진 사용자를 지원하면 네트워크 왕복 시간이 길어져 응답 지연이 증가할 수 있다.

이 문제를 줄이기 위해 대부분의 클라우드 서비스 사업자는 엣지 서버를 제공한다. 사용자 트래픽을 가장 가까운 엣지 서버로 전달하면 원본 서버까지 매번 멀리 이동하지 않아도 되어 지연 시간을 줄일 수 있다.

## 모니터링

처리율 제한 장치를 설치한 뒤에는 실제로 효과적으로 동작하는지 확인하기 위해 데이터를 모아야 한다.

모니터링할 수 있는 관점은 다음과 같다.

- 처리율 제한 규칙이 의도한 대로 동작하는지
- 정상 사용자가 과도하게 차단되고 있지 않은지
- 제한된 요청 수가 비정상적으로 증가하고 있지 않은지
- 처리율 제한 장치가 API 응답 시간에 큰 영향을 주고 있지 않은지
