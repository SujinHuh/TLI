# 4장 처리율 제한 장치의 설계

## 한 줄 정의
처리율 제한 장치는 클라이언트나 서비스가 보내는 트래픽의 처리율을 제어하여 일정 기간 동안 허용되는 요청 수를 제한하는 장치이다.

## 핵심 내용
- HTTP API에서는 특정 기간 내 클라이언트 요청 횟수를 제한하는 방식으로 동작한다.
- DoS 공격으로 인한 자원 고갈을 방지하는 데 도움이 된다.
- 불필요한 요청 처리를 줄여 서버 비용을 절감할 수 있다.
- 우선순위가 높은 API에 더 많은 자원을 할당할 수 있다.
- 제3자 API 사용료를 지불하는 서비스에서는 비용 통제 측면에서도 중요하다.

## 설계 요구사항
- 설정된 처리율을 초과하는 요청은 정확하게 제한해야 한다.
- 처리율 제한 장치가 HTTP 응답 시간에 나쁜 영향을 주면 안 된다.
- 가능한 적은 메모리를 사용해야 한다.
- 여러 서버나 프로세스에서 공유할 수 있는 분산형 처리율 제한이 가능해야 한다.
- 요청이 제한되었을 때 사용자에게 그 사실을 명확히 알려야 한다.
- 제한 장치에 장애가 생겨도 전체 시스템에 영향을 주지 않아야 한다.

## 처리율 제한 장치를 둘 수 있는 위치
처리율 제한 장치는 클라이언트 측에도 둘 수 있고, 서버가 통제하는 여러 계층에도 둘 수 있다.

```text
Client
 -> CDN
 -> WAF
 -> Load Balancer
 -> Reverse Proxy
 -> API Gateway
 -> Application Middleware
 -> Controller / Service
```

각 위치의 의미는 다음과 같다.

- 클라이언트 측: 웹 프론트엔드, 모바일 앱, 데스크톱 앱처럼 사용자가 직접 실행하는 영역이다. 버튼 연타 방지나 중복 요청 방지 같은 UX 목적에는 사용할 수 있지만, 사용자가 우회하거나 조작할 수 있으므로 보안 목적의 처리율 제한 위치로는 안정적이지 않다.
- CDN: 사용자와 가까운 엣지 위치에서 요청을 먼저 받는 계층이다. 정적 리소스 캐싱뿐 아니라 특정 경로로 몰리는 대량 요청이나 단순 반복 요청을 애플리케이션 서버에 도달하기 전에 줄이는 데 사용할 수 있다.
- WAF: 웹 공격 패턴을 탐지하고 차단하는 계층이다. 특정 IP, 비정상 요청 패턴, 과도한 요청량을 기준으로 제한할 수 있어 DoS/DDoS 방어에 도움이 된다.
- Load Balancer: 여러 서버로 요청을 분산하는 계층이다. 특정 서버로 요청이 몰리지 않게 분산하면서, 기본적인 요청량 제한이나 비정상 트래픽 차단 정책을 함께 둘 수 있다.
- Reverse Proxy: API 서버 앞에서 요청을 대신 받아 내부 서버로 전달하는 계층이다. NGINX, Envoy, HAProxy 같은 프록시에서 IP나 경로 기준으로 요청 수를 제한할 수 있다.
- API Gateway: 여러 API 앞단에서 인증, 라우팅, 로깅, 처리율 제한 같은 공통 기능을 담당하는 계층이다. API Key, 사용자, endpoint, 요금제 기준으로 비교적 정교한 처리율 제한을 적용하기 좋다.
- Application Middleware: 애플리케이션 내부에서 Controller나 비즈니스 로직에 도달하기 전에 실행되는 계층이다. Spring Filter, Interceptor, AOP, Gateway Filter 같은 위치에서 사용자 정보나 서비스 정책을 바탕으로 세밀한 제한을 걸 수 있다.
- Controller / Service: 실제 요청을 처리하는 비즈니스 로직 계층이다. 가장 세밀한 정책 판단은 가능하지만, 이 지점까지 요청이 들어온 뒤 제한하면 앞단 서버 자원 보호 효과는 상대적으로 줄어든다.

## 클라이언트 측이 안정적이지 않은 이유
클라이언트는 사용자가 통제할 수 있는 영역이기 때문에 처리율 제한을 신뢰하기 어렵다.

예를 들어 사용자는 공식 앱이나 웹 화면을 통하지 않고 API를 직접 호출할 수 있다. 브라우저 개발자 도구, curl, Postman, 스크립트 등을 사용하면 클라이언트에 들어 있는 요청 제한 로직을 우회할 수 있다. 또한 요청 헤더나 User-Agent를 조작해 정상 클라이언트처럼 보이게 만들 수도 있다.

따라서 버튼 연타 방지 같은 UX 목적의 제한은 클라이언트에서 할 수 있지만, DoS 방어, 비용 통제, API 보호 목적의 처리율 제한은 서버가 통제하는 영역에서 수행해야 한다.

## 서버 측 처리 방식
서버 측 처리율 제한은 크게 API 서버 내부에 두는 방식과 API 서버 앞단 계층에 두는 방식으로 나눌 수 있다.

- API 서버 내부 방식: API 서버 코드 안에서 요청 횟수를 검사한다. 구현 흐름을 애플리케이션 로직과 함께 관리할 수 있지만, 서버가 여러 대라면 Redis 같은 중앙 저장소를 사용해 요청 횟수를 공유해야 한다.
- Application Middleware 방식: Controller에 도달하기 전에 Filter, Interceptor, AOP 같은 계층에서 요청을 제한한다. 사용자 정보나 서비스 정책을 활용하기 쉽다.
- API Gateway 방식: 여러 API 서버 앞에서 공통으로 처리율 제한을 수행한다. API Key, 사용자, endpoint, 요금제별 제한을 적용하기 좋다.
- Reverse Proxy 방식: NGINX, Envoy, HAProxy 같은 프록시에서 IP, 경로, 요청 속도 기준으로 제한한다. API 서버에 요청이 전달되기 전에 차단할 수 있다.
- Load Balancer 방식: 서버 분산 계층에서 비정상적으로 많은 요청을 제한하거나 특정 서버로의 쏠림을 완화한다.
- CDN/WAF 방식: 가장 앞단의 엣지 또는 보안 계층에서 공격성 트래픽과 대량 요청을 먼저 차단한다. 내부 서버까지 요청이 들어오기 전에 막을 수 있어 서버 보호에 유리하다.
