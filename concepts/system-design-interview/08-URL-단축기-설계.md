# 8장 URL 단축기 설계

## 한 줄 정의
긴 URL에 짧은 키를 부여하고, 단축 주소로 접속하면 원래 URL로 이동시키는 서비스다.

## 이번 학습 범위
문제 이해와 설계 범위부터 API 엔드포인트, 리다이렉션,
해시 함수와 해시 후 충돌 해소까지 가볍게 훑어봤다.
아래는 해당 범위와 대화에서 확인한 개념을 정리한 첫 메모다.

## 쉬운 ver
긴 주소에 짧은 별명을 붙이고, 별명과 원래 주소를 함께 기록한다고 생각하면 된다.
사용자가 짧은 주소로 들어오면 기록에서 원래 주소를 찾아 안내한다.

서로 다른 주소에 같은 별명이 붙으면 구분할 수 없으므로,
이미 쓰인 별명인지 확인하고 겹칠 때 처리하는 방법이 필요하다.

## 개발자 ver

### API 엔드포인트
두 가지 요청 흐름을 구분한다.

- 생성: 원본 URL을 받아 단축 키를 만들고, 키와 원본 URL의 매핑을 저장한다.
- 이동: 단축 키로 원본 URL을 조회하고 리다이렉션 응답을 보낸다.

### 301과 302 리다이렉션
- 301 Moved Permanently: 대상 주소가 영구적으로 이동했음을 나타낸다.
- 302 Found: 대상 주소가 일시적으로 다른 주소에 있음을 나타낸다.
- 이동할 주소는 Location 헤더로 전달한다.
- 캐시 동작은 상태 코드와 캐시 제어 설정 등을 함께 봐야 한다.
  “301은 무조건 캐시된다”거나 “302는 절대 캐시되지 않는다”고 단정하지 않는다.

### 해시 함수를 이용한 단축 키 생성
원본 URL의 해시값을 계산하고, 그 값 일부 등을 이용해 단축 키 후보를 만든다.
원본으로 이동할 때는 해시를 역산하지 않고 저장된 매핑을 조회한다.

### 해시 후 충돌 해소
서로 다른 원본 URL에서 같은 단축 키가 나오면 충돌이다.

키 후보가 다른 URL에 이미 배정되었는지 확인해야 한다.
충돌하면 추가 입력을 넣어 다시 계산하는 등의 방법으로
다른 후보를 만들고 확인할 수 있다.

## 예시
긴 URL → 단축 키 생성 → 키와 원본 URL 저장
단축 주소 접속 → 키로 원본 URL 조회 → 원본 주소로 리다이렉션

## 주의할 점
- 해시를 사용한다고 단축 키의 유일성이 자동으로 보장되는 것은 아니다.
- 같은 원본 URL에 같은 키를 다시 사용하는 것과,
  다른 원본 URL이 같은 키를 갖는 충돌은 구분한다.
- 이번에는 흐름을 가볍게 살펴봤으며, 장 전체를 정독하거나 구현한 기록은 아니다.

## 2026-09-21 복습과 보완

### 쉬운 ver
URL 단축은 긴 주소를 공유하거나 입력하기 편하게 짧은 이름을 붙이는 것이다.
서버 수를 줄이거나 원본 URL을 압축하는 기술은 아니다.

두 요청을 구분하면 이해하기 쉽다.
- 만들기: 긴 주소를 받아 짧은 코드를 만들고 연결 정보를 저장한다.
- 사용하기: 짧은 주소로 접속하면 저장된 연결 정보에서 원래 주소를 찾는다.

8장은 코드 계산뿐 아니라 생성, 저장, 조회, 리다이렉션을 포함한 서비스 전체의 설계를 다룬다.

### 개발자 ver

#### 데이터 모델과 코드 생성 방법
데이터 모델은 단축 코드와 원본 URL의 매핑을 저장하는 구조다.
해시나 고유 ID의 Base62 변환은 단축 코드를 만드는 방법이다.

#### 해시값과 단축 코드의 길이
해시값을 문자열로 표현한 뒤 일부만 단축 코드로 사용할 수 있다.
따라서 해시 결과 전체의 길이와 최종 코드 길이는 다를 수 있다.
전체 해시값이 달라도 선택한 부분이 같으면 단축 코드 충돌이 생긴다.

#### 랜덤 코드도 사용할 수 있다
해시가 유일한 방법은 아니다. 랜덤 코드를 생성해 원본 URL과 연결할 수도 있다.
두 방식 모두 짧은 코드가 겹칠 수 있어 중복 방지와 충돌 처리가 필요하다.

해시는 같은 입력과 조건에서 같은 계산 결과가 나온다.
랜덤 방식에서 기존 URL의 코드를 재사용하려면 별도 조회 정책을 둘 수 있다.
해시를 쓴다는 사실만으로 최종 코드의 유일성이나 보안이 보장되지는 않는다.

#### 해시 후 충돌 해소와 고유 ID의 Base62 변환
두 방식은 별개의 설계 선택지다.
해시 충돌이 생기면 Base62로 전환한다는 뜻이 아니다.

- 해시 방식: 원본 URL로 코드 후보를 계산한다.
  다른 URL이 같은 코드를 사용하면 추가 입력으로 재계산하는 등의 처리가 필요하다.
  별도의 고유 숫자 발급기는 필요하지 않지만, 최종 코드의 중복을 막아야 한다.

- 고유 ID → Base62 방식: 단축 링크마다 중복 없는 숫자 ID를 발급하고 변환한다.
  ID 전체를 동일한 문자 규칙으로 변환하면 서로 다른 ID의 코드가 겹치지 않는다.
  분산 환경에서는 여러 서버가 중복 없는 ID를 발급하도록 설계해야 한다.
  ID가 커지면 코드 길이가 늘어날 수 있고, 순차 ID는 코드를 추측하기 쉬울 수 있다.

Base62는 숫자와 영문 대소문자, 총 62개 기호를 사용하는 표현 방식이다.
해시 함수가 아니며, 같은 값을 Base62로 바꾼다고 충돌이 해결되지는 않는다.

#### 생성 요청과 조회 요청
아래 경로는 설명용 예시다.

- POST /api/v1/urls
  원본 URL → 코드 생성 → 코드와 원본 URL 저장 → 단축 URL 반환

- GET /{shortKey}
  이미 생성된 코드 → 원본 URL 조회 → 리다이렉션 응답

한 GET 요청 안에서 먼저 코드를 만들고 조회하는 것이 아니다.
누군가 단축 링크를 만든 뒤, 다른 시점에 그 링크를 클릭하는 별도 요청이다.

#### 리다이렉션 상세 흐름
유효한 단축 URL을 조회하는 일반적인 구성 예시다.

1. 브라우저가 단축 URL로 GET 요청을 보낸다.
2. 로드 밸런서가 웹 서버로 요청을 분산한다.
3. 웹 서버가 단축 키로 캐시를 조회한다.
4. 캐시에 없으면 DB에서 매핑을 조회하고 캐시를 채운다.
5. 서버는 301 또는 302와 Location 헤더로 원본 URL을 알려준다.
6. 브라우저가 원본 URL로 새 요청을 보낸다.

캐시에 있으면 DB 조회를 생략할 수 있다.
DB에도 없는 키는 별도 오류 처리가 필요하다.
단축 서버가 원본 페이지의 내용을 대신 반환하는 흐름과는 구분한다.

#### 실제 사례와 가상 예시 구분
YOURLS는 숫자 ID를 문자 코드로 변환하며 Base62를 선택할 수 있는 공개 사례다.
Meta나 X의 내부 코드 생성 방식은 확인된 근거 없이 단정하지 않는다.

사내 문서 공유 서비스를 해시 방식으로 설계한다는 예시는
이해를 돕기 위한 가상 예시이며, 특정 회사의 실제 구현 사례는 아니다.

### 이번 학습에서 다시 구분한 점
- URL 단축은 서버를 줄이는 것이 아니다.
- 짧은 코드로 원본을 역산하는 것이 아니라 저장된 매핑을 조회한다.
- 해시 방식과 고유 ID의 Base62 변환은 별개의 선택지다.
- 생성 요청과 단축 링크 접속 요청은 서로 다른 요청이다.
- 리다이렉션 응답을 받은 브라우저가 원본 URL로 다시 요청한다.
- 오늘은 질문과 재설명을 통해 복습했으며, 직접 구현한 기록은 아니다.
