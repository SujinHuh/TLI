# 8장 URL 단축기 설계

## 한 줄 정의
긴 URL에 짧은 키를 부여하고, 단축 주소로 접속하면 원래 URL로 이동시키는 서비스다.

## 이번 학습 범위
문제 이해와 설계 범위부터 API 엔드포인트, 리다이렉션,
해시 함수와 해시 후 충돌 해소까지 가볍게 훑어봤다.
아래는 해당 범위와 대화에서 확인한 개념을 정리한 첫 메모다.

## 쉬운 ver
긴 주소에 짧은 별명을 붙이고, 별명과 원래 주소를 함께 기록한다고 생각하면 된다.
사용자가 짧은 주소로 들어오면 기록에서 원래 주소를 찾아 안내한다.

서로 다른 주소에 같은 별명이 붙으면 구분할 수 없으므로,
이미 쓰인 별명인지 확인하고 겹칠 때 처리하는 방법이 필요하다.

## 개발자 ver

### API 엔드포인트
두 가지 요청 흐름을 구분한다.

- 생성: 원본 URL을 받아 단축 키를 만들고, 키와 원본 URL의 매핑을 저장한다.
- 이동: 단축 키로 원본 URL을 조회하고 리다이렉션 응답을 보낸다.

### 301과 302 리다이렉션
- 301 Moved Permanently: 대상 주소가 영구적으로 이동했음을 나타낸다.
- 302 Found: 대상 주소가 일시적으로 다른 주소에 있음을 나타낸다.
- 이동할 주소는 Location 헤더로 전달한다.
- 캐시 동작은 상태 코드와 캐시 제어 설정 등을 함께 봐야 한다.
  “301은 무조건 캐시된다”거나 “302는 절대 캐시되지 않는다”고 단정하지 않는다.

### 해시 함수를 이용한 단축 키 생성
원본 URL의 해시값을 계산하고, 그 값 일부 등을 이용해 단축 키 후보를 만든다.
원본으로 이동할 때는 해시를 역산하지 않고 저장된 매핑을 조회한다.

### 해시 후 충돌 해소
서로 다른 원본 URL에서 같은 단축 키가 나오면 충돌이다.

키 후보가 다른 URL에 이미 배정되었는지 확인해야 한다.
충돌하면 추가 입력을 넣어 다시 계산하는 등의 방법으로
다른 후보를 만들고 확인할 수 있다.

## 예시
긴 URL → 단축 키 생성 → 키와 원본 URL 저장
단축 주소 접속 → 키로 원본 URL 조회 → 원본 주소로 리다이렉션

## 주의할 점
- 해시를 사용한다고 단축 키의 유일성이 자동으로 보장되는 것은 아니다.
- 같은 원본 URL에 같은 키를 다시 사용하는 것과,
  다른 원본 URL이 같은 키를 갖는 충돌은 구분한다.
- 이번에는 흐름을 가볍게 살펴봤으며, 장 전체를 정독하거나 구현한 기록은 아니다.
