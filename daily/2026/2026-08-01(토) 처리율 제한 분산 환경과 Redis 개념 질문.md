# 📅 2026-08-01(토) 처리율 제한 분산 환경과 Redis 개념 질문

## 🎯 목표
- 가상 면접 사례로 배우는 대규모 시스템 설계 기초 4장 이어 읽기

## ✅ 완료
- 분산 환경에서 처리율 제한 장치를 구현할 때 단일 서버보다 고려할 점이 많아진다는 흐름 정리
- 여러 서버와 병렬 스레드 환경에서 경쟁 조건과 동기화 문제가 생길 수 있다는 점 확인
- 경쟁 조건의 대표 해결책으로 락이 있지만, 락은 시스템 성능을 떨어뜨릴 수 있다는 점 정리
- 고정 세션을 사용하면 같은 클라이언트 요청을 같은 처리율 제한 장치로 보낼 수 있지만, 확장성과 유연성이 떨어진다는 점 확인
- 여러 처리율 제한 장치가 같은 요청 카운터를 공유하려면 Redis 같은 중앙 집중형 데이터 저장소를 사용할 수 있다는 점 정리
- 데이터 센터에서 멀리 떨어진 사용자는 지연 시간이 증가할 수 있고, 엣지 서버를 사용해 사용자와 가까운 위치에서 트래픽을 처리하면 지연 시간을 줄일 수 있다는 점 확인
- 처리율 제한 장치를 설치한 뒤에는 제한 정책이 효과적으로 동작하는지 모니터링이 필요하다는 점 정리
- Redis는 메모리 기반 저장소이며 기본적으로 휘발성 특성이 있지만, RDB/AOF 같은 영속성 설정으로 재시작 후 복구를 도울 수 있다는 점 질문으로 확인

## ⏱️ 공부 시간
16:30 ~ 21:55 (총 5시간 25분)

## ✍️ 회고
가상면접 4장을 여기까지 읽었다. 오늘은 처리율 제한 장치가 단일 서버에서는 단순해 보이지만, 여러 서버로 확장되는 순간 경쟁 조건과 동기화 문제가 생긴다는 흐름을 잡았다.

Redis는 오늘 깊게 정리하기보다는 내일 이어서 공부할 주제로 임시 메모에 남겨두기로 했다. 지금은 Redis를 여러 서버가 함께 보는 빠른 메모리 저장소이자, 처리율 제한에서는 공용 카운터 역할을 하는 도구로 이해했다.
