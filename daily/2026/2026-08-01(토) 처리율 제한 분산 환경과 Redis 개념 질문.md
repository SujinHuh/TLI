# 📅 2026-08-01(토) 처리율 제한 분산 환경과 Redis 개념 질문

## 🎯 목표
- 가상 면접 사례로 배우는 대규모 시스템 설계 기초 4장 이어 읽기

## ✅ 완료
- 분산 환경에서 처리율 제한 장치를 구현할 때 단일 서버보다 고려할 점이 많아진다는 흐름 정리
- 여러 서버와 병렬 스레드 환경에서 경쟁 조건과 동기화 문제가 생길 수 있다는 점 확인
- 경쟁 조건의 대표 해결책으로 락이 있지만, 락은 시스템 성능을 떨어뜨릴 수 있다는 점 정리
- 고정 세션을 사용하면 같은 클라이언트 요청을 같은 처리율 제한 장치로 보낼 수 있지만, 확장성과 유연성이 떨어진다는 점 확인
- 여러 처리율 제한 장치가 같은 요청 카운터를 공유하려면 Redis 같은 중앙 집중형 데이터 저장소를 사용할 수 있다는 점 정리
- 데이터 센터에서 멀리 떨어진 사용자는 지연 시간이 증가할 수 있고, 엣지 서버를 사용해 사용자와 가까운 위치에서 트래픽을 처리하면 지연 시간을 줄일 수 있다는 점 확인
- 처리율 제한 장치를 설치한 뒤에는 제한 정책이 효과적으로 동작하는지 모니터링이 필요하다는 점 정리
- Redis는 메모리 기반 저장소이며 기본적으로 휘발성 특성이 있지만, RDB/AOF 같은 영속성 설정으로 재시작 후 복구를 도울 수 있다는 점 질문으로 확인

## ✍️ 회고
오늘은 날씨 관련해서 내가 보는 부분도 있었다.

구글 로그인 문제는 도메인이 있어야 한다고 해서, 우선 내가 임시로 사용하는 것이니 임시 비밀번호를 만들어 나만 쓸 수 있게 만들었다.

위에서 말한 것은 하네스 키트를 만들어 완성된 프로젝트이다. 그리고 AI 새로운 트렌드를 받아서 만드는 프로젝트는 LLM Wiki까지 만들었다.

AI가 생각보다 빠르게 발전하고 있는데, 나는 그 속도를 충분히 체감하지 못하고 있다는 생각이 들었다. 매번 직접 검색해서 따라가기보다는 관련 흐름을 빠르게 받아보는 편이 나을 것 같아서, 나의 편리성을 위해 만들어보는 프로젝트다. 지금은 Andrej Karpathy의 LLM Wiki를 참고해서 만들고 있는 중이다.

오늘은 가상 면접 책을 읽으면서 Redis에 대해서도 공부했다. Redis라는 이름만 알고 있었는데, 실제로 어떤 상황에서 사용하는지와 처리율 제한 장치에서 어떤 역할을 하는지 조금 알게 되었다. 서버 요청 횟수 같은 값을 Redis 같은 메모리 기반 저장소에 카운터로 저장하면, 로드밸런싱으로 요청이 여러 서버에 나뉘어 들어가더라도 각 서버가 따로 자기 메모리만 보는 문제가 줄어든다는 점을 이해했다.

특히 서버가 여러 대일 때는 각 서버가 요청 횟수를 따로 기억하면 전체 요청 수를 정확히 알기 어렵고, 그래서 Redis 같은 중앙 저장소를 통해 요청 카운터를 공유할 수 있다는 점이 분산 처리 환경과 연결되어 이해되었다.
