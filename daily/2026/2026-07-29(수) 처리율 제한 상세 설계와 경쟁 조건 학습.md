# 📅 2026-07-29(수) 처리율 제한 상세 설계와 경쟁 조건 학습

## 🎯 목표
- 가상면접 4장 처리율 제한 장치의 상세 설계 읽기
- 처리율 제한 규칙이 어디에 저장되고 어떻게 사용되는지 이해하기
- 분산 환경에서 처리율 제한 장치를 구현할 때 생기는 경쟁 조건 이해하기

## ✅ 완료
- 처리율 제한 규칙은 디스크에 보관하고, 작업 프로세스가 수시로 읽어 캐시에 저장한다는 점 정리
- 클라이언트 요청은 먼저 처리율 제한 미들웨어에 도달하고, 미들웨어가 캐시에서 제한 규칙을 가져온다는 점 확인
- 처리율 제한 미들웨어는 Redis 캐시에서 카운터와 마지막 요청 타임스탬프를 가져와 요청 제한 여부를 판단한다는 점 정리
- 요청이 처리율 제한에 걸리면 API는 클라이언트에게 `429 Too Many Requests` 응답을 보낸다는 점 확인
- 제한된 요청은 그대로 버릴 수도 있고, 나중에 처리하기 위해 메시지 큐에 보관할 수도 있다는 점 정리
- 단일 서버와 달리 여러 서버와 병렬 스레드를 지원하는 분산 환경에서는 경쟁 조건과 동기화 문제가 생긴다는 점 확인
- 경쟁 조건은 여러 스레드가 Redis의 같은 카운터 값을 동시에 읽고 갱신할 때 실제 요청 수와 저장된 카운터 값이 어긋날 수 있는 문제라는 점 정리
- 락을 사용하면 경쟁 조건을 해결할 수 있지만 성능 저하가 생길 수 있다는 점 확인
- 락 대신 사용할 수 있는 해결책으로 Lua 스크립트와 Redis의 정렬 집합, Sorted Set을 확인
- 동기화 이슈는 내일 이어서 공부하기로 함
