1.운영 DB와 통계 DB를 분리한 이유를 설명하시오.

개념

DB 문제는 정합성, 성능, 동시성의 균형을 묻는 경우가 많다. 인덱스는 조회 성능을 높이지만 쓰기 비용과 저장 공간을 증가시키고, 트랜잭션은 ACID를 통해 데이터 일관성을 보장한다.

답변

실행 계획에서는 index 사용 여부, rows 추정치, join 방식, filesort/temp table 여부를 확인한다. isolation level은 dirty read, non-repeatable read, phantom read 같은 현상을 어디까지 막을지 결정한다. 운영 DB와 통계 DB를 분리하는 이유는 대량 조회와 배치가 실시간 트랜잭션 처리에 주는 부하를 줄이고 장애 영향 범위를 분리하기 위해서다.

3.DB를 논리 분리가 아니라 물리 분리했을 때의 장점과 단점을 설명하시오.

답변

장점은 대량 조회, 집계, 배치 작업이 운영 트랜잭션 DB의 CPU, I/O, connection pool을 잠식하지 않는다는 점이다. 장애가 나도 영향 범위를 통계 DB나 배치 영역으로 제한하기 쉽다. 단점은 데이터 동기화 지연, 복제/ETL 실패, 운영 비용 증가, 정합성 검증 로직이 필요하다는 점이다. 따라서 실시간 정합성이 필요한 데이터와 지연 허용 가능한 통계 데이터를 명확히 나눠야 한다.

개념

Spring Batch는 대량 데이터를 안정적으로 처리하기 위한 배치 프레임워크다. Job은 전체 배치 작업, Step은 작업 단계, Reader/Processor/Writer는 읽기, 가공, 쓰기 역할을 나눈다.

답변

8.배치 중복 실행을 막거나 멱등하게 만드는 방법을 설명하시오.

개념

REST와 Web Backend 문제는 HTTP를 계약으로 이해하는지가 중요하다. method, status code, header/body, 인증 방식, timeout, retry 정책이 모두 클라이언트와 서버 사이의 명확한 약속이다.

답변

9.대량 배치 처리에서 실패 격리 전략을 설명하시오.

개념

실패 격리는 한 기능, 외부 시스템, 배치 단위의 장애가 전체 서비스 장애로 번지지 않도록 경계를 나누는 설계다. 대표적으로 circuit breaker는 실패가 누적된 호출을 빠르게 차단하고, bulkhead는 자원을 격리한다.

답변

circuit breaker는 외부 API가 느리거나 실패할 때 계속 호출하지 않고 일정 시간 차단해 thread와 connection 고갈을 막는다. bulkhead는 기능별 thread pool, connection pool, queue를 분리해 한 영역 장애가 전체 자원을 잡아먹지 않게 한다. 배치에서는 service_id 단위 트랜잭션, 재처리 큐, 실패 이력 저장으로 실패 범위를 좁힐 수 있다.

MyBatis와 DB 접근

1.MyBatis의 동작 원리를 설명하시오.

개념

MyBatis는 SQL을 개발자가 직접 작성하고 mapper를 통해 Java 객체와 결과를 매핑하는 persistence framework다. SQL 제어력이 높아 복잡한 조회나 튜닝이 필요한 시스템에서 장점이 있다.

답변

JPA는 객체와 테이블 매핑을 중심으로 변경 감지, 영속성 컨텍스트, JPQL 등을 제공한다. MyBatis는 SQL이 명시적이라 실행 쿼리를 예측하기 쉽지만 반복 SQL과 매핑 관리가 늘어날 수 있다. 동적 SQL은 조건 누락, 인덱스 미사용, SQL Injection 가능성을 주의해야 하며 실행 계획과 실제 rows를 확인해야 한다.

2.FeignClient 연동 시 timeout을 어떻게 설정할지 설명하시오.

개념

FeignClient timeout은 외부 API 호출이 내부 요청 처리 시간을 무한정 잡아먹지 않게 하는 기본 보호 장치다. 연결 수립과 응답 대기를 나눠 설정한다.

답변

connect timeout은 TCP 연결을 맺는 데 허용할 시간이고 read timeout은 요청 후 응답 데이터를 기다리는 시간이다. 내부 API의 목표 응답 시간보다 외부 호출 timeout 총합이 과도하게 길어지지 않게 잡아야 한다. retry를 함께 쓰면 총 대기 시간이 늘어나므로 횟수와 backoff를 제한하고, 장애가 반복되면 circuit breaker로 빠르게 차단한다.

장애 대응 경험

1.Schema Validation 실패가 발생했을 때 원인을 어떻게 좁혀 볼지 설명하시오.

개념

Schema Validation 실패는 데이터 구조가 약속한 schema와 맞지 않는 상황이다. 필드 누락, 타입 불일치, enum 값 오류, null 허용 위반, schema version 불일치가 대표 원인이다.

답변

먼저 실패한 원본 데이터와 validation error path를 확인해 어떤 필드에서 실패했는지 본다. 이후 producer 쪽 배포 변경, schema version 변경, optional/required 조건 변경, 샘플 데이터의 null과 타입을 확인한다. 재발 방지를 위해 실패 샘플을 테스트 케이스로 추가하고, 실패 데이터는 별도 저장소에 격리해 수정 후 재처리할 수 있게 한다.

2.reset 로직 개선 경험을 상태 전환과 재처리 관점에서 설명하시오.

개념

장애 대응 경험 문제는 “무엇을 했다”보다 원인 좁히기, 영향 범위 확인, 재발 방지까지 이어지는 사고방식을 본다. Schema Validation은 입력/파일/메시지가 기대한 구조와 타입을 만족하는지 확인하는 방어선이다.

답변

먼저 실패한 데이터 샘플, schema version, 필수 필드, null/format 오류, 배포 변경 여부를 확인한다. reset 로직은 상태 전환이 중복 실행되어도 안전한지, 실패 후 재처리할 때 이전 상태를 깨뜨리지 않는지 봐야 한다. 재발 방지는 테스트 케이스, 검증 로그, 알림, 재처리 절차 문서화까지 포함해 답변하는 것이 좋다.

3.S3 업로드 실패 처리 경험을 DB/S3 정합성 관점에서 설명하시오.

개념

S3는 객체 스토리지로 파일과 메타데이터를 key 기반으로 저장한다. DB처럼 트랜잭션과 복잡한 질의를 제공하는 저장소가 아니므로 정합성 전략을 별도로 설계해야 한다.

답변

S3 업로드와 DB 저장은 하나의 로컬 트랜잭션으로 묶을 수 없기 때문에 상태값, 재시도 큐, 보상 삭제, 멱등 object key가 필요하다. Parquet은 columnar 형식이라 필요한 컬럼만 읽기 좋고 압축 효율이 높아 대용량 분석에 유리하다. CSV/JSON보다 사람이 바로 읽기는 어렵지만 스키마와 컬럼 기반 처리 측면에서 장점이 있다.

4.장애 발생 시 로그에서 어떤 값을 먼저 확인할지 설명하시오.

개념

장애 로그 분석은 영향 범위와 실패 지점을 빠르게 좁히는 과정이다. 먼저 시간, 요청 식별자, 에러 유형, 지연 구간을 확인해야 한다.

답변

우선 장애 발생 시각의 error rate와 대표 trace id를 잡고, 해당 요청의 API path, service id, status code, exception type, latency를 본다. 외부 API 호출이 있으면 대상 시스템, 응답 코드, timeout 여부를 확인하고, DB 작업이 있으면 쿼리 식별자, lock wait, connection 대기 여부를 확인한다. 같은 trace id로 여러 로그를 이어 보면 어느 구간에서 실패했는지 빠르게 좁힐 수 있다.
