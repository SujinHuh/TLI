# EU Data Act 대응 프로젝트 업무 상세 정리

## 작성 목적

이 문서는 면접 전 회사에 전달하기 위한 업무 상세 정리본입니다. 개인적인 견해보다 실제 프로젝트 구조, 데이터 흐름, 담당 범위, 구현 내용을 중심으로 정리했습니다.

## 1. 프로젝트 전체 흐름

이 프로젝트는 EU Data Act 대응을 위해 사용자가 요청한 데이터를 외부 제3자에게 제공할 수 있도록 백엔드 API와 연계 시스템을 개발한 프로젝트입니다. 사용자가 데이터 제공을 요청하면 시스템에서 요청 단위의 티켓이 발급되고, 그 티켓을 기준으로 제공 가능한 데이터가 조회되고 전달되는 구조였습니다.

제가 주로 담당한 영역은 이 흐름 안에서 데이터 제공 여부를 판단하는 데 필요한 기준정보와 메타데이터를 관리하는 부분이었습니다. 사용자 요청이 들어왔다고 해서 모든 데이터를 바로 제공할 수 있는 것은 아니기 때문에, 어떤 서비스의 어떤 데이터가 제공 대상인지, 현재 유효한 버전은 무엇인지, 제공 가능한 상태인지 확인할 수 있는 관리 구조가 필요했습니다.

이 역할을 담당하는 MetaService 영역에서 기준정보 관리와 메타데이터 관리 기능을 개발했습니다.

## 2. 담당 범위

제가 담당한 업무는 크게 아래 영역입니다.

- 서비스별 기준정보 등록, 조회, 수정 API 개발
- 메타데이터 Excel/CSV 업로드 및 파싱 처리
- 등록된 메타데이터와 필드 정의 정보 CSV 다운로드 기능 개발
- 대용량 검증 파일 업로드 처리
- 외부 검증 API 연계 및 검증 결과 저장
- 메타데이터 파일 업로드와 S3 적재 흐름을 MetaService 내부 처리로 이관
- Excel/CSV 인코딩 이슈 개선
- 메타데이터 버전 상태 전환 배치 개발
- 서비스 단위 트랜잭션 분리
- 일일 통계 배치 개발
- 운영 DB와 통계 DB 역할 분리

## 3. 기준정보 관리

서비스별 기준정보를 등록, 조회, 수정하는 API를 구현했습니다.

기준정보에는 서비스 식별 정보, 제공 상태, 데이터 제공 여부 판단에 필요한 운영 설정값, 메타데이터 버전, 적용일 같은 정보가 포함되어 있었습니다. 세부 운영 정책이나 실제 판단 기준은 내부 정책에 가까운 내용이기 때문에, 외부 설명에서는 서비스 단위로 데이터 제공 가능 여부를 판단하기 위한 기준정보를 관리했다고 설명할 수 있습니다.

## 4. 메타데이터 관리

서비스에서 제공하는 데이터 구조를 메타데이터로 관리하는 기능을 개발했습니다.

여기서 메타데이터는 특정 서비스 데이터가 어떤 항목들로 구성되어 있는지, 각 항목의 타입이나 설명 정보는 무엇인지, 제공 제한이나 민감 처리 대상에 해당하는지 등을 정의하는 정보입니다.

담당자는 Excel 또는 CSV 파일을 통해 데이터 구조 정보를 한 번에 등록하거나 수정할 수 있었고, 시스템에서는 이를 서비스와 버전 기준으로 관리했습니다.

## 5. Excel/CSV 업로드

업로드 기능에서는 Excel 또는 CSV 파일에 들어 있는 데이터 구조 정보를 읽어 파싱하고, 서비스 기준정보와 연결해 저장하는 흐름을 구현했습니다.

업로드 과정에서는 필수 항목 누락 여부, 데이터 형식, 기존 버전과의 관계를 확인하는 처리가 필요했습니다. 업로드된 메타데이터는 이후 실제 데이터 검증이나 제공 가능 여부 판단에 사용되기 때문에, 단순 파일 저장보다 버전 기준 관리가 중요했습니다.

제공 metadata CSV에는 아래 6개 필드가 포함되었습니다.

- `schema`
- `fieldname`
- `datatype`
- `description(en)`
- `description(fr)`
- `tradesecret`

## 6. CSV 다운로드

운영자가 화면에서 많은 데이터를 한 번에 확인하기 어려운 경우가 있어, 등록된 메타데이터와 필드 정의 정보를 CSV로 다운로드할 수 있는 기능도 제공했습니다.

담당자가 파일로 내려받아 검토하고, 수정이 필요하면 다시 업로드할 수 있도록 하기 위한 기능이었습니다. 실제 운영에서는 화면에서 한 줄씩 확인하는 것보다 파일 기반으로 검토하는 경우가 많았기 때문에 업로드와 다운로드 기능을 함께 구현했습니다.

## 7. 검증 파일 업로드 및 외부 검증 API 연계

검증 흐름에서는 담당자가 실제 데이터 검증을 위한 대용량 파일을 업로드하면, 시스템에서 해당 파일을 처리한 뒤 외부 검증 API와 연계해 검증 결과를 받는 구조였습니다.

검증 대상 파일은 압축 파일 형태로 업로드되었고, 내부에는 실제 데이터 구조 검증에 필요한 파일들이 포함되어 있었습니다. 시스템은 업로드된 파일을 처리한 뒤 외부 검증 API를 호출했고, 수신한 결과를 메타데이터 버전 단위로 저장했습니다.

이렇게 저장된 결과를 통해 특정 메타데이터 버전이 실제 데이터와 맞는지, 제공 가능한 상태인지 추적할 수 있었습니다.

## 8. S3 적재 흐름 이관

기존에 서버리스 구조로 분리되어 있던 메타데이터 파일 업로드와 S3 적재 흐름을 MetaService 내부 처리로 이관했습니다.

기존에는 업로드 이후 일부 처리가 별도로 수행되고 있어 처리 흐름이 나뉘어 있었고, 문제가 생겼을 때 어느 구간에서 오류가 발생했는지 확인하기 어려운 부분이 있었습니다.

파일 업로드, 파싱, 저장, S3 적재까지 이어지는 흐름을 Spring Boot 기반 MetaService 내부에서 처리하도록 정리했습니다. 이를 통해 업로드 흐름을 한곳에서 관리할 수 있게 되었고, 장애가 났을 때 확인해야 하는 지점을 줄일 수 있었습니다.

## 9. 메타데이터 상태와 S3 업로드 시점

메타데이터는 상태에 따라 처리 흐름이 달랐습니다.

### saved temporarily

최초 업로드 이후 아직 live로 확정되지 않은 임시 저장 상태입니다. 이 상태에서는 파일을 S3에 바로 업로드하지 않고 DB 데이터 중심으로 관리했습니다.

### live

실제 제공 가능한 상태입니다. `saved temporarily` 상태에서 `live` 상태로 변경될 때 S3 업로드가 수행되도록 처리했습니다.

### deprecated

더 이상 사용하지 않는 상태입니다. 기존에는 파일 및 버킷 삭제 로직이 있었으나, 이전 버전 파일은 버전 관리를 위해 삭제하지 않고 남겨두는 방향으로 정리했습니다.

## 10. CSV 인코딩 이슈 개선

운영 중 Excel과 CSV 인코딩 차이 때문에 한글이나 다국어 설명이 깨지거나, 서버에서 파일을 읽는 과정에서 오류가 나는 문제가 있었습니다.

원인을 확인해보니 Excel에서 CSV를 저장하는 방식, UTF-8 BOM 포함 여부, 다운로드 시 Content-Type 설정에 따라 같은 파일도 다르게 해석되는 경우가 있었습니다.

이 부분은 다운로드 시 인코딩 방식을 정리하고, 업로드 시 서버에서 처리 가능한 파일 기준을 명확히 하면서 개선했습니다. 담당자가 파일을 수정한 뒤 다시 업로드할 때 같은 문제가 반복되지 않도록 업로드와 다운로드 가이드도 함께 정리했습니다.

## 11. 메타데이터 상태 전환 배치

EU Data Act 대응 시스템에서는 사용자가 데이터를 요청했을 때 어떤 서비스의 어떤 메타데이터 버전이 현재 유효한지 판단할 수 있어야 했습니다.

MetaService에서는 서비스별 메타데이터 버전을 관리하고, 각 버전이 언제부터 적용되는지, 기존 버전은 언제부터 더 이상 사용되지 않는지 관리하는 기능이 필요했습니다.

제가 담당한 부분은 메타데이터 버전의 상태 전환을 배치로 처리하는 기능이었습니다. 배치는 정해진 시간에 실행되면서 서비스별 메타데이터 버전의 적용일과 현재 상태를 확인하고, 조건에 맞는 버전을 다음 상태로 변경하는 방식으로 동작했습니다.

상태 전환 로직은 Spring Batch의 Tasklet 방식으로 구현했습니다. 배치는 서비스별 메타데이터 버전을 조회한 뒤 적용일과 현재 상태를 기준으로 활성화 대상인지, 기존 버전을 종료 준비 상태로 변경해야 하는지 판단했습니다.

신규 버전이 활성화되면 기존 활성 버전은 바로 종료하지 않고 일정 기간 유예 상태로 전환되도록 처리했습니다. 이 유예 구간은 외부 연계 시스템이나 데이터를 받아가는 쪽에서 버전 변경에 대응할 시간이 필요했기 때문에 두었습니다.

## 12. 상태 전환 배치 트랜잭션 구조 개선

기존 구조에서는 여러 서비스의 상태 전환이 하나의 트랜잭션 안에서 처리되고 있었습니다. 이 구조에서는 특정 서비스 하나에서 오류가 발생해도 전체 배치가 롤백될 수 있었습니다.

예를 들어 대부분의 서비스는 정상적으로 상태 전환이 가능한데 일부 서비스의 데이터나 상태값에 문제가 있으면, 정상 서비스까지 함께 반영되지 않는 문제가 생길 수 있었습니다.

이를 개선하기 위해 처리 단위를 서비스 기준으로 나누었습니다. 각 서비스별로 트랜잭션을 분리해서, 특정 서비스에서 오류가 발생하더라도 해당 서비스만 롤백되고 다른 서비스의 처리 결과는 유지되도록 변경했습니다.

이 방식은 부분 성공을 허용하는 구조이기 때문에, 서비스 단위 처리가 업무적으로 독립적이라는 전제가 중요했습니다. 특정 서비스의 상태 전환 실패가 다른 서비스의 상태 전환 결과까지 무효화할 필요는 없다고 판단했기 때문에 트랜잭션 경계를 서비스 단위로 조정했습니다. 다만 실패한 서비스는 별도로 식별하고 재처리할 수 있어야 하므로, 배치 실행 결과와 실패 원인을 남기는 것이 중요했습니다.

이렇게 바꾸면서 배치 실패가 전체 서비스로 번지는 상황을 줄일 수 있었습니다.

## 13. 일일 통계 배치

EU Data Act 대응 시스템에서는 메타데이터가 등록되거나 스키마 정보가 변경되는 일이 계속 발생했습니다. 운영 화면에서는 현재 서비스 기준정보와 메타데이터 상태를 관리해야 했고, 별도로 전일 기준으로 어떤 메타데이터가 변경되었는지, 어떤 스키마 정보가 업데이트되었는지 집계해서 확인할 필요가 있었습니다.

제가 담당한 업무는 전일 기준 메타데이터 변경 건수와 스키마 업데이트 건수를 집계하는 일일 통계 배치를 개발하는 것이었습니다.

배치는 하루에 한 번 실행되며, 운영 DB에 저장된 메타데이터와 스키마 정보를 조회한 뒤 서비스 단위와 스키마 단위로 변경 건수를 집계하고, 그 결과를 통계용 저장소에 적재하는 흐름으로 동작했습니다.

### Job 정보

- Job 이름: `MetaserviceStatisticsJob`
- 실행 시각: 매일 00시 00분
- 주요 목적: 서비스와 메타데이터 관련 일 단위 통계 수집

### 통계 항목

- `service_count`
- `dataset_version_up_count`
- `schema_count`

### 집계 기준

- service 도출 기준: `DEL_FG = 'N'`, `STS_CD = '1'`
- meta/schema 도출 기준: `DEL_FG = 'N'`, `STS_CD = '2'`

## 14. 통계 DB 분리

초기에는 운영 데이터와 통계 데이터가 같은 DB 또는 같은 DB 인스턴스/저장소 영역에서 함께 관리되는 구조였습니다.

운영 데이터는 실제 서비스 처리와 상태 관리에 사용되는 데이터이고, 통계 데이터는 전일 변경 건수나 집계 결과처럼 조회와 분석 목적에 가까운 데이터였습니다. 두 데이터는 사용 목적이 다른데도 같은 저장소에 함께 있어, 통계 적재나 조회가 많아질 경우 운영 DB에 영향을 줄 수 있는 구조였습니다.

이 부분을 개선하기 위해 운영 DB와 통계 DB의 역할을 분리했습니다.

운영 DB는 실제 서비스 기준정보와 메타데이터를 조회하는 역할에 집중하고, 통계 DB는 배치 결과를 적재하고 통계 조회에 사용하는 역할로 나누었습니다. 이렇게 나누면서 데이터의 목적이 더 명확해졌고, 운영 처리와 통계 처리가 같은 저장소 안에서 섞이는 문제를 줄일 수 있었습니다.

배치에서는 운영 DB에서 필요한 데이터를 읽고, 집계 결과는 통계 DB에 저장해야 했기 때문에 읽기와 쓰기 대상이 달랐습니다. 이를 위해 데이터소스 설정을 분리하고, 적절한 DB로 연결될 수 있도록 구성했습니다.

운영 데이터 조회는 운영 DB를 바라보고, 통계 결과 적재는 통계 DB를 바라보는 흐름으로 정리했습니다.

## 15. 통계 배치 read/write 분리

기존 통계 배치는 `insert-select` 또는 읽기와 쓰기가 결합된 구조였습니다. 운영 데이터 테이블에서 데이터를 읽고 통계 테이블에 적재하는 흐름이 같은 DB 컨텍스트 안에서 강하게 결합되어 있었습니다.

이를 read query와 write query로 분리했습니다.

- `RStatistics.xml`: MetaService 영역의 원천 데이터를 조회해 서비스별 통계 데이터를 생성
- `WStatistics.xml`: Statistics 영역의 통계 테이블에 `foreach` batch insert 형태로 적재

운영 DB에서는 원천 데이터를 조회하고, 통계 DB에서는 집계 결과를 저장하도록 역할을 분리했습니다.

## 16. 정리

제가 담당한 업무는 EU Data Act 대응 시스템에서 데이터 제공 판단에 필요한 기준정보와 메타데이터를 관리하는 백엔드 기능 개발이었습니다.

서비스 기준정보 API, 메타데이터 Excel/CSV 업로드와 다운로드, 대용량 검증 파일 업로드, 외부 검증 API 연계, 검증 결과 저장, S3 적재 구조 이관, CSV 인코딩 이슈 개선, 메타데이터 상태 전환 배치, 트랜잭션 구조 개선, 일일 통계 배치, 통계 DB 분리를 담당했습니다.

이 과정에서 단순히 CRUD API를 만드는 것보다, 데이터 제공 흐름 안에서 기준정보와 메타데이터가 어떤 역할을 하는지 이해하고 운영자가 파일 기반으로 대량 데이터를 관리할 수 있도록 흐름을 정리하는 데 초점을 두었습니다.
