# 스페이드컴퍼니 면접 예상질문

## 답변 방향

이번 면접은 단순히 CS 정답을 암기해서 맞히는 방식보다, 업무 구조를 이해하고 있는지, 왜 그렇게 판단했는지, 모르는 부분을 어떻게 추론하고 확인하는지를 보는 방식으로 준비합니다.

5년차 백엔드 개발자 기준에서는 “기능을 구현했다”에서 답변이 끝나면 약합니다. 10년차 이상의 면접관은 구현 사실보다 그 판단의 근거, 트레이드오프, 장애 시 확인 순서, 운영 영향 범위를 더 깊게 물을 가능성이 큽니다.

따라서 답변에는 트랜잭션 경계, 장애 영향 범위, 운영 안정성, 성능 병목, 대안 비교, 확인 방법이 같이 들어가야 합니다.

답변은 아래 흐름을 기본으로 잡습니다.

```text
제가 아는 범위는 여기까지입니다.
구조상으로는 이런 요소가 필요할 것 같습니다.
그래서 저는 이렇게 판단했습니다.
실제 업무에서는 공식 문서, 설정값, 로그, 실행 계획, 모니터링 지표로 확인하겠습니다.
```

주의할 점은 실제로 확인하지 않은 장애나 성능 개선 효과를 단정하지 않는 것입니다. “실제 장애가 발생해서 바꿨다”보다 “데이터가 늘거나 배치 시간이 길어지면 이런 구조적 리스크가 있어 개선했다”처럼 말하는 편이 안전합니다.

## 답변을 풍부하게 만드는 반대/대안 개념

면접에서 답변을 더 깊게 만들려면 “제가 선택한 방식”만 말하지 말고, 반대 개념이나 대안도 함께 비교합니다. 아래 표현을 외워서 그대로 말하기보다, 질문에 맞게 한두 개만 꺼내 쓰는 것이 좋습니다.

- 전체 시스템 직접 구현 vs 담당 모듈 구현
  - 전체 EU Data Act 시스템을 모두 구현한 것이 아니라, MetaService에서 기준정보, 메타데이터, 상태 전환 배치, 통계 배치 흐름을 담당했다고 범위를 명확히 말합니다.
- 기준정보 vs 메타데이터
  - 기준정보는 “이 서비스가 제공 대상인지, 어떤 상태인지”를 보는 운영 기준이고, 메타데이터는 “실제 제공 데이터가 어떤 schema와 field로 구성되는지”를 정의하는 정보입니다.
- 화면 단건 등록 vs Excel/CSV 대량 업로드
  - 단건 등록은 검증 흐름이 단순하지만 운영자가 많은 필드를 반복 입력해야 합니다. Excel/CSV 업로드는 대량 반영에 유리하지만 파싱, 인코딩, 필수값 검증, 실패 재처리 설계가 중요합니다.
- CSV vs Excel
  - CSV는 단순 텍스트라 가볍지만 인코딩과 구분자 문제가 생길 수 있습니다. Excel은 운영자에게 익숙하지만 라이브러리 처리, 셀 타입, 대용량 메모리 사용을 고려해야 합니다.
- 임시 저장 시점 S3 업로드 vs live 전환 시점 S3 업로드
  - 임시 저장 시점에 S3에 올리면 빠르게 외부 저장소에 남길 수 있지만, 제공 확정 전 파일이 남는 정합성 문제가 생깁니다. live 전환 시점 업로드는 확정된 데이터 중심으로 관리할 수 있지만, DB와 S3 사이 실패 처리와 재처리가 중요합니다.
- 서버리스 분리 vs MetaService 내부 이관
  - 서버리스는 독립 확장과 비동기 처리에 유리하지만 흐름이 분산되면 장애 추적이 어려워질 수 있습니다. 내부 이관은 흐름과 로그를 한곳에서 보기 쉽지만 서비스 책임과 부하가 늘 수 있습니다.
- 수동 상태 변경 vs 배치 자동화
  - 수동 처리는 예외 대응이 유연하지만 누락과 시점 오류가 생기기 쉽습니다. 배치 자동화는 일관된 상태 전이에 유리하지만 실패 시 재처리 기준과 실행 이력 관리가 필요합니다.
- 전체 트랜잭션 원자성 vs service_id 단위 부분 성공
  - 전체 트랜잭션은 모두 성공하거나 모두 실패하므로 정합성이 단순합니다. 반대로 service_id 단위 부분 성공은 한 서비스 실패가 전체 배치 실패로 번지는 것을 줄일 수 있지만, 실패 서비스 목록과 재처리 기준을 따로 관리해야 합니다.
- 전체 롤백 vs 실패 건만 롤백
  - 전체 롤백은 데이터 상태를 단순하게 유지하기 쉽지만 성공 가능한 데이터까지 다시 처리해야 합니다. 실패 건만 롤백하면 재처리 비용을 줄일 수 있지만, 어떤 단위까지 부분 성공을 허용할지 업무 기준이 필요합니다.
- 실시간 집계 vs 일일 배치 집계
  - 실시간 집계는 최신성을 확보할 수 있지만 요청마다 계산 비용이 발생합니다. 일일 배치는 최신성은 낮지만 UTC 기준 일자처럼 명확한 기준으로 안정적인 집계가 가능합니다.
- 단일 DB 관리 vs 운영 DB/통계 DB 분리
  - 단일 DB는 구조가 단순하지만 통계 적재나 조회가 운영 DB 자원에 영향을 줄 수 있습니다. DB 분리는 책임과 부하를 나누는 데 유리하지만 연결 설정, 장애 대응, 모니터링 복잡도가 늘어납니다.
- CQRS vs 단순 DB 역할 분리
  - CQRS는 command 모델과 query 모델을 의도적으로 분리하는 아키텍처 패턴입니다. 이 프로젝트는 운영 DB와 통계 DB의 역할 분리로 설명하는 것이 우선이고, CQRS 질문이 나오면 “개념적으로는 읽기/쓰기 관심사를 분리한다는 점이 닮았지만, 완전한 CQRS 도입으로 단정하지는 않겠다”고 답합니다.
- insert-select vs select 후 batch insert
  - insert-select는 같은 DB 안에서 처리할 때 단순하고 빠를 수 있습니다. select와 batch insert를 분리하면 운영 DB 조회와 통계 DB 적재 책임을 나눌 수 있지만, 애플리케이션 메모리와 네트워크 왕복 비용을 고려해야 합니다.
- MVCC consistent read vs locking read
  - 일반 SELECT는 보통 MVCC 기반 consistent read라 row lock을 직접 잡지 않습니다. 반대로 SELECT FOR UPDATE 같은 locking read는 이후 수정 가능성을 전제로 lock을 잡아 동시성에 영향을 줄 수 있습니다.
- lock 문제 vs DB 자원 사용 문제
  - 조회가 느리다고 무조건 lock 문제로 보면 안 됩니다. 대량 스캔, 인덱스 미사용, 긴 트랜잭션, 커넥션 점유, undo purge 지연처럼 DB 자원 사용 관점도 함께 봐야 합니다.
- LazyConnectionDataSourceProxy vs 즉시 커넥션 획득
  - 즉시 커넥션을 잡으면 흐름은 단순하지만 트랜잭션 속성 기반 라우팅이 어려워질 수 있습니다. LazyConnectionDataSourceProxy는 실제 쿼리 시점까지 커넥션 획득을 늦춰 라우팅 판단 여지를 만들지만, 단독으로 read/write routing을 해주는 것은 아닙니다. MetaService에서 직접 사용한 것으로 단정하지 말고 개념 질문이 들어왔을 때만 설명합니다.
- DB 물리 분리 vs 쿼리/인덱스 튜닝
  - DB를 분리하면 자원 경합을 줄일 수 있지만 항상 성능 개선으로 이어지는 것은 아닙니다. 병목이 잘못된 실행 계획이나 인덱스 부재라면 먼저 쿼리 튜닝이 더 효과적일 수 있습니다.
- 전체 파일 메모리 로딩 vs streaming 처리
  - 전체 로딩은 구현이 단순하지만 대용량 파일에서 OOM 위험이 있습니다. streaming 처리는 메모리 사용을 줄이지만 파싱, 검증, 실패 위치 추적이 더 복잡해집니다.
- 단순 재시도 vs circuit breaker/fail fast
  - 단순 retry는 일시 장애에 효과적이지만 외부 시스템 장애가 길어지면 부하를 키울 수 있습니다. circuit breaker나 fail fast는 장애 전파를 줄일 수 있지만 설정 기준과 복구 정책이 필요합니다. 실제 적용 여부가 기억나지 않으면 “제가 직접 확인한 범위는 로그 기반 재실행이고, timeout/retry/circuit breaker는 설정과 운영 지표로 확인하겠습니다”라고 답변합니다.
- 상태값 기반 if/else vs 상태 머신
  - 단순 상태값 분기는 구현이 쉽지만 상태가 늘어나면 전이 규칙이 흩어질 수 있습니다. 상태 머신은 허용 가능한 전이를 명확히 만들 수 있지만 설계와 구현 복잡도가 증가합니다.
- DB Source of Truth vs S3 Source of Truth
  - 보통 제공 가능 여부와 메타데이터 상태는 DB를 기준으로 판단하는 것이 자연스럽습니다. 다만 실제 파일 존재 여부는 S3 object 확인이 필요하므로, DB 상태와 S3 object key를 연결해 정합성을 확인해야 합니다.
- 중복 실행 차단 vs 멱등하게 허용
  - 배치 중복 실행을 lock으로 막으면 중복 처리를 예방할 수 있지만 락 해제 실패에 주의해야 합니다. 멱등하게 설계하면 같은 입력이 반복되어도 결과가 같아 재처리가 쉬워지지만 key 설계가 중요합니다.

## 1. EU Data Act 전체 흐름과 MetaService 역할

이 파트는 프로젝트의 목적, 전체 데이터 제공 흐름, 그리고 그 안에서 MetaService가 왜 필요한지 설명하는 영역입니다. 면접에서는 “전체를 다 했다”가 아니라 “전체 흐름을 이해하고, 그중 데이터 제공 판단에 필요한 MetaService 영역을 담당했다”는 식으로 범위를 명확히 잡습니다.

### 1-1. 이 프로젝트 전체 흐름을 설명해 주세요.

#### 답변 핵심

- EU Data Act 대응을 위해 사용자가 요청한 데이터를 외부 제3자에게 제공할 수 있도록 만든 시스템이다.
- 사용자가 데이터 제공을 요청하면 요청 단위 티켓이 발급되고, 해당 티켓 기준으로 제공 가능한 데이터가 조회되고 전달되는 구조였다.
- 내가 담당한 영역은 MetaService에서 데이터 제공 판단에 필요한 기준정보와 메타데이터를 관리하는 부분이었다.
- 기준정보, 메타데이터 업로드/다운로드, 검증 API 연계, S3 적재, 상태 전환 배치, 통계 배치를 담당했다.

#### 답변 예시

제가 담당한 프로젝트는 EU Data Act 대응을 위해 사용자가 요청한 데이터를 외부 제3자에게 제공할 수 있도록 지원하는 백엔드 시스템이었습니다. 전체적으로는 사용자가 데이터 제공을 요청하면 요청 단위의 티켓이 발급되고, 그 티켓을 기준으로 제공 가능한 데이터가 조회되고 전달되는 구조였습니다.

그중 제가 담당한 영역은 MetaService였습니다. 사용자 요청이 들어왔다고 해서 모든 데이터를 바로 제공할 수 있는 것은 아니기 때문에, 어떤 서비스의 어떤 데이터가 제공 대상인지, 현재 유효한 메타데이터 버전이 무엇인지, 제공 가능한 상태인지 판단할 수 있는 기준정보와 메타데이터 관리가 필요했습니다. 저는 이 기준정보 API, 메타데이터 Excel/CSV 업로드와 다운로드, 검증 API 연계, S3 적재 흐름, 상태 전환 배치, 통계 배치 개발을 담당했습니다.

5년차 백엔드 개발자 관점에서는 단순 API 구현보다 데이터 제공 판단에 필요한 기준정보와 메타데이터의 lifecycle을 안정적으로 관리하는 것이 중요했습니다. 상태값이 잘못 전환되거나 검증 결과가 잘못 연결되면 제공 가능 여부 판단 자체가 흔들릴 수 있기 때문에, 파일 업로드, 버전, 상태 전환, 검증 결과, 통계 배치가 어떤 흐름으로 연결되는지를 보고 개발했습니다.

#### 꼬리 질문

<details>
<summary>MetaService가 전체 시스템에서 어떤 역할인가요?</summary>

MetaService는 사용자의 데이터 제공 요청을 실제 데이터 구조와 연결하기 전에, 어떤 서비스와 메타데이터 버전이 제공 가능한지 판단할 수 있게 기준정보와 메타데이터 lifecycle을 관리하는 역할입니다. 전체 시스템을 모두 담당했다기보다 제공 가능 여부 판단에 필요한 backend 영역을 맡았다고 설명하는 것이 안전합니다.

</details>

<details>
<summary>기준정보와 메타데이터는 어떻게 다른가요?</summary>

기준정보는 서비스 단위의 제공 대상 여부, 상태, 적용일 같은 운영 기준이고, 메타데이터는 실제 제공 데이터의 schema, field, datatype, description 같은 구조 정의입니다. 기준정보는 제공 가능 여부를 판단하고, 메타데이터는 무엇을 어떤 형태로 제공하는지 설명합니다.

</details>

<details>
<summary>사용자가 요청한 데이터가 제공 가능한지 어떻게 판단하나요?</summary>

요청 티켓만 보고 판단하지 않고, 해당 서비스가 기준정보상 제공 대상인지, 현재 상태가 제공 가능한 상태인지, 유효한 메타데이터 버전과 S3 object가 연결되어 있는지를 함께 봅니다. 실제 구현 세부 정책은 내부 기준이므로 면접에서는 판단 요소 중심으로 설명합니다.

</details>

<details>
<summary>직접 구현한 범위와 연계만 한 범위는 어디까지인가요?</summary>

직접 담당한 범위는 MetaService의 기준정보, 메타데이터 업로드/다운로드, S3 적재 흐름, 상태 전환 배치, 통계 배치 쪽입니다. 외부 검증 모듈/API나 전체 Data Act 요청 처리 시스템은 연계 흐름을 이해하고 호출한 범위로 말하는 것이 안전합니다.

</details>

<details>
<summary>이 프로젝트에서 가장 위험했던 데이터 정합성 포인트는 어디였나요?</summary>

DB 상태와 S3 object가 서로 다른 저장소에 있어 하나의 트랜잭션으로 묶기 어렵다는 점이 가장 큰 정합성 포인트입니다. S3 업로드 성공 후 DB 저장 실패, DB 완료 상태인데 S3 object 누락 같은 케이스를 로그와 재처리 기준으로 관리해야 합니다.

</details>

<details>
<summary>5년차 개발자로서 단순 구현 외에 어떤 운영 리스크를 고려했나요?</summary>

단순 API 성공 여부보다 실패 범위, 재처리 단위, 배치 중복 실행, 상태 전환 오류, 대용량 파일 처리, 운영 DB와 통계 DB 부하 분리를 같이 봐야 합니다. 면접에서는 기능 설명 뒤에 장애 시 확인 순서와 복구 기준까지 덧붙이면 5년차 관점이 살아납니다.

</details>
#### 주의할 점

- 전체 Data Act 시스템을 모두 직접 구현한 것처럼 말하지 않습니다.
- “MetaService 영역에서 담당했다”는 범위를 명확히 말합니다.

### 1-2. 기준정보와 메타데이터의 차이는 무엇인가요?

#### 관련 개념

- [기준정보](#concept-기준정보)
- [메타데이터](#concept-메타데이터)
- [서비스 식별 정보](#concept-서비스-식별-정보)
- [스키마와 필드 정의](#concept-스키마와-필드-정의)
- [제공 가능 여부 판단](#concept-제공-가능-여부-판단)

#### 답변 핵심

- 기준정보는 서비스 단위의 운영 기준과 제공 상태를 관리하는 정보다.
- 메타데이터는 해당 서비스 데이터가 어떤 구조와 필드로 구성되는지 정의하는 정보다.
- 기준정보는 “이 서비스가 제공 대상인가”에 가깝고, 메타데이터는 “어떤 데이터 구조를 제공하는가”에 가깝다.

#### 답변 예시

기준정보는 서비스 단위로 데이터 제공 가능 여부를 판단하기 위한 운영 기준에 가까웠습니다. 예를 들어 서비스 식별 정보, 제공 상태, 적용일, 현재 유효한 메타데이터 버전 같은 정보가 포함되었습니다.

반면 메타데이터는 실제 제공 대상 데이터의 구조를 설명하는 정보였습니다. 어떤 schema와 fieldname이 있고, datatype은 무엇인지, description은 어떻게 제공되는지, trade secret 여부 같은 필드 정의 정보를 관리했습니다. 그래서 기준정보가 서비스의 제공 가능 여부와 현재 상태를 보는 정보라면, 메타데이터는 실제 제공 데이터의 구조와 의미를 정의하는 정보라고 설명할 수 있습니다.

#### 꼬리 질문

<details>
<summary>기준정보가 잘못되면 어떤 문제가 생기나요?</summary>

기준정보가 잘못되면 제공 대상이 아닌 서비스가 제공 가능하다고 판단되거나, 반대로 제공해야 할 데이터가 누락될 수 있습니다. 즉 데이터 자체보다 제공 판단 기준이 흔들리는 문제라 영향 범위가 큽니다.

</details>

<details>
<summary>메타데이터가 잘못되면 어떤 문제가 생기나요?</summary>

메타데이터가 잘못되면 schema, fieldname, datatype, description이 실제 제공 데이터와 맞지 않아 외부 사용자가 데이터를 잘못 해석할 수 있습니다. 제공 가능 여부는 맞더라도 데이터 의미와 품질이 깨질 수 있습니다.

</details>

<details>
<summary>메타데이터를 버전으로 관리한 이유는 무엇인가요?</summary>

서비스 데이터 구조는 시간이 지나며 바뀔 수 있으므로 특정 시점에 어떤 메타데이터가 유효했는지 남겨야 합니다. 버전 관리가 있어야 과거 요청 재현, live 전환, rollback 또는 deprecated 판단을 더 안전하게 할 수 있습니다.

</details>
#### 주의할 점

- 내부 정책 세부 기준을 외부에 구체적으로 말하지 않습니다.
- “서비스 제공 판단을 위한 기준정보” 정도로 안전하게 설명합니다.

## 2. 메타데이터 업로드, 검증, S3 제공 흐름

이 파트는 운영자가 메타데이터를 파일로 등록하고, 검증 API와 S3 적재 흐름을 거쳐 제공 가능한 데이터로 관리하는 과정입니다. 파일 업로드, 파싱, 인코딩, 외부 검증, S3와 DB 정합성처럼 외부 시스템과 연결되는 지점을 중심으로 설명합니다.

### 2-1. 메타데이터를 Excel/CSV로 업로드하게 한 이유는 무엇인가요?

#### 관련 개념

- [대량 데이터 등록](#concept-대량-데이터-등록)
- [파일 파싱](#concept-파일-파싱)
- [CSV](#concept-csv)
- [Excel](#concept-excel)
- [검증 로직](#concept-검증-로직)
- [운영자 업무 흐름](#concept-운영자-업무-흐름)

#### 답변 핵심

- 메타데이터는 필드 단위 데이터가 많아 화면에서 한 줄씩 등록하기 어렵다.
- 운영자가 파일로 검토하고 수정한 뒤 한 번에 반영하는 업무 흐름이 필요했다.
- 업로드 시 필수 항목, 데이터 형식, 기존 버전과의 관계를 검증했다.

#### 답변 예시

메타데이터는 서비스별로 schema, fieldname, datatype, description 같은 필드 정의가 여러 건 존재했습니다. 이런 데이터를 화면에서 한 줄씩 등록하거나 수정하면 운영 부담이 크기 때문에, Excel 또는 CSV로 내려받아 검토하고 다시 업로드하는 흐름이 필요했습니다.

업로드에서는 단순히 파일을 저장하는 것이 아니라 파일 내용을 파싱해서 서비스 기준정보와 연결하고, 필수 항목 누락 여부, 데이터 형식, 기존 버전과의 관계를 확인했습니다. 메타데이터는 이후 검증이나 제공 가능 여부 판단에 사용되기 때문에 버전 기준으로 정확히 관리하는 것이 중요했습니다.

#### 꼬리 질문

<details>
<summary>파일 업로드 시 어떤 검증을 했나요?</summary>

필수 컬럼 누락, 데이터 타입, 서비스 기준정보와의 연결, 기존 버전과의 관계, 빈 값이나 잘못된 enum 값 같은 기본 검증을 봅니다. 외부 검증 모듈/API가 있는 부분은 직접 로직을 모두 구현했다고 단정하지 않고 연계했다고 표현합니다.

</details>

<details>
<summary>CSV와 Excel 처리에서 주의할 점은 무엇인가요?</summary>

CSV는 인코딩, 구분자, 줄바꿈 처리에 주의해야 하고 Excel은 셀 타입, 날짜/숫자 자동 변환, 대용량 메모리 사용에 주의해야 합니다. 운영자에게 익숙한 형식이어도 서버에서는 파싱 실패와 데이터 왜곡 가능성을 검증해야 합니다.

</details>

<details>
<summary>대용량 파일이면 메모리 문제를 어떻게 고려해야 하나요?</summary>

파일 전체를 한 번에 메모리에 올리면 OOM 위험이 있으므로 streaming 처리, row 단위 검증, 업로드 크기 제한, 임시 파일 사용 여부를 검토합니다. Excel도 라이브러리에 따라 메모리 사용량이 커질 수 있어 처리 방식 선택이 중요합니다.

</details>

<details>
<summary>업로드 중간에 실패하면 어떻게 처리해야 하나요?</summary>

어느 단계에서 실패했는지 구분해야 합니다. 파싱 전 실패, DB 저장 중 실패, S3 업로드 후 DB 실패는 복구 방식이 다르므로 service_id, file key, version, 상태값, batch log를 남겨 실패 건만 재처리할 수 있게 하는 것이 좋습니다.

</details>
#### 주의할 점

- “파일만 저장했다”가 아니라 파싱, 검증, 버전 관리까지 설명합니다.

### 2-2. CSV 인코딩 문제는 왜 발생하나요?

#### 관련 개념

- [문자 인코딩](#concept-문자-인코딩)
- [UTF-8](#concept-utf-8)
- [UTF-8 BOM](#concept-utf-8-bom)
- [Content-Type](#concept-content-type)
- [Excel CSV 저장 방식](#concept-excel-csv-저장-방식)
- [다국어 데이터](#concept-다국어-데이터)

#### 답변 핵심

- CSV 자체에는 인코딩 메타정보가 명확히 포함되지 않는 경우가 많다.
- Excel은 환경에 따라 CSV를 UTF-8 BOM 포함, CP949 등 다르게 저장하거나 해석할 수 있다.
- 서버 업로드와 다운로드에서 인코딩 기준을 명확히 해야 한다.

#### 답변 예시

CSV는 텍스트 파일이지만 파일 내부에 인코딩 정보를 항상 명확하게 갖고 있는 것은 아닙니다. 그래서 같은 CSV라도 Excel에서 저장하거나 열 때 사용하는 기본 인코딩, UTF-8 BOM 포함 여부, 서버의 파일 읽기 방식에 따라 한글이나 다국어 설명이 깨질 수 있습니다.

이 프로젝트에서도 description(en), description(fr)처럼 다국어 설명 필드가 있었기 때문에 인코딩 처리가 중요했습니다. 다운로드 시 Content-Type과 charset을 명확히 하고, 업로드 시 서버에서 처리 가능한 인코딩 기준을 정리했습니다. 또한 운영자가 파일을 수정한 뒤 다시 업로드할 때 같은 문제가 반복되지 않도록 가이드를 함께 정리했습니다.

#### 꼬리 질문

<details>
<summary>UTF-8 BOM은 무엇인가요?</summary>

UTF-8 BOM은 파일 앞에 붙는 인코딩 식별 바이트입니다. Excel에서 CSV를 열 때 한글 깨짐을 줄이는 데 도움이 될 수 있지만, 서버 파서가 BOM을 컬럼명 일부로 오해하지 않도록 제거 또는 처리해야 합니다.

</details>

<details>
<summary>CSV와 Excel 파일은 어떻게 다른가요?</summary>

CSV는 텍스트 기반이라 단순하고 가볍지만 인코딩과 구분자 이슈가 큽니다. Excel은 셀 타입과 시트 구조를 가질 수 있어 운영자에게 편하지만 파싱 라이브러리, 타입 변환, 대용량 처리 비용을 고려해야 합니다.

</details>

<details>
<summary>Content-Type과 charset은 어떤 역할을 하나요?</summary>

Content-Type은 파일이나 응답의 미디어 타입을 알려주고, charset은 텍스트를 어떤 문자셋으로 해석할지 알려줍니다. CSV 다운로드나 업로드에서 charset이 맞지 않으면 한글 깨짐이나 파싱 오류가 생길 수 있습니다.

</details>

<details>
<summary>서버에서 인코딩을 자동 감지하면 안전한가요?</summary>

자동 감지는 편하지만 100% 신뢰하기 어렵습니다. 운영 파일 형식을 UTF-8 등으로 명확히 정하고, 업로드 시 허용 인코딩과 실패 메시지를 분명히 주는 방식이 더 안전합니다.

</details>
#### 주의할 점

- “Excel 문제입니다”로만 말하지 말고, 파일 포맷과 서버 처리 기준의 문제로 설명합니다.

### 2-3. S3 업로드와 DB 저장 사이의 정합성은 어떻게 보나요?

#### 관련 개념

- [S3](#concept-s3)
- [외부 저장소](#concept-외부-저장소)
- [상태 기반 처리](#concept-상태-기반-처리)
- [DB와 외부 시스템 정합성](#concept-db와-외부-시스템-정합성)
- [보상 처리](#concept-보상-처리)

#### 답변 핵심

- 메타데이터 업로드와 S3 적재는 DB 트랜잭션만으로 원자성을 보장하기 어렵다.
- S3 업로드 성공 후 DB 저장이 실패하면 S3 object는 남을 수 있다.
- 실제로 삭제 보상 로직을 검토했지만 최종 운영 흐름에서는 object를 바로 삭제하지 않는 방향이었다.
- DB와 S3는 하나의 DB 트랜잭션으로 묶을 수 없으므로 실패 처리와 재처리가 중요하다.

#### 답변 예시

메타데이터 파일 업로드와 S3 적재는 DB 저장과 다르게 하나의 DB 트랜잭션으로 묶을 수 없었습니다. 그래서 S3 업로드는 성공했지만 이후 DB 저장이나 상태 업데이트가 실패하는 경우처럼, 한쪽만 성공하는 상황을 항상 고려해야 했습니다.

이 경우 S3 object를 삭제하는 보상 로직도 검토했지만, 최종적으로는 바로 삭제하지 않고 S3 object가 남을 수 있는 구조로 운영했습니다. 그래서 저는 S3와 DB가 자동으로 같이 롤백된다고 보지 않고, object key, metadata version, 상태값, 로그를 기준으로 재처리하거나 정합성을 확인하는 방식으로 접근했습니다.

10년차 이상 면접관이라면 여기서 “S3는 성공했는데 DB가 실패하면 어떻게 복구할 것인가” 또는 “반대로 DB는 성공했는데 S3 업로드가 실패하면 어떻게 할 것인가”를 물을 수 있습니다. 이때는 DB와 S3를 하나의 트랜잭션으로 묶을 수 없다는 점을 먼저 인정하고, object key 기준 멱등성, 실패 로그, 재처리 기준, 필요 시 outbox 패턴 같은 대안을 함께 말하면 좋습니다.

#### 꼬리 질문

<details>
<summary>DB 저장은 성공했는데 S3 업로드가 실패하면 어떻게 하나요?</summary>

DB 상태를 완료로 확정하기 전에 S3 업로드 성공 여부를 확인하거나, 실패 상태와 로그를 남겨 재처리 대상으로 잡아야 합니다. 중요한 것은 DB만 성공한 상태를 제공 가능 상태로 오해하지 않도록 상태 전이를 분리하는 것입니다.

</details>

<details>
<summary>S3 업로드는 DB 트랜잭션처럼 롤백할 수 있나요?</summary>

S3는 DB 트랜잭션에 참여하지 않기 때문에 DB rollback처럼 자동 원복할 수 없습니다. 보상 트랜잭션, 상태 기반 재처리, object key 멱등성 같은 방식으로 정합성을 맞춰야 합니다.

</details>

<details>
<summary>S3 업로드 성공 후 DB 저장이 실패하면 object를 삭제하나요?</summary>

이 프로젝트에서는 삭제 로직이 있었지만 실제로는 S3 object를 삭제하지 않고 남기는 방향이었다고 정리되어 있습니다. 따라서 면접에서는 삭제했다고 단정하지 말고, 남은 object를 로그와 key 기준으로 재처리하거나 정리 정책을 고민해야 한다고 답하는 것이 안전합니다.

</details>

<details>
<summary>deprecated 상태에서는 어떤 처리가 있었나요?</summary>

deprecated 또는 종료 상태는 더 이상 제공 대상이 아닌 버전이나 서비스를 구분하기 위한 상태로 볼 수 있습니다. 실제 세부 정책은 단정하지 말고, 제공 가능 여부 판단과 S3/DB 상태 연결에서 제외 또는 별도 관리되는 흐름이라고 설명합니다.

</details>

<details>
<summary>S3 업로드 재처리를 멱등하게 만들려면 어떤 키가 필요하나요?</summary>

service_id, metadata version, 적용일, 파일 유형처럼 같은 입력을 유일하게 식별할 수 있는 object key가 필요합니다. 같은 작업을 다시 실행해도 같은 key에 대해 동일 결과가 나오게 설계해야 중복 업로드와 재처리가 쉬워집니다.

</details>

<details>
<summary>outbox 패턴을 적용하면 어떤 장단점이 있나요?</summary>

Outbox 패턴은 DB 변경과 외부 전송 요청을 같은 DB 트랜잭션에 기록해 유실을 줄이는 장점이 있습니다. 대신 outbox table, relay worker, 중복 발행 처리, 모니터링이 필요해 구조가 복잡해집니다.

</details>
#### 주의할 점

- S3 업로드까지 DB 트랜잭션처럼 롤백된다고 말하지 않습니다.
- 정합성은 상태값, 로그, 재처리, 보상 처리로 맞춘다고 설명합니다.

### 2-4. 서버리스로 분리되어 있던 S3 적재 흐름을 MetaService 내부로 이관한 이유는 무엇인가요?

#### 관련 개념

- [서버리스](#concept-서버리스)
- [Spring Boot](#concept-spring-boot)
- [장애 추적](#concept-장애-추적)
- [책임 경계](#concept-책임-경계)
- [관측성](#concept-관측성)
- [운영 복잡도](#concept-운영-복잡도)

#### 답변 핵심

- 기존 구조는 업로드 이후 일부 처리가 별도 서버리스 흐름으로 나뉘어 있었다.
- 흐름이 분산되어 오류 발생 구간을 확인하기 어려웠다.
- 파일 업로드, 파싱, 저장, S3 적재를 MetaService 내부에서 처리해 흐름을 한곳에서 관리했다.
- 서버리스가 나쁜 구조라는 뜻은 아니고, 이 업무에서는 처리 흐름과 장애 추적을 단순화하는 목적이었다.

#### 답변 예시

기존에는 메타데이터 파일 업로드 이후 일부 처리가 서버리스 구조로 분리되어 있었습니다. 서버리스 자체가 나쁘다는 의미는 아니지만, 이 업무에서는 업로드, 파싱, 저장, S3 적재까지 이어지는 흐름이 나뉘어 있어 문제가 생겼을 때 어느 구간에서 실패했는지 확인하기 어려운 부분이 있었습니다.

그래서 해당 흐름을 Spring Boot 기반 MetaService 내부 처리로 이관했습니다. 이렇게 하면 업로드 요청 이후의 처리 흐름을 한 서비스 안에서 추적할 수 있고, 로그와 상태값을 기준으로 장애 확인 지점을 줄일 수 있었습니다.

#### 꼬리 질문

<details>
<summary>서버리스 구조의 장점은 무엇인가요?</summary>

서버리스는 특정 작업을 독립적으로 실행하고 필요할 때만 확장하기 좋습니다. S3 이벤트 기반 처리처럼 비동기 작업에 잘 맞지만, 흐름이 분산되면 로그 추적과 장애 원인 파악이 어려워질 수 있습니다.

</details>

<details>
<summary>내부 서비스로 이관하면 단점은 무엇인가요?</summary>

MetaService 내부로 들어오면 흐름과 로그를 한곳에서 보기 쉬워지지만, 서비스 책임과 부하가 늘어납니다. 파일 업로드나 S3 적재가 무거워지면 API 응답 지연, 배치 지연, 장애 영향 범위를 같이 고려해야 합니다.

</details>

<details>
<summary>장애 추적은 어떤 로그나 상태값으로 하나요?</summary>

service_id, metadata version, ticket 또는 batch execution id, S3 object key, 외부 API 요청 id, 상태값, 실패 단계와 exception message가 필요합니다. 이 값들이 있어야 업로드, 검증, DB 저장, S3 적재 중 어디서 실패했는지 빠르게 나눌 수 있습니다.

</details>

<details>
<summary>다시 설계한다면 어떤 기준으로 분리할지 정하겠나요?</summary>

처리 시간이 길고 재시도가 필요한 작업인지, 장애 격리가 필요한지, 운영자가 즉시 결과를 봐야 하는지, 로그 추적이 얼마나 중요한지를 기준으로 봅니다. 무조건 서버리스나 내부 서비스가 답이 아니라 운영 복잡도와 장애 영향 범위를 비교해야 합니다.

</details>
#### 주의할 점

- “서버리스는 안 좋다”처럼 말하지 않습니다.
- 이 프로젝트의 운영성과 추적성 관점에서 이관했다고 설명합니다.

### 2-5. 대용량 파일 업로드 시 메모리 이슈는 어떻게 고려해야 하나요?

#### 관련 개념

- [Multipart Upload](#concept-multipart-upload)
- [Streaming](#concept-streaming)
- [Buffer](#concept-buffer)
- [File Size Limit](#concept-file-size-limit)
- [Timeout](#concept-timeout)
- [S3 Multipart Upload](#concept-s3-multipart-upload)

#### 답변 핵심

- 파일 전체를 메모리에 올리면 OOM 위험이 있다.
- 업로드 크기 제한, 임시 파일 저장, streaming 처리, timeout, 재시도 기준을 고려해야 한다.
- 압축 파일 보안은 일반론으로만 설명하고, 실제 담당 구현처럼 말하지 않는다.

#### 답변 예시

대용량 파일 업로드에서는 파일 전체를 한 번에 메모리에 올리는 구조가 위험하다고 생각합니다. 파일 크기가 커지면 OOM이 날 수 있고, 요청 처리 시간이 길어지면서 timeout이나 커넥션 점유 문제도 생길 수 있습니다.

그래서 실제 설계에서는 업로드 가능한 파일 크기 제한, 임시 파일 저장 위치, streaming 처리 여부, S3 multipart upload 사용 가능성, 실패 시 재처리 기준을 함께 봐야 합니다. 압축 파일 처리나 검증 모듈을 직접 구현하는 범위라면 압축 해제 후 실제 크기가 커지는 문제, 파일 개수 제한, zip slip 같은 경로 조작, 확장자와 MIME 검증도 확인해야 합니다. 제 담당 범위에서는 압축 파일 보안 검증을 직접 구현했다기보다 외부 검증 모듈/API를 연계한 흐름이었고, 보안 검증 항목은 일반적인 설계 고려사항으로 설명하겠습니다.

#### 꼬리 질문

<details>
<summary>MultipartFile을 그대로 사용하면 어떤 문제가 있나요?</summary>

MultipartFile을 전체 byte로 읽으면 대용량 파일에서 메모리 사용량이 커지고 OOM 위험이 생깁니다. 가능하면 stream 기반 처리, 크기 제한, 임시 저장소, row 단위 검증을 고려해야 합니다.

</details>

<details>
<summary>압축 파일 검증 시 어떤 보안 이슈가 있나요?</summary>

zip slip, 압축 해제 후 크기 폭증, 너무 많은 파일 개수, 확장자와 MIME 불일치 같은 문제가 있습니다. 직접 구현 범위가 아니었다면 일반 보안 고려사항으로만 설명하는 것이 안전합니다.

</details>

<details>
<summary>S3 multipart upload는 언제 쓰나요?</summary>

큰 파일을 여러 part로 나눠 업로드해야 할 때 사용합니다. 네트워크 실패 시 전체를 다시 올리지 않고 실패 part만 재시도할 수 있어 대용량 업로드 안정성에 유리합니다.

</details>

<details>
<summary>zip slip은 무엇이고 어떻게 막나요?</summary>

zip slip은 압축 파일 내부 경로에 ../ 같은 값을 넣어 의도한 디렉터리 밖에 파일을 쓰게 만드는 공격입니다. 압축 해제 전 canonical path를 검증하고 허용된 디렉터리 밖 경로는 차단해야 합니다.

</details>

<details>
<summary>압축 해제 후 파일 크기 폭증은 어떻게 제한하나요?</summary>

압축 파일 크기뿐 아니라 해제 후 총 크기, 파일 개수, 개별 파일 크기, 압축률 상한을 제한해야 합니다. 제한 없이 풀면 디스크나 메모리를 고갈시키는 공격으로 이어질 수 있습니다.

</details>
#### 주의할 점

- 실제 프로젝트에서 구현하지 않은 방식은 “했다”가 아니라 “고려해야 한다”로 말합니다.
- 압축 파일 보안 검증을 직접 담당했다고 말하지 않습니다.

### 2-6. 외부 검증 API가 실패하면 어떻게 처리해야 하나요?

#### 관련 개념

- [외부 API 연계](#concept-외부-api-연계)
- [Timeout](#concept-timeout)
- [Retry](#concept-retry)
- [Idempotency](#concept-idempotency)
- [상태 관리](#concept-상태-관리)
- [장애 격리](#concept-장애-격리)

#### 답변 핵심

- 외부 API 실패는 네트워크 실패, timeout, 검증 실패 응답으로 나눠서 봐야 한다.
- 무조건 재시도하면 중복 요청 문제가 생길 수 있어 idempotency가 중요하다.
- 이 프로젝트의 외부 검증은 parquet 파일 업로드 과정의 검증 모듈/API 연계이며, 상태 전환 배치나 일 통계 배치와 섞어 말하지 않는다.

#### 답변 예시

외부 검증 API 실패는 단순히 실패 하나로 보지 않고 네트워크 오류, timeout, 검증 결과상 실패를 구분해서 봐야 한다고 생각합니다. 네트워크 오류나 일시적 timeout은 제한된 횟수의 재시도를 고려할 수 있지만, 요청 자체가 잘못된 경우라면 재시도보다 상태를 실패로 남기고 원인을 확인하는 것이 맞습니다.

또 외부 API가 중복 호출될 수 있기 때문에 요청 ID나 메타데이터 버전 기준으로 멱등성을 고려해야 합니다. 이상적으로는 검증 요청 상태, 실패 사유, 재처리 가능 여부를 저장해 운영자가 추적할 수 있게 하는 것이 좋지만, 제가 확인한 실제 흐름에서는 CloudWatch와 batch 로그를 보고 실패 내용을 확인한 뒤 다시 실행하는 방식에 가까웠습니다.

다만 이 항목은 상태 전환 배치나 일 통계 배치와 분리해서 말해야 합니다. 외부 검증은 parquet 파일 업로드 과정에서 다른 검증 모듈/API를 호출하는 흐름이고, 배치 재처리는 상태 전환 배치와 일 단위 통계 배치의 운영 방식입니다. 제가 확인한 실제 운영 흐름은 CloudWatch와 batch 로그를 보고 실패 내용을 확인한 뒤 다시 실행하는 방식이었고, retry, timeout, circuit breaker 적용 여부는 설정과 로그를 기준으로 확인하겠습니다.

#### 꼬리 질문

<details>
<summary>Retry와 Circuit Breaker는 어떻게 다른가요?</summary>

Retry는 일시적인 실패를 다시 시도하는 방식이고, Circuit Breaker는 실패가 반복될 때 호출 자체를 잠시 차단해 장애 전파를 줄이는 방식입니다. Retry는 회복 가능성이 있을 때, Circuit Breaker는 외부 시스템이 불안정할 때 효과적입니다.

</details>

<details>
<summary>멱등성이 왜 중요한가요?</summary>

외부 API나 배치는 timeout 후 실제 성공 여부를 바로 알기 어려운 경우가 많습니다. 같은 요청을 다시 보내도 결과가 중복 생성되지 않아야 안전하게 재시도할 수 있기 때문에 멱등 key와 상태 확인이 중요합니다.

</details>

<details>
<summary>외부 API timeout은 몇 초로 잡아야 하나요?</summary>

정답 초가 정해져 있지는 않고 SLA, 평균 응답 시간, 사용자 대기 가능 시간, 재시도 정책을 보고 정해야 합니다. 모르면 특정 숫자를 단정하기보다 측정 지표와 장애 전파 방지 기준으로 정하겠다고 답합니다.

</details>
#### 주의할 점

- 실제 구현하지 않은 circuit breaker를 구현했다고 말하지 않습니다.
- 외부 검증 실패 처리와 상태 전환/통계 배치 재처리를 한 문단에서 섞지 않습니다.

### 2-7. S3와 DB 중 어느 쪽을 Source of Truth로 봐야 하나요?

#### 관련 개념

- [Source of Truth](#concept-source-of-truth)
- [Object Key](#concept-object-key)
- [Metadata Version](#concept-metadata-version)
- [Orphan Object](#concept-orphan-object)
- [보상 처리](#concept-보상-처리)
- [멱등성](#concept-멱등성)

#### 답변 핵심

- 메타데이터 상태와 제공 가능 여부 판단은 DB 상태값을 기준으로 보는 것이 자연스럽다.
- S3는 실제 파일 객체 저장소 역할이다.
- DB와 S3 정합성이 어긋나면 object key, metadata version, 상태값, 업로드 이력을 기준으로 복구해야 한다.

#### 답변 예시

이 구조에서는 제공 가능 여부나 현재 유효한 메타데이터 버전 판단은 DB의 상태값을 source of truth로 보는 것이 자연스럽다고 생각합니다. S3는 실제 파일 객체가 저장되는 외부 저장소 역할이고, 어떤 파일을 제공 가능한 것으로 볼지는 DB의 metadata version과 상태값이 결정해야 합니다.

다만 S3 업로드 성공 후 DB 상태 업데이트가 실패하면 S3에는 파일이 있지만 DB에서는 제공 가능 상태가 아닌 orphan object가 생길 수 있습니다. 실제 흐름에서는 S3 object를 바로 삭제하지 않고 남기는 방향이었으므로, object key와 metadata version을 기준으로 업로드 완료 여부를 추적하고 재처리나 별도 정리 기준을 고려해야 한다고 설명하겠습니다.

#### 꼬리 질문

<details>
<summary>S3 업로드 성공 후 DB 업데이트 실패 시 어떻게 복구하나요?</summary>

batch log나 application log에서 service_id와 object key를 찾아 DB 상태를 재처리하거나, 같은 key로 멱등하게 다시 업로드 후 DB 저장을 재시도합니다. 이 프로젝트에서는 object를 삭제하지 않고 남기는 흐름이었다는 점을 같이 말합니다.

</details>

<details>
<summary>DB는 완료 상태인데 S3 object가 없으면 어떻게 감지하나요?</summary>

DB의 object key 기준으로 S3 head object 확인을 하거나, 배치 검증 작업으로 완료 상태와 실제 object 존재 여부를 대조할 수 있습니다. 운영에서는 누락 감지 로그와 알림이 있어야 복구가 빠릅니다.

</details>

<details>
<summary>S3 object를 삭제하지 않고 남기면 어떤 운영 리스크가 있나요?</summary>

미사용 object가 누적되어 비용이 늘고, DB 상태와 맞지 않는 파일이 남아 혼란을 만들 수 있습니다. 대신 재처리 근거로 쓸 수 있으므로 lifecycle 정책, 정리 배치, 상태 추적 기준이 필요합니다.

</details>
#### 주의할 점

- DB와 S3가 자동으로 정합성을 보장한다고 말하지 않습니다.

### 2-8. 이 구조에서 장애가 나면 어디부터 확인하겠나요?

#### 관련 개념

- [Correlation ID](#concept-correlation-id)
- [Request ID](#concept-request-id)
- [로그 추적](#concept-로그-추적)
- [Batch Metadata](#concept-batch-metadata)
- [S3 Object](#concept-s3-object)
- [외부 API Request ID](#concept-외부-api-request-id)

#### 답변 핵심

- 먼저 장애 구간을 나눈다.
- 업로드, 파싱, validation, S3, 외부 검증 API, 상태 전환 배치, 통계 배치 중 어디인지 좁힌다.
- 요청 ID, service id, metadata version, 검증 파일 ID, S3 object key, batch execution id로 로그와 DB를 연결해 본다.

#### 답변 예시

먼저 장애가 어느 흐름에서 발생했는지 나눠서 볼 것 같습니다. 메타데이터 업로드 문제인지, validation 문제인지, S3 업로드 문제인지, 외부 검증 API 문제인지, 상태 전환 배치나 통계 배치 문제인지 구분하겠습니다.

그다음 요청 ID, service id, metadata version, 검증 파일 ID, S3 object key, batch execution id 같은 추적 키로 애플리케이션 로그와 DB 상태를 연결해서 보겠습니다. 외부 검증 API라면 외부 요청 ID와 응답 코드, timeout 여부를 확인하고, S3라면 object 존재 여부와 업로드 완료 상태를 확인하겠습니다.

배치 장애라면 batch metadata table, 실패 step, 실패 service id, 실패 사유, 마지막 처리 상태를 확인해 재처리 범위를 정하겠습니다.

#### 꼬리 질문

<details>
<summary>로그에 어떤 키를 반드시 남기겠나요?</summary>

service_id, metadata version, batch execution id, S3 object key, 요청 id, 상태값, 실패 단계, exception class/message를 남기겠습니다. 이 키들이 있어야 실패 건만 추적하고 재처리할 수 있습니다.

</details>

<details>
<summary>장애 구간을 어떻게 빠르게 분리하나요?</summary>

입력 파일 파싱, 외부 검증 API, DB 저장, S3 업로드, 상태 전환 배치, 통계 적재처럼 단계별로 나누고 각 단계의 로그와 상태값을 확인합니다. 마지막 성공 단계와 최초 실패 단계를 찾는 방식으로 좁힙니다.

</details>

<details>
<summary>실패한 서비스만 재처리하려면 어떤 데이터가 필요하나요?</summary>

실패한 service_id, 대상 version, 처리 기준일, 실패 단계, 이전 상태, 재실행 가능 여부, S3 object key가 필요합니다. 전체 재실행이 아니라 부분 재처리를 하려면 성공/실패 경계가 기록되어 있어야 합니다.

</details>
#### 주의할 점

- “로그를 봅니다”로 끝내지 않습니다.
- 어떤 로그 키와 어떤 상태값을 볼지 구체적으로 말합니다.

## 3. 배치, 통계, DB 분리, 운영 안정성

이 파트는 상태 전환 배치, service_id 단위 트랜잭션 분리, 일일 통계 배치, 운영 DB와 통계 DB 분리처럼 운영 안정성과 장애 영향 범위를 줄이기 위한 개선을 설명하는 영역입니다. 뒤쪽의 CS 질문은 이 업무를 더 깊게 설명하기 위한 보강 개념으로 연결해서 답변합니다.

### 3-1. 메타데이터 상태 전환 배치는 왜 필요했나요?

#### 관련 개념

- [Spring Batch](#concept-spring-batch)
- [Tasklet](#concept-tasklet)
- [상태 전환](#concept-상태-전환)
- [적용일](#concept-적용일)
- [메타데이터 버전](#concept-메타데이터-버전)
- [수명주기 관리](#concept-수명주기-관리)

#### 답변 핵심

- 사용자가 데이터를 요청했을 때 현재 유효한 메타데이터 버전을 판단해야 했다.
- 서비스별 메타데이터 버전은 적용일과 상태에 따라 live, deprecated 등으로 전환되어야 했다.
- 사람이 수동으로 바꾸면 누락이나 시점 오류가 생길 수 있어 배치로 자동화했다.

#### 답변 예시

데이터 제공 판단에는 현재 어떤 메타데이터 버전이 유효한지가 중요했습니다. 신규 버전이 등록되어도 바로 제공 가능한 것은 아니고, 적용일과 현재 상태를 기준으로 live 전환 여부를 판단해야 했습니다.

그래서 정해진 시간에 실행되는 배치를 통해 서비스별 메타데이터 버전의 적용일과 상태를 확인하고, 조건에 맞는 버전을 다음 상태로 변경했습니다. 이 로직은 Spring Batch Tasklet 방식으로 구현했습니다. 처리 과정에서는 신규 버전이 활성화되면 기존 활성 버전을 바로 종료하지 않고 일정 기간 유예 상태로 전환해 외부 연계 시스템이 버전 변경에 대응할 시간을 둘 수 있도록 했습니다.

#### 꼬리 질문

<details>
<summary>Tasklet과 Chunk 방식의 차이는 무엇인가요?</summary>

Tasklet은 하나의 작업 단위를 직접 구현하는 방식이고, Chunk는 read-process-write를 일정 크기 단위로 반복하며 commit하는 방식입니다. 단순 상태 전환은 Tasklet도 가능하지만 대량 데이터 처리와 재시작성은 Chunk가 유리할 수 있습니다.

</details>

<details>
<summary>상태 전환이 잘못되면 어떤 문제가 생기나요?</summary>

제공되면 안 되는 데이터가 활성화되거나, 제공해야 할 서비스가 계속 대기 상태로 남을 수 있습니다. 상태값은 제공 가능 여부 판단과 연결되므로 단순 컬럼 변경이 아니라 업무 규칙으로 봐야 합니다.

</details>

<details>
<summary>적용일 기준 처리는 시간대 문제를 어떻게 고려해야 하나요?</summary>

기준 시간대가 UTC인지 KST인지 명확히 정해야 하고, 자정 경계에서 누락이나 중복이 없도록 start inclusive, end exclusive 같은 규칙을 둬야 합니다. 이 문서에서는 UTC 기준 자정부터 다음날 자정까지로 정리되어 있습니다.

</details>

<details>
<summary>배치가 중간에 실패하면 어떻게 복구하나요?</summary>

실패한 service_id와 단계가 로그에 남아 있어야 하고, 성공한 건은 유지하고 실패한 건만 재실행할 수 있어야 합니다. 전체 롤백보다 부분 성공을 허용했다면 재처리 기준과 멱등성이 더 중요해집니다.

</details>
#### 주의할 점

- 상태값 이름과 전환 조건은 실제 코드 기준으로 확인하고 말합니다.

### 3-2. 상태 전환 배치에서 트랜잭션을 서비스 단위로 분리한 이유는 무엇인가요?

#### 관련 개념

- [Transaction](#concept-transaction)
- [Rollback](#concept-rollback)
- [Spring Batch](#concept-spring-batch)
- [장애 영향 범위](#concept-장애-영향-범위)
- [부분 실패 처리](#concept-부분-실패-처리)

#### 답변 핵심

- 기존에는 여러 서비스 상태 전환이 하나의 트랜잭션 안에서 처리되었다.
- 한 서비스에서 오류가 나면 전체 배치가 롤백될 수 있었다.
- 서비스 단위로 트랜잭션을 분리해 특정 서비스 실패가 다른 서비스에 전파되지 않도록 했다.
- 단점은 전체 원자성이 줄고, 실패 서비스 재처리 기준을 별도로 관리해야 한다는 점이다.

#### 답변 예시

기존 구조에서는 여러 서비스의 상태 전환이 하나의 트랜잭션 안에서 처리되고 있었습니다. 이 경우 일부 서비스의 데이터나 상태값에 문제가 생기면, 정상적으로 처리 가능한 다른 서비스까지 함께 롤백될 수 있었습니다.

그래서 처리 단위를 서비스 기준으로 나누고, 각 서비스별로 트랜잭션을 분리했습니다. 이렇게 하면 특정 서비스에서 오류가 발생해도 해당 서비스만 롤백되고 다른 서비스의 처리 결과는 유지됩니다. 다만 이 방식은 전체 배치를 하나의 원자적 작업으로 보는 구조는 아니기 때문에, 실패한 서비스 목록과 재처리 기준을 별도로 관리하는 것이 중요합니다.

여기서 중요한 것은 트랜잭션을 무조건 작게 나누는 것이 아니라, 업무적으로 독립 처리 가능한 단위가 무엇인지 판단하는 것입니다. 서비스 간 상태 전환이 서로 의존한다면 하나의 트랜잭션으로 묶는 것이 맞을 수 있지만, 이 경우에는 서비스 단위로 독립 처리할 수 있었기 때문에 실패 영향 범위를 줄이는 쪽이 더 적절했습니다.

#### 꼬리 질문

<details>
<summary>트랜잭션을 잘게 나누면 단점은 무엇인가요?</summary>

전체 원자성이 깨져 일부만 성공한 상태가 생길 수 있습니다. 그래서 어떤 단위까지 부분 성공을 허용할지 업무 기준이 필요하고, 실패 목록과 재처리 방법을 반드시 남겨야 합니다.

</details>

<details>
<summary>실패한 서비스만 재처리하려면 어떻게 설계하나요?</summary>

service_id 단위로 처리 결과를 기록하고, 성공/실패 상태와 실패 원인을 남겨 재실행 대상을 선별해야 합니다. 재실행 시 같은 service_id와 기준일에 대해 결과가 중복되지 않도록 멱등하게 설계합니다.

</details>

<details>
<summary>전체 롤백이 더 적절한 경우는 언제인가요?</summary>

모든 데이터가 함께 성공해야 의미가 있거나, 일부 성공 상태가 업무적으로 허용되지 않는 경우에는 전체 롤백이 맞습니다. 예를 들어 여러 레코드가 하나의 불변 조건을 공유하면 부분 성공이 오히려 정합성을 해칠 수 있습니다.

</details>

<details>
<summary>배치 처리 결과는 어디에 기록해야 하나요?</summary>

Spring Batch 메타 테이블, 별도 batch log table, application log, monitoring metric에 남길 수 있습니다. 중요한 것은 job execution id, service_id, 기준일, 처리 건수, 성공/실패 상태, 실패 원인이 조회 가능해야 한다는 점입니다.

</details>
#### 주의할 점

- “무조건 트랜잭션을 작게 나누는 것이 좋다”고 말하지 않습니다.
- 업무상 부분 성공이 허용되는지에 따라 판단한다고 설명합니다.

### 3-3. 일일 통계 배치는 왜 만들었나요?

#### 관련 개념

- [Batch](#concept-batch)
- [Business Metric](#concept-business-metric)
- [일 단위 집계](#concept-일-단위-집계)
- [운영 데이터](#concept-운영-데이터)
- [통계 데이터](#concept-통계-데이터)

#### 답변 핵심

- 전일 기준 메타데이터 변경 건수와 스키마 업데이트 건수를 확인할 필요가 있었다.
- 실시간 요청마다 계산하기보다 하루 한 번 집계해 통계 저장소에 적재하는 방식이 요구사항에 맞았다.
- `MetaserviceStatisticsJob`이 UTC 기준 매일 00시에 실행되며 서비스 수, 데이터셋 버전업 수, 스키마 수를 집계했다.

#### 답변 예시

운영 화면에서는 현재 서비스 기준정보와 메타데이터 상태를 관리해야 했고, 별도로 전일 기준으로 어떤 메타데이터가 변경되었는지, 어떤 스키마 정보가 업데이트되었는지 집계해서 확인할 필요가 있었습니다.

그래서 UTC 기준 매일 00시에 실행되는 `MetaserviceStatisticsJob`을 개발했습니다. 이 배치는 운영 DB의 메타데이터와 스키마 정보를 조회한 뒤 서비스 단위와 스키마 단위로 변경 건수를 집계하고, 결과를 통계 저장소에 적재하는 흐름이었습니다. 통계 항목은 `service_count`, `dataset_version_up_count`, `schema_count`였습니다.

#### 꼬리 질문

<details>
<summary>왜 실시간 조회가 아니라 배치로 처리했나요?</summary>

통계는 매 요청마다 계산하면 운영 DB 부하가 커지고 응답 시간이 불안정해질 수 있습니다. 일 단위 기준이 명확하다면 배치로 미리 집계해 통계 조회와 운영 트랜잭션의 부하를 분리하는 것이 유리합니다.

</details>

<details>
<summary>매일 00시에 실행할 때 주의할 점은 무엇인가요?</summary>

시간대, 기준일 범위, 지연 데이터, 중복 실행, 이전 실행 실패 여부를 확인해야 합니다. 특히 UTC 기준이라면 로컬 시간과 혼동하지 않도록 로그와 파라미터도 UTC 기준으로 맞추는 것이 좋습니다.

</details>

<details>
<summary>배치 실패 시 다음 날 통계는 어떻게 되나요?</summary>

실패한 날의 집계가 누락되거나 다음 날 집계와 섞이면 통계 신뢰도가 떨어집니다. 기준일 파라미터로 실패한 날짜만 재처리할 수 있게 하고, 성공 여부를 로그나 상태 테이블로 확인해야 합니다.

</details>

<details>
<summary>집계 기준 날짜는 어떻게 잡아야 하나요?</summary>

업무 기준 시간대를 먼저 정하고, start inclusive와 end exclusive 범위로 잡는 것이 안전합니다. 여기서는 UTC 기준 자정부터 다음날 자정까지로 답하면 됩니다.

</details>
#### 주의할 점

- “배치가 항상 성능상 유리하다”고 말하지 않습니다.
- 일 단위 집계 요구사항에 맞는 방식이었다고 설명합니다.

### 3-4. 운영 DB와 통계 DB를 분리한 이유는 무엇인가요?

#### 관련 개념

- [운영 DB](#concept-운영-db)
- [통계 DB](#concept-통계-db)
- [OLTP와 OLAP](#concept-oltp와-olap)
- [커넥션 풀](#concept-커넥션-풀)
- [I/O 부하](#concept-i-o-부하)
- [읽기/쓰기 역할 분리](#concept-읽기-쓰기-역할-분리)
- [CQRS](#concept-cqrs)

#### 답변 핵심

- 운영 데이터는 서비스 처리와 현재 상태 관리에 사용된다.
- 통계 데이터는 집계 결과 저장과 조회 목적에 가깝다.
- 같은 저장소에서 섞이면 통계 적재나 조회가 운영 DB 자원에 영향을 줄 수 있다.
- 운영 DB는 원천 데이터 조회, 통계 DB는 집계 결과 저장과 조회에 집중하도록 역할을 분리했다.

#### 답변 예시

운영 DB와 통계 DB를 분리한 이유는 데이터의 목적과 역할이 달랐기 때문입니다. 운영 DB는 서비스 기준정보와 메타데이터의 현재 상태를 관리하는 데 사용되고, 통계 DB는 전일 변경 건수 같은 집계 결과 저장과 조회에 사용됩니다.

제가 확인한 구조에서는 운영 DB인 `dataact.metaservice`와 통계 DB인 `dataact.statistic`이 물리적으로 분리되어 있었습니다. 이 구조에서는 통계 배치가 오래 실행되거나 통계 조회가 많아질 때 운영 DB의 커넥션, read I/O, write I/O, 트랜잭션 유지 시간에 영향을 줄 가능성을 줄일 수 있습니다. 그래서 운영 DB에서는 원천 데이터를 조회하고, 집계 결과 저장과 통계 조회는 통계 DB에서 처리하도록 역할을 나눠 설명하겠습니다.

다만 “DB를 분리했으니 무조건 성능이 좋아졌다”라고 단정하기보다는, 운영 데이터와 통계 데이터의 저장 책임을 분리하고 통계 적재/조회가 운영 DB에 직접 누적되는 구조를 줄였다고 설명하겠습니다. 실제 성능 효과는 처리 건수, 쿼리 실행 계획, 커넥션 사용량, I/O 지표를 봐야 판단할 수 있습니다.

#### 꼬리 질문

<details>
<summary>DB를 분리하면 무조건 성능이 좋아지나요?</summary>

무조건은 아닙니다. 병목이 쿼리 실행 계획, 인덱스 부재, 애플리케이션 로직이면 DB 분리만으로 해결되지 않습니다. 다만 운영 DB와 통계 DB의 자원 경합을 줄이는 데는 도움이 될 수 있습니다.

</details>

<details>
<summary>같은 MySQL 인스턴스 안의 schema 분리와 물리 DB 분리는 어떻게 다른가요?</summary>

schema 분리는 논리적으로 객체를 나누지만 CPU, 메모리, I/O 같은 인스턴스 자원은 공유합니다. 물리 DB 분리는 자원을 더 독립적으로 분리할 수 있지만 운영과 모니터링 복잡도가 늘어납니다.

</details>

<details>
<summary>통계 DB 장애가 나면 운영 서비스에는 어떤 영향이 있나요?</summary>

분리가 잘 되어 있으면 핵심 운영 API는 계속 동작할 수 있지만 통계 조회나 통계 적재는 실패할 수 있습니다. 단, 같은 애플리케이션 커넥션 풀이나 트랜잭션 흐름을 공유한다면 장애 전파 가능성도 확인해야 합니다.

</details>

<details>
<summary>CQRS와 단순 DB 역할 분리는 어떻게 다른가요?</summary>

CQRS는 command와 query의 모델과 책임을 의도적으로 분리하는 아키텍처 패턴입니다. 제가 이력서에 CQRS 관점을 언급했다면, 이 프로젝트에서 운영 DB는 현재 상태와 원천 데이터를 관리하고 통계 DB는 집계 결과 조회에 사용되도록 역할을 나눴다는 점을 설명하려는 의도입니다. 다만 별도의 command model/query model, 이벤트 기반 동기화, projection pipeline까지 갖춘 완전한 CQRS 구조로 단정하지는 않겠습니다. 면접에서는 “읽기/쓰기 관심사를 분리하는 관점은 이해하고 있고, 제 업무에서는 운영 DB와 통계 DB의 역할 분리로 적용 범위를 설명할 수 있다”고 답하겠습니다.

</details>

#### 주의할 점

- 확인된 사실 기준으로 `dataact.metaservice`와 `dataact.statistic`은 물리적으로 다른 DB였다고 말합니다.
- 성능 수치가 없으므로 “역할 분리와 운영 영향 가능성 축소”라고 설명합니다.

### 3-5. insert-select 구조를 왜 select와 insert로 분리했나요?

#### 관련 개념

- [`INSERT INTO ... SELECT`](#concept-insert-into-select)
- [운영 DB 조회](#concept-운영-db-조회)
- [통계 DB 적재](#concept-통계-db-적재)
- [Transaction Manager](#concept-transaction-manager)
- [Batch Insert](#concept-batch-insert)

#### 답변 핵심

- insert-select는 읽기와 쓰기가 하나의 SQL 또는 같은 DB 컨텍스트에 결합될 수 있다.
- 운영 DB 조회와 통계 DB 적재를 분리하려면 read query와 write query를 분리하는 편이 명확했다.
- 운영 DB에서는 원천 데이터를 조회하고, 통계 DB에는 집계 결과를 batch insert했다.
- 운영 DB 조회 로직과 통계 DB 적재 로직의 책임을 구분하기 쉬워졌다.

#### 답변 예시

기존 통계 배치는 읽기와 쓰기가 결합된 구조였습니다. `insert-select` 형태는 같은 DB 안에서 처리할 때는 단순하고 빠를 수 있지만, 운영 DB에서 원천 데이터를 읽고 통계 DB에 결과를 저장해야 하는 구조에서는 읽기와 쓰기 역할을 분리하기 어렵습니다.

그래서 read query와 write query를 분리했습니다. `RStatistics.xml`에서는 MetaService 영역의 원천 데이터를 조회해 통계 데이터를 만들고, `WStatistics.xml`에서는 Statistics 영역의 통계 테이블에 `foreach` batch insert 형태로 적재했습니다. 이렇게 하면서 운영 DB는 조회 역할, 통계 DB는 저장 역할로 나누고 배치 처리 흐름에서 연결 대상을 더 명확하게 구분할 수 있었습니다.

다만 select와 insert를 분리하면 DB 내부에서 한 번에 처리하던 데이터를 애플리케이션이 중간에 들고 있어야 하므로 메모리 사용이 늘 수 있고, DB와 애플리케이션 사이의 네트워크 왕복도 증가할 수 있습니다. 따라서 데이터량, batch size, 중간 결과 보관 방식, 실패 시 재처리 기준을 같이 고려해야 합니다.

#### 꼬리 질문

<details>
<summary>insert-select의 장점은 무엇인가요?</summary>

같은 DB 안에서 데이터를 바로 옮기거나 집계할 때 애플리케이션 왕복이 적고 구현이 단순합니다. 대량 처리에서 DB 내부 최적화를 활용할 수 있는 것도 장점입니다.

</details>

<details>
<summary>select와 insert를 분리하면 단점은 무엇인가요?</summary>

중간 결과가 애플리케이션 메모리를 사용하고, 네트워크 왕복과 batch insert 조정 비용이 생깁니다. 또한 select 시점과 insert 시점 사이 데이터 변경 가능성도 고려해야 합니다.

</details>

<details>
<summary>애플리케이션 메모리에 중간 결과를 들고 있으면 어떤 문제가 있나요?</summary>

데이터가 많으면 heap 사용량이 늘고 GC pause나 OOM이 발생할 수 있습니다. streaming, paging, chunk 처리, batch size 제한으로 메모리 상한을 관리해야 합니다.

</details>

<details>
<summary>batch insert 크기는 어떻게 정해야 하나요?</summary>

DB packet size, transaction log, lock 유지 시간, 네트워크 왕복, 애플리케이션 메모리를 보고 정합니다. 무조건 크게 잡기보다 운영 지표를 보며 적정 크기를 찾아야 합니다.

</details>
#### 주의할 점

- insert-select가 항상 나쁜 방식이라고 말하지 않습니다.
- 이 프로젝트에서는 DB 역할 분리 목적 때문에 분리했다고 설명합니다.

### 3-6. MySQL에서 일반 SELECT는 lock을 잡나요?

#### 관련 개념

- [MySQL InnoDB](#concept-mysql-innodb)
- [MVCC](#concept-mvcc)
- [Consistent Read](#concept-consistent-read)
- [Locking Read](#concept-locking-read)
- [Row Lock](#concept-row-lock)
- [Isolation Level](#concept-isolation-level)

#### 답변 핵심

- InnoDB의 일반 SELECT는 보통 MVCC 기반 consistent read로 처리되어 row lock을 직접 잡지 않는다.
- `SELECT FOR UPDATE`, `SELECT LOCK IN SHARE MODE`, `UPDATE`, `DELETE`는 lock을 잡을 수 있다.
- 일반 SELECT라도 대량 스캔, 인덱스 미사용, 긴 트랜잭션이면 I/O, CPU, undo log 유지, undo purge 지연, 커넥션 점유 부담을 줄 수 있다.

#### 답변 예시

MySQL InnoDB 기준으로 일반 SELECT는 보통 MVCC를 통해 consistent read로 처리되기 때문에 row lock을 직접 잡지 않는 것으로 알고 있습니다. 그래서 단순 조회가 바로 update를 막는다고 말하면 부정확할 수 있습니다.

다만 일반 SELECT라도 대량 데이터를 조회하거나 인덱스를 제대로 타지 못하는 쿼리가 오래 실행되면 lock이 아니더라도 운영 DB의 read I/O, CPU, 커넥션 점유, undo log 유지 비용이 커질 수 있습니다. 긴 consistent read가 유지되면 undo purge가 지연될 수도 있습니다. 그래서 저는 통계 배치의 영향은 lock 하나만이 아니라 DB 자원 사용 전체 관점에서 봐야 한다고 이해하고 있습니다.

#### 꼬리 질문

<details>
<summary>MVCC가 무엇인가요?</summary>

MVCC는 데이터를 수정할 때 기존 버전을 보존해 읽기 트랜잭션이 일관된 스냅샷을 볼 수 있게 하는 방식입니다. 일반 SELECT가 row lock 없이도 일관된 읽기를 할 수 있는 기반입니다.

</details>

<details>
<summary>Repeatable Read에서는 어떤 일이 생기나요?</summary>

같은 트랜잭션 안에서 같은 조건으로 읽으면 동일한 스냅샷을 보게 됩니다. MySQL InnoDB에서는 phantom 방지를 위해 특정 locking read나 range update에서 gap lock이 개입할 수 있습니다.

</details>

<details>
<summary>gap lock은 언제 발생할 수 있나요?</summary>

InnoDB에서 Repeatable Read 격리 수준의 range 검색, SELECT FOR UPDATE, UPDATE/DELETE 범위 조건 등에서 index record 사이 gap을 잠글 수 있습니다. 일반 consistent read SELECT와는 구분해야 합니다.

</details>

<details>
<summary>실행 계획을 보면 무엇을 확인해야 하나요?</summary>

사용 인덱스, type, rows, filtered, Extra의 Using filesort/temporary 여부를 봅니다. 예상보다 많은 rows를 읽거나 인덱스를 타지 않으면 쿼리 조건과 인덱스 설계를 다시 봐야 합니다.

</details>
#### 주의할 점

- “SELECT는 무조건 lock을 잡는다”고 말하지 않습니다.
- “SELECT는 아무 영향도 없다”고도 말하지 않습니다.

### 3-7. LazyConnectionDataSourceProxy는 어떤 문제를 해결하기 위한 개념인가요?

#### 관련 개념

- [Spring Transaction](#concept-spring-transaction)
- [DataSource](#concept-datasource)
- [LazyConnectionDataSourceProxy](#concept-lazyconnectiondatasourceproxy)
- [Read/Write Routing](#concept-read-write-routing)
- [readOnly Transaction](#concept-readonly-transaction)

#### 답변 핵심

- 트랜잭션이 시작되자마자 실제 DB 커넥션을 잡지 않고, 실제 쿼리 실행 시점까지 커넥션 획득을 지연할 수 있다.
- read/write routing 자체는 보통 `AbstractRoutingDataSource` 같은 라우팅 DataSource와 함께 구성될 때 의미가 있다.
- `LazyConnectionDataSourceProxy`는 커넥션 획득 시점을 늦춰 트랜잭션 속성이 라우팅 판단에 반영될 여지를 만든다.
- 다만 이 프로젝트의 MetaService에 직접 적용했다고 단정하지 않고, 운영 DB 조회와 통계 DB 적재처럼 연결 대상이 나뉘는 구조에서 왜 이런 개념이 언급되는지 설명하는 정도로 답변한다.

#### 답변 예시

제가 이해한 LazyConnectionDataSourceProxy의 목적은 실제 커넥션 획득을 쿼리 실행 시점까지 늦추는 것입니다. Spring에서 트랜잭션이 시작될 때 바로 커넥션을 잡아버리면, 이후에 readOnly 여부나 라우팅 조건을 반영하기 어려운 경우가 있을 수 있습니다.

다만 LazyConnectionDataSourceProxy 혼자 read/write routing을 해주는 것은 아니고, 보통 `AbstractRoutingDataSource` 같은 라우팅 DataSource와 함께 구성될 때 의미가 있다고 이해하고 있습니다. 실제 DB 작업이 발생하는 시점에 트랜잭션 속성이나 라우팅 조건을 보고 적절한 datasource를 선택할 수 있도록 커넥션 획득을 지연하는 역할에 가깝습니다.

제가 담당한 MetaService에는 이 구성이 직접 적용된 것으로 보지 않고 있습니다. 다만 이 프로젝트에서는 운영 DB 조회와 통계 DB 적재처럼 연결 대상이 달랐기 때문에 datasource 설정과 transaction manager 구성이 중요했고, 이런 맥락에서 LazyConnectionDataSourceProxy와 라우팅 DataSource의 역할 차이를 이해할 필요가 있다고 보고 있습니다.

#### 꼬리 질문

<details>
<summary>readOnly=true면 DB에 쓰기가 절대 불가능한가요?</summary>

절대적인 보안 장벽은 아닙니다. Spring의 readOnly는 트랜잭션 힌트 성격이 강하고, DB/드라이버/라우팅 설정에 따라 동작이 달라질 수 있습니다. 쓰기 차단은 권한과 라우팅 정책까지 함께 봐야 합니다.

</details>

<details>
<summary>Transaction Manager는 어떤 역할을 하나요?</summary>

트랜잭션 시작, commit, rollback, propagation, isolation 같은 경계를 관리합니다. 어떤 DataSource와 연결되는지에 따라 실제 커넥션과 트랜잭션 범위가 결정됩니다.

</details>

<details>
<summary>커넥션 풀과 DataSource는 어떻게 다른가요?</summary>

DataSource는 커넥션을 얻기 위한 표준 인터페이스이고, 커넥션 풀은 실제 DB 커넥션을 재사용하기 위해 관리하는 구현입니다. HikariCP 같은 풀이 DataSource 구현으로 사용될 수 있습니다.

</details>

<details>
<summary>`LazyConnectionDataSourceProxy`와 `AbstractRoutingDataSource`의 역할 차이는 무엇인가요?</summary>

LazyConnectionDataSourceProxy는 실제 쿼리 시점까지 커넥션 획득을 늦추는 역할이고, AbstractRoutingDataSource는 현재 컨텍스트에 따라 어떤 DataSource를 쓸지 결정하는 역할입니다. Lazy proxy가 단독으로 read/write routing을 해주는 것은 아닙니다.

</details>
#### 주의할 점

- readOnly가 모든 DB 쓰기를 물리적으로 막는다고 단정하지 않습니다.
- 직접 적용했다고 말하지 말고, 실제 라우팅 기준은 프로젝트 설정을 기준으로 확인해야 한다고 말합니다.

### 3-8. DB를 분리하면 무조건 성능이 좋아지나요?

#### 관련 개념

- [물리 분리](#concept-물리-분리)
- [논리 분리](#concept-논리-분리)
- [Schema 분리](#concept-schema-분리)
- [DB 인스턴스](#concept-db-인스턴스)
- [병목 지점](#concept-병목-지점)
- [트레이드오프](#concept-트레이드오프)

#### 답변 핵심

- 무조건 좋아지는 것은 아니다.
- 같은 물리 서버 안에서 schema만 나눈 경우 CPU, Memory, Disk I/O는 여전히 공유할 수 있다.
- 물리적으로 분리하면 자원 경합은 줄일 수 있지만 운영 복잡도, 동기화, 장애 대응 비용이 늘 수 있다.
- 병목이 DB 자원 경합인지, 쿼리/인덱스 문제인지 먼저 확인해야 한다.

#### 답변 예시

DB를 분리한다고 무조건 성능이 좋아진다고 보지는 않습니다. 만약 같은 MySQL 인스턴스 안에서 schema만 나눈 구조라면 논리적으로 역할은 나뉘지만 CPU, 메모리, 디스크 I/O 같은 물리 자원은 여전히 공유할 수 있습니다.

반대로 물리적으로 DB를 분리하면 운영 DB와 통계 DB의 자원 경합을 줄일 수 있지만, 데이터 동기화, 장애 대응, 배포와 모니터링 복잡도는 늘어납니다. 그래서 실제로는 쿼리 실행 계획, 인덱스, 커넥션 사용량, I/O 지표를 보고 병목이 어디인지 확인한 뒤 분리 효과를 판단해야 한다고 생각합니다.

#### 꼬리 질문

<details>
<summary>schema 분리와 물리 DB 분리의 차이는 무엇인가요?</summary>

schema 분리는 논리적 구분이라 같은 인스턴스 자원을 공유할 수 있습니다. 물리 DB 분리는 인스턴스나 서버를 나눠 자원 격리 효과를 더 기대할 수 있지만 네트워크, 권한, 운영 복잡도가 늘어납니다.

</details>

<details>
<summary>어떤 지표를 보고 DB 분리 효과를 판단하나요?</summary>

운영 DB의 CPU, I/O, lock wait, slow query, connection pool 사용률, 통계 배치 시간, API latency를 봅니다. 분리 전후로 같은 기준의 지표를 비교해야 효과를 말할 수 있습니다.

</details>

<details>
<summary>DB 분리 대신 쿼리 튜닝으로 해결할 수 있는 경우는 언제인가요?</summary>

병목 원인이 인덱스 부재, 잘못된 조인 순서, 불필요한 full scan, 과도한 정렬/임시 테이블이라면 먼저 쿼리 튜닝이 효과적일 수 있습니다. 자원 경합이 핵심일 때 DB 분리를 검토합니다.

</details>
#### 주의할 점

- DB 분리를 만능 해결책처럼 말하지 않습니다.

### 3-9. 통계 배치가 10분에서 2시간으로 늘어나면 무엇을 확인하겠나요?

#### 관련 개념

- [실행 계획](#concept-실행-계획)
- [Slow Query Log](#concept-slow-query-log)
- [인덱스](#concept-인덱스)
- [Connection Pool](#concept-connection-pool)
- [Batch Insert Size](#concept-batch-insert-size)
- [DB I/O](#concept-db-i-o)
- [네트워크 왕복](#concept-네트워크-왕복)

#### 답변 핵심

- 처리 건수가 늘었는지 먼저 확인한다.
- 운영 DB 조회가 느린지, 애플리케이션 집계가 느린지, 통계 DB insert가 느린지 구간을 나눈다.
- 실행 계획, 인덱스 사용 여부, slow query, DB CPU/I/O, connection pool active count, batch insert size를 확인한다.

#### 답변 예시

먼저 배치 시간이 늘어난 원인을 구간별로 나눠서 확인하겠습니다. 운영 DB에서 원천 데이터를 조회하는 시간이 늘어난 것인지, 애플리케이션에서 집계하는 시간이 늘어난 것인지, 통계 DB에 insert하는 시간이 늘어난 것인지 분리해서 봐야 합니다.

그다음 처리 건수 증가 여부, 쿼리 실행 계획 변경, 인덱스 사용 여부, slow query log, DB CPU와 I/O, connection pool active count, batch insert size를 확인하겠습니다. select와 insert를 분리한 구조에서는 네트워크 왕복과 애플리케이션 메모리 사용도 병목이 될 수 있으므로, 중간 결과 데이터량도 함께 보겠습니다.

#### 꼬리 질문

<details>
<summary>실행 계획에서 어떤 항목을 보나요?</summary>

인덱스 선택 여부, 예상 rows, join type, filter 비율, filesort/temporary 사용 여부를 봅니다. 실행 계획과 실제 처리 시간이 맞지 않으면 통계 정보와 데이터 분포도 확인합니다.

</details>

<details>
<summary>인덱스를 추가하면 항상 해결되나요?</summary>

항상은 아닙니다. 쓰기 비용과 저장 공간이 늘고, 선택도가 낮은 컬럼이면 효과가 작을 수 있습니다. 쿼리 패턴과 카디널리티를 보고 필요한 인덱스만 추가해야 합니다.

</details>

<details>
<summary>batch insert size는 크게 잡을수록 좋은가요?</summary>

너무 작으면 왕복 비용이 크고, 너무 크면 transaction log, packet size, lock 시간, 메모리 사용이 커집니다. 운영 환경에서 실패율과 처리 시간을 보며 적정값을 찾아야 합니다.

</details>

<details>
<summary>운영 DB 조회가 느린지 통계 DB 적재가 느린지 어떻게 구분하나요?</summary>

select 단계와 insert 단계 시간을 분리 측정하고, 각 DB의 slow query, connection pool, CPU/I/O 지표를 따로 봅니다. 로그에 단계별 소요 시간을 남기면 병목 구간을 빠르게 나눌 수 있습니다.

</details>
#### 주의할 점

- “DB 분리했으니 통계 배치는 운영에 영향이 없다”고 말하지 않습니다.
- 지표로 구간을 나눠 확인한다고 답합니다.

### 3-10. 상태 전환 배치를 상태 머신으로 설계한다면 어떤 장단점이 있나요?

#### 관련 개념

- [상태 머신](#concept-상태-머신)
- [상태 전이표](#concept-상태-전이표)
- [현재 상태](#concept-현재-상태)
- [이벤트](#concept-이벤트)
- [전이 조건](#concept-전이-조건)
- [잘못된 전이 차단](#concept-잘못된-전이-차단)

#### 답변 핵심

- 상태가 늘어나면 if문으로 조건을 흩뿌리는 방식은 관리가 어려워질 수 있다.
- 상태 머신은 허용 가능한 전이를 명확히 표현할 수 있다.
- 단점은 초기 설계 비용과 구현 복잡도가 늘 수 있다는 점이다.

#### 답변 예시

상태값이 적고 전환 조건이 단순하면 if문 기반 처리도 충분할 수 있습니다. 하지만 상태가 늘어나고 전환 조건이 복잡해지면 어떤 상태에서 어떤 상태로 갈 수 있는지 코드만 보고 파악하기 어려워질 수 있습니다.

상태 머신으로 설계하면 현재 상태, 이벤트, 조건을 기준으로 허용 가능한 전이를 전이표처럼 관리할 수 있습니다. 잘못된 전이를 차단하기 쉽고, 상태 추가나 변경 시 영향 범위를 파악하기도 좋아집니다.

다만 초기 설계와 테스트 비용이 늘 수 있기 때문에, 상태가 얼마나 복잡한지와 변경 가능성을 보고 선택해야 한다고 생각합니다.

#### 꼬리 질문

<details>
<summary>상태 전이표에는 어떤 정보가 들어가야 하나요?</summary>

현재 상태, 다음 상태, 전이 조건, 허용 액터, 적용일 기준, 실패 시 처리, 재처리 가능 여부가 들어가야 합니다. 숫자 코드만 두기보다 의미와 전이 규칙이 함께 관리되어야 합니다.

</details>

<details>
<summary>잘못된 상태 전이는 어떻게 막나요?</summary>

허용된 현재 상태에서만 update되도록 조건을 걸고, DB constraint나 optimistic locking, 상태 전이 검증 로직을 둘 수 있습니다. 배치에서도 update count를 확인해 예상과 다르면 로그를 남겨야 합니다.

</details>

<details>
<summary>상태 머신을 DB로 관리할지 코드로 관리할지 어떻게 정하나요?</summary>

상태 전이 규칙이 자주 바뀌고 운영자가 관리해야 하면 DB 관리가 유리합니다. 규칙이 안정적이고 코드 리뷰로 통제하는 것이 중요하면 코드 관리가 단순하고 안전할 수 있습니다.

</details>
#### 주의할 점

- “상태 머신이 무조건 더 좋다”고 말하지 않습니다.

### 3-11. Gap Lock은 언제 발생할 수 있나요?

#### 관련 개념

- [InnoDB](#concept-innodb)
- [Repeatable Read](#concept-repeatable-read)
- [Next-Key Lock](#concept-next-key-lock)
- [Gap Lock](#concept-gap-lock)
- [Range Condition](#concept-range-condition)
- [Locking Read](#concept-locking-read)

#### 답변 핵심

- 일반 SELECT는 보통 consistent read라 row lock을 직접 잡지 않는다.
- 하지만 `SELECT ... FOR UPDATE`, `UPDATE`, `DELETE` 같은 locking read/write에서 range condition이 있으면 next-key lock이나 gap lock이 발생할 수 있다.
- MySQL InnoDB의 Repeatable Read에서는 phantom read를 막기 위해 gap lock이 사용될 수 있다.

#### 답변 예시

MySQL InnoDB에서 일반 SELECT는 보통 MVCC 기반 consistent read라 row lock을 직접 잡지 않는 것으로 알고 있습니다. 다만 `SELECT ... FOR UPDATE`, `UPDATE`, `DELETE`처럼 lock을 동반하는 쿼리에서 범위 조건을 사용하면 next-key lock이나 gap lock이 발생할 수 있습니다.

특히 Repeatable Read에서 phantom read를 막기 위해 실제 row뿐 아니라 row 사이의 gap까지 잠글 수 있습니다. 그래서 lock 문제를 판단할 때는 쿼리가 일반 SELECT인지 locking read인지, isolation level이 무엇인지, 조건이 point lookup인지 range scan인지, 인덱스를 타는지 확인해야 합니다.

#### 꼬리 질문

<details>
<summary>Gap lock과 row lock은 어떻게 다른가요?</summary>

row lock은 실제 index record를 잠그고, gap lock은 record 사이의 범위를 잠가 새로운 row 삽입을 막습니다. gap lock은 phantom 방지와 range 조건 동시성 제어에 관련됩니다.

</details>

<details>
<summary>Phantom read는 무엇인가요?</summary>

같은 트랜잭션 안에서 같은 조건으로 다시 조회했을 때 다른 트랜잭션이 추가한 row 때문에 결과 row 집합이 달라지는 현상입니다. MVCC와 locking 정책으로 이를 줄이거나 막습니다.

</details>

<details>
<summary>Read Committed에서는 gap lock 동작이 어떻게 달라질 수 있나요?</summary>

Read Committed에서는 일반적으로 gap lock 사용이 줄고, 각 statement마다 최신 committed 데이터를 봅니다. 다만 foreign key 검사나 duplicate key 검사 등 일부 상황에서는 gap lock이 여전히 생길 수 있습니다.

</details>
#### 주의할 점

- “SELECT는 lock이 없다”로 단순화하지 않습니다.
- 쿼리 형태와 isolation level을 같이 말합니다.

### 3-12. 배치가 중복 실행되면 어떤 문제가 생기고 어떻게 막나요?

#### 관련 개념

- [Idempotency](#concept-idempotency)
- [Unique Key](#concept-unique-key)
- [Job Parameter](#concept-job-parameter)
- [Batch Execution](#concept-batch-execution)
- [중복 Insert](#concept-중복-insert)
- [Locking](#concept-locking)

#### 답변 핵심

- 같은 기준일 배치가 중복 실행되면 통계가 중복 적재되거나 상태 전환이 중복 처리될 수 있다.
- 기준일, service id, metadata version 같은 키로 멱등성을 보장해야 한다.
- Spring Batch job parameter, unique key, 실행 상태 관리, 이미 처리된 데이터 skip 전략을 고려한다.

#### 답변 예시

배치가 중복 실행되면 같은 기준일의 통계가 중복 insert되거나, 이미 전환된 상태를 다시 전환하려는 문제가 생길 수 있습니다. 그래서 배치 처리는 멱등성을 고려해야 합니다.

통계 배치라면 기준일과 service id, schema id 같은 값을 unique key로 잡거나, 기존 데이터를 삭제 후 재생성하는 방식, 또는 upsert 방식 중 요구사항에 맞는 방법을 선택할 수 있습니다. 상태 전환 배치라면 현재 상태와 적용일을 다시 확인해서 이미 처리된 데이터는 건너뛰도록 해야 합니다.

Spring Batch 관점에서는 job parameter와 batch execution 상태를 확인하고, 실패한 실행을 재시작할지 새 실행으로 볼지도 명확히 해야 합니다.

#### 꼬리 질문

<details>
<summary>멱등성이란 무엇인가요?</summary>

같은 요청이나 작업을 여러 번 실행해도 최종 결과가 한 번 실행한 것과 같게 유지되는 성질입니다. 배치 재실행, 외부 API retry, S3 업로드 재처리에서 중요합니다.

</details>

<details>
<summary>upsert와 delete-insert 중 어떤 방식이 더 적절한가요?</summary>

기존 row를 유지하며 값만 갱신하면 upsert가 유리하고, 특정 기준일 집계를 통째로 재생성해야 하면 delete-insert가 단순할 수 있습니다. 외래키, 이력 보존, 중간 실패 시 상태를 보고 선택해야 합니다.

</details>

<details>
<summary>Spring Batch JobInstance는 무엇으로 구분되나요?</summary>

JobInstance는 Job 이름과 JobParameters 조합으로 구분됩니다. 같은 파라미터로 이미 완료된 Job은 다시 실행이 제한될 수 있어 기준일이나 service_id 같은 파라미터 설계가 중요합니다.

</details>
#### 주의할 점

- “스케줄러가 한 번만 실행하니까 괜찮다”고 말하지 않습니다.

### 3-13. 다시 설계한다면 어떤 부분을 개선하고 싶나요?

#### 관련 개념

- [관측성](#concept-관측성)
- [재처리](#concept-재처리)
- [장애 추적](#concept-장애-추적)
- [상태 머신](#concept-상태-머신)
- [테스트 자동화](#concept-테스트-자동화)

#### 답변 핵심

- 상태 전환, S3 업로드, 외부 검증 API 연계는 실패 지점이 많다.
- 상태값과 로그, 재처리 기준을 더 명확히 설계하면 운영성이 좋아진다.
- 통계 배치는 실행 결과, 처리 건수, 실패 서비스 목록을 더 체계적으로 남기면 좋다.

#### 답변 예시

다시 설계한다면 상태 전환과 외부 연계 지점의 관측성과 재처리 흐름을 더 명확히 만들고 싶습니다. 이 프로젝트에서는 메타데이터 상태 전환, S3 업로드, 외부 검증 API 연계처럼 DB 외부 시스템과 연결되는 지점이 많았습니다.

이런 지점은 DB 트랜잭션만으로 정합성을 보장하기 어렵기 때문에, 상태값, 요청 ID, 실패 사유, 재처리 가능 여부를 더 체계적으로 남기는 구조가 중요하다고 생각합니다. 또 배치 쪽에서는 서비스별 처리 결과, 실패 서비스 목록, 처리 건수를 운영자가 쉽게 확인할 수 있게 만들면 장애 대응이 더 좋아질 것 같습니다.

#### 꼬리 질문

<details>
<summary>상태 머신으로 관리하면 어떤 장점이 있나요?</summary>

허용 가능한 상태 전이가 명확해지고, 잘못된 상태 변경을 사전에 막기 쉽습니다. 코드 곳곳에 if/else가 흩어지는 것을 줄이고, 상태 변경 로그와 검증 기준을 일관되게 만들 수 있습니다.

</details>

<details>
<summary>재처리 API를 만든다면 어떤 조건이 필요하나요?</summary>

재처리 대상 service_id, 기준일/version, 현재 상태, 이전 실패 로그, 멱등 key, 권한, 중복 실행 방지 조건이 필요합니다. 성공한 건을 다시 망가뜨리지 않도록 dry-run이나 대상 조회 기능도 있으면 좋습니다.

</details>

<details>
<summary>로그와 모니터링 지표는 무엇을 남기겠나요?</summary>

처리 건수, 성공/실패 건수, service_id, batch execution id, 단계별 소요 시간, 외부 API latency, S3 업로드 결과, DB insert 시간, exception 유형을 남기겠습니다. 지표는 알림 기준과 연결되어야 운영에서 의미가 있습니다.

</details>
#### 주의할 점

- 기존 구현을 부정하기보다 “운영성을 더 높일 수 있는 개선점”으로 말합니다.

### 3-14. Java에서 객체 하나를 생성하면 메모리에 얼마만큼 쌓이나요?

#### 관련 개념

- [JVM](#concept-jvm)
- [Heap](#concept-heap)
- [Object Header](#concept-object-header)
- [Mark Word](#concept-mark-word)
- [Klass Pointer](#concept-klass-pointer)
- [Compressed Oops](#concept-compressed-oops)
- [Padding](#concept-padding)
- [JOL](#concept-jol)

#### 답변 핵심

- 정확한 크기는 JVM 구현, 32/64bit, compressed oops, 객체 필드, 정렬 단위에 따라 달라진다.
- 객체는 필드 값만 저장되는 것이 아니라 JVM이 관리하기 위한 object header가 붙는다.
- 참조 크기와 padding 때문에 `int` 하나만 있어도 4바이트보다 커질 수 있다.

#### 답변 예시

정확한 바이트 수는 JVM 설정과 객체 구조에 따라 달라질 수 있어서 바로 단정하긴 어렵습니다. 다만 객체가 JVM heap에 생성되면 필드 값만 저장되는 것은 아니고, JVM이 객체를 관리하기 위한 object header가 붙는 것으로 알고 있습니다.

예를 들어 lock 상태나 GC에서 필요한 정보를 담는 mark word, 클래스 정보를 가리키는 포인터 같은 메타 정보가 필요할 수 있습니다. 또 64bit JVM인지, compressed oops가 켜져 있는지에 따라 참조 크기도 달라질 수 있고, 객체 정렬 때문에 padding이 붙을 수도 있습니다. 그래서 실제 크기는 JOL 같은 도구나 JVM 옵션을 확인해서 검증하겠습니다.

#### 꼬리 질문

<details>
<summary>객체 헤더에는 어떤 정보가 들어가나요?</summary>

JVM 객체 헤더에는 mark word와 klass pointer 같은 정보가 들어갑니다. mark word에는 hash, lock 상태, GC 관련 정보가 담길 수 있고, klass pointer는 객체의 클래스 메타데이터를 가리킵니다.

</details>

<details>
<summary>compressed oops는 왜 사용하나요?</summary>

64bit JVM에서 객체 참조 포인터 크기를 줄여 heap 메모리 사용량을 낮추기 위해 사용합니다. 참조 크기가 줄면 객체가 많은 애플리케이션에서 메모리 효율과 캐시 효율이 좋아질 수 있습니다.

</details>

<details>
<summary>stack과 heap의 차이는 무엇인가요?</summary>

stack은 메서드 호출 프레임, 지역 변수, 참조 값이 저장되는 영역이고 thread별로 분리됩니다. heap은 객체 인스턴스가 저장되는 공유 영역이며 GC의 주요 관리 대상입니다.

</details>

<details>
<summary>primitive와 wrapper 객체는 메모리 관점에서 어떻게 다른가요?</summary>

primitive는 값 자체가 저장되어 오버헤드가 작습니다. wrapper는 객체이므로 객체 헤더와 참조 비용이 추가되어 컬렉션에 대량 저장하면 메모리 사용량이 크게 늘 수 있습니다.

</details>
#### 주의할 점

- “int 하나니까 4바이트입니다”로 끝내지 않습니다.

### 3-15. HTTP/1.1에서 HTTP/2, HTTP/3로 넘어가며 무엇을 얻고 무엇을 포기했나요?

#### 관련 개념

- [HTTP/1.1](#concept-http-1-1)
- [HTTP/2](#concept-http-2)
- [HTTP/3](#concept-http-3)
- [TCP](#concept-tcp)
- [UDP](#concept-udp)
- [QUIC](#concept-quic)
- [TLS](#concept-tls)
- [Multiplexing](#concept-multiplexing)
- [Head-of-Line Blocking](#concept-head-of-line-blocking)

#### 답변 핵심

- HTTP/1.1은 연결 사용과 요청 처리 방식에서 병목이 생길 수 있었다.
- HTTP/2는 하나의 TCP 연결에서 여러 스트림을 multiplexing해 연결 효율을 높였다.
- 하지만 TCP 레벨 head-of-line blocking 문제는 남아 있었다.
- HTTP/3는 QUIC 기반으로 UDP 위에서 동작하며 연결 설정 지연과 패킷 손실 영향을 줄이려 했다.
- 인프라, 프록시, 방화벽, 서버 지원 여부에 따라 도입 효과가 달라질 수 있다.

#### 답변 예시

정확한 세부 스펙을 모두 외우고 있지는 않지만, 버전이 올라갔다는 것은 기존 방식의 병목을 줄이려는 목적이 있었다고 이해하고 있습니다.

HTTP/1.1에서는 keep-alive를 사용하더라도 요청 처리와 연결 사용 방식에서 한계가 있었습니다. HTTP/2는 하나의 TCP 연결에서 여러 요청과 응답을 스트림으로 multiplexing해서 연결 사용 효율을 높였습니다. 다만 TCP 기반이기 때문에 패킷 손실이 발생하면 같은 연결의 다른 스트림도 영향을 받을 수 있는 head-of-line blocking 문제가 남을 수 있습니다.

HTTP/3는 QUIC을 사용해 UDP 위에서 동작하고, 연결 설정과 패킷 손실 영향을 줄이려는 방향으로 발전한 것으로 이해하고 있습니다. 하지만 고객 환경에서 중간 프록시나 방화벽, 서버 지원 여부가 맞지 않으면 업그레이드 효과가 제한될 수 있기 때문에 실제 도입은 환경을 확인해야 한다고 생각합니다.

#### 꼬리 질문

<details>
<summary>HTTP/2 multiplexing은 무엇인가요?</summary>

하나의 TCP connection 안에서 여러 요청과 응답 stream을 동시에 주고받는 기능입니다. HTTP/1.1의 connection당 순차 처리 한계를 줄이지만 TCP 계층의 head-of-line blocking은 남을 수 있습니다.

</details>

<details>
<summary>TCP head-of-line blocking은 무엇인가요?</summary>

TCP는 순서 보장을 하므로 앞선 packet이 손실되면 뒤 packet이 도착해도 애플리케이션에 전달되지 못하고 기다리는 현상입니다. HTTP/2도 TCP 위에서 동작하므로 이 문제를 완전히 피하지 못합니다.

</details>

<details>
<summary>QUIC은 왜 UDP 기반인가요?</summary>

QUIC은 transport 기능을 사용자 공간에서 구현해 연결 설정, 암호화, stream별 손실 복구를 개선하기 위해 UDP 위에 만들어졌습니다. TCP의 커널 구현 제약을 피하고 HTTP/3의 head-of-line blocking을 줄이는 목적이 있습니다.

</details>

<details>
<summary>HTTP/2로 올리면 항상 빨라지나요?</summary>

항상은 아닙니다. 네트워크 상태, 서버 설정, 요청 개수, 리소스 크기, TLS 설정에 따라 효과가 다릅니다. 단일 큰 파일 다운로드처럼 multiplexing 이점이 적은 경우에는 차이가 작을 수 있습니다.

</details>
#### 주의할 점

- “HTTP/3가 무조건 가장 좋다”고 말하지 않습니다.

### 3-16. 브라우저 주소창에 https://google.com을 입력하면 가장 먼저 무슨 일이 일어나나요?

#### 관련 개념

- [URL Parsing](#concept-url-parsing)
- [Browser Cache](#concept-browser-cache)
- [HSTS](#concept-hsts)
- [DNS](#concept-dns)
- [TCP](#concept-tcp)
- [TLS](#concept-tls)
- [HTTP](#concept-http)
- [Rendering](#concept-rendering)

#### 답변 핵심

- 가장 먼저 브라우저가 입력값을 URL 또는 검색어로 해석한다.
- 캐시, HSTS, DNS 캐시 등을 확인할 수 있다.
- IP를 찾은 뒤 TCP 또는 QUIC 연결을 만든다.
- HTTPS라면 TLS handshake를 수행한다.
- HTTP 요청을 보내고 응답을 받은 뒤 렌더링한다.

#### 답변 예시

가장 먼저 하나만 말하라고 하면 브라우저가 입력값을 URL로 해석하는 단계부터 시작한다고 생각합니다. 이후 브라우저 캐시, HSTS 정책, DNS 캐시를 확인하고, 도메인에 대한 IP를 알기 위해 DNS 조회를 수행합니다.

IP를 찾으면 프로토콜에 따라 TCP 연결을 맺고, HTTPS이기 때문에 TLS handshake로 인증서 검증과 암호화에 필요한 협상을 합니다. 그다음 HTTP 요청을 보내고, 응답을 받으면 HTML, CSS, JavaScript 리소스를 파싱해서 화면을 렌더링합니다. 실제 순서는 브라우저 캐시, DNS 캐시, HTTP 버전, QUIC 사용 여부에 따라 일부 달라질 수 있습니다.

#### 꼬리 질문

<details>
<summary>DNS 조회 순서는 어떻게 되나요?</summary>

브라우저/OS 캐시를 먼저 확인하고, hosts 파일, 로컬 resolver, 재귀 DNS 서버를 거쳐 권한 있는 DNS 서버에서 IP를 찾습니다. 실제 순서는 OS와 네트워크 설정에 따라 달라질 수 있습니다.

</details>

<details>
<summary>TLS handshake에서는 무엇을 하나요?</summary>

클라이언트와 서버가 프로토콜 버전과 암호 스위트를 협상하고, 서버 인증서를 검증한 뒤, 세션 키를 안전하게 합의합니다. 이후 HTTP 데이터는 이 키로 암호화되어 전송됩니다.

</details>

<details>
<summary>HTTPS에서 인증서는 왜 필요한가요?</summary>

인증서는 접속한 서버가 진짜 해당 도메인의 서버인지 검증하고, 공개키를 신뢰할 수 있게 전달하기 위해 필요합니다. 이를 통해 중간자 공격을 줄이고 암호화 통신의 신뢰 기반을 만듭니다.

</details>

<details>
<summary>CDN은 어느 단계에서 영향을 주나요?</summary>

DNS 단계에서 가까운 edge 서버로 라우팅하거나, TLS 종료와 캐시 응답 단계에서 영향을 줍니다. 정적 리소스는 origin까지 가지 않고 CDN edge에서 바로 응답될 수 있습니다.

</details>
#### 주의할 점

- “DNS가 무조건 가장 먼저”라고 단정하지 않습니다.

## 확인된 사실과 아직 조심할 부분

면접에서는 아래처럼 “확인된 사실”과 “직접 담당하지 않았거나 기억이 불확실한 부분”을 구분해서 말합니다. 이 구분을 명확히 하면 모르는 내용을 억지로 단정하지 않으면서도 5년차 백엔드 개발자답게 판단 근거를 설명할 수 있습니다.

### 확인된 사실

1. 운영 DB는 `dataact.metaservice`, 통계 DB는 `dataact.statistic`이었고 물리적으로 분리되어 있었습니다.
2. S3 업로드 실패 시에는 배치 로그를 확인한 뒤 재업로드를 다시 수행했습니다.
3. S3 업로드 성공 후 DB 저장이 실패해도 S3 object는 삭제하지 않고 남아 있었습니다.
4. 상태 전환 배치는 기존 전체 롤백 구조에서 `service_id` 단위 부분 성공 구조로 개선했습니다.
5. 실패한 서비스는 배치 로그에서 `service_id` 중심으로 확인한 뒤 해당 기준으로 다시 실행했습니다.
6. 상태 코드는 `0: 등록`, `1: 대기`, `2: 활성`, `3: 유예`, `4: 종료` 흐름으로 정리할 수 있습니다.
7. 일일 통계 배치 기준일은 UTC 기준 자정부터 다음날 자정까지였습니다.
8. 외부 검증과 배치는 별개 흐름입니다. 외부 검증은 parquet 파일 업로드 과정에서 다른 검증 모듈/API를 호출하는 흐름이고, 배치는 상태 전환 배치와 일 단위 통계 배치입니다.

### 조심해서 말할 부분

1. 외부 검증 API의 timeout, retry, circuit breaker 설정은 직접 확인한 범위가 아니므로 설정과 운영 로그 기준으로 확인하겠다고 말합니다.
2. 대용량 검증 파일 업로드의 파일 크기 제한 여부는 직접 확인한 범위가 아니므로 업로드 설정, gateway 제한, 애플리케이션 설정을 확인하겠다고 말합니다.
3. 압축 파일 보안 검증은 직접 구성한 로직이 아니라 외부 검증 모듈/API 연계 흐름이었으므로, 직접 구현했다고 말하지 않습니다.
4. `LazyConnectionDataSourceProxy`는 개념 설명은 가능하지만, 사용자가 담당한 MetaService에는 사용하지 않은 것으로 알고 있으므로 “직접 적용했다”고 말하지 않습니다.
5. 상태 전환 배치 실패 사유를 별도 테이블로 관리하지는 않았으므로, 개선점으로는 “실패 사유와 재처리 대상 테이블을 분리해두면 더 좋았을 것”이라고 말할 수 있습니다.

### Java 객체 메모리 구조

Java 객체는 보통 object header, instance field, padding으로 구성됩니다. 면접에서 객체 하나의 크기를 물으면 정확한 byte 수를 단정하기보다 JVM 구현, compressed oops 여부, 필드 타입, alignment에 따라 달라진다고 말하는 편이 안전합니다. 대용량 파일 파싱이나 배치 중간 결과를 메모리에 들고 있을 때 객체 수가 많아지면 heap 사용량과 GC 부담이 커질 수 있다는 식으로 연결하면 좋습니다.

### JVM heap, stack, GC

heap은 객체가 저장되는 영역이고, stack은 메서드 호출 프레임과 지역 변수 참조가 쌓이는 영역입니다. GC는 더 이상 참조되지 않는 heap 객체를 회수합니다. 대용량 Excel/CSV 파일을 한 번에 메모리에 올리면 heap 사용량이 커지고 GC가 잦아질 수 있으므로, streaming 처리나 batch size 조절을 고려해야 한다고 연결할 수 있습니다.

### HTTP/1.1, HTTP/2, HTTP/3

HTTP/1.1은 요청/응답 기반이며 connection당 처리 한계와 head-of-line blocking 문제가 있습니다. HTTP/2는 multiplexing으로 하나의 TCP connection에서 여러 stream을 처리할 수 있지만 TCP 계층의 head-of-line blocking은 남습니다. HTTP/3는 QUIC/UDP 기반으로 연결 수립과 패킷 손실 영향을 줄이는 방향입니다. 외부 검증 API 호출이나 대용량 업로드 API를 설명할 때 네트워크 프로토콜 차이를 보강 개념으로 사용할 수 있습니다.

### TCP, UDP, QUIC

TCP는 연결 지향, 순서 보장, 재전송을 제공하지만 지연이 늘 수 있습니다. UDP는 연결과 순서 보장을 기본 제공하지 않아 가볍지만 애플리케이션 계층에서 보완이 필요합니다. QUIC은 UDP 위에서 TLS와 stream multiplexing을 제공하는 프로토콜입니다. 면접에서는 “HTTP/3가 UDP를 쓴다”에서 멈추지 말고, QUIC이 신뢰성과 보안을 프로토콜 계층에서 보완한다고 말하면 좋습니다.

### DNS, TLS, HTTPS 요청 흐름

브라우저가 HTTPS URL에 접근하면 DNS로 IP를 찾고, TCP 또는 QUIC 연결을 맺은 뒤 TLS handshake로 암호화 채널을 구성하고 HTTP 요청을 보냅니다. 외부 API 연계 장애를 볼 때는 DNS 해석 실패, TLS 인증서 문제, connection timeout, read timeout, 응답 코드 문제처럼 구간을 나눠 확인한다고 답변할 수 있습니다.

### MySQL InnoDB MVCC

MVCC는 Multi-Version Concurrency Control의 약자로, 읽기 작업이 쓰기 작업을 무조건 막지 않도록 여러 버전의 데이터를 이용해 일관된 읽기를 제공하는 방식입니다. InnoDB의 일반 SELECT는 보통 MVCC 기반 consistent read로 처리되어 row lock을 직접 잡지 않습니다. 다만 긴 트랜잭션은 undo log 유지와 undo purge 지연을 만들 수 있으므로, 통계 배치 조회 부하는 lock뿐 아니라 DB 자원 사용 관점에서도 봐야 합니다.

### 트랜잭션 ACID

ACID는 Atomicity, Consistency, Isolation, Durability를 의미합니다. 전체 배치를 하나의 트랜잭션으로 묶으면 원자성은 강하지만 한 서비스 실패가 전체 롤백으로 이어질 수 있습니다. 이 프로젝트에서는 업무적으로 service_id 단위 독립 처리가 가능했기 때문에 전체 원자성보다 실패 영향 범위 축소를 선택했다고 설명하면 좋습니다.

### Isolation Level

Isolation Level은 동시에 실행되는 트랜잭션이 서로의 변경을 얼마나 볼 수 있는지 정하는 기준입니다. Read Committed, Repeatable Read, Serializable 등이 있고, MySQL InnoDB는 기본적으로 Repeatable Read를 많이 사용합니다. 격리 수준이 높을수록 일관성은 강해질 수 있지만 lock 경합이나 동시성 저하가 생길 수 있어 업무 특성에 맞게 판단해야 합니다.

### Lock, row lock, gap lock, next-key lock

row lock은 실제 인덱스 레코드에 걸리는 lock이고, gap lock은 인덱스 레코드 사이의 빈 범위에 걸리는 lock입니다. next-key lock은 row lock과 gap lock이 결합된 형태로 phantom read를 막는 데 사용될 수 있습니다. 일반 SELECT는 보통 lock을 잡지 않지만, UPDATE, DELETE, SELECT FOR UPDATE 같은 쿼리와 범위 조건에서는 lock 영향이 생길 수 있습니다.

### Spring Batch Tasklet과 Chunk

Tasklet은 하나의 단계에서 원하는 로직을 직접 수행하는 방식이고, Chunk는 일정 단위로 read-process-write를 반복하며 commit하는 방식입니다. 상태 전환처럼 비교적 절차가 명확한 작업은 Tasklet으로 설명하기 쉽고, 대량 데이터를 반복 처리하는 작업은 Chunk가 적합할 수 있습니다. 면접에서는 “무조건 Tasklet이 좋다”가 아니라 처리량, 재시작성, commit 단위를 보고 선택한다고 말하는 것이 좋습니다.

### DB read/write 분리

read/write 분리는 조회와 저장의 책임 또는 연결 대상을 나누는 방식입니다. 일반적인 read replica 라우팅과, 이 프로젝트처럼 운영 DB에서 원천 데이터를 조회하고 통계 DB에 집계 결과를 저장하는 구조는 구분해서 말해야 합니다. 여기서는 “운영 DB 조회 -> 통계 DB 적재” 흐름이 핵심이며, 단순히 readOnly면 자동으로 다른 DB로 간다고 말하면 위험합니다.

### LazyConnectionDataSourceProxy

LazyConnectionDataSourceProxy는 트랜잭션 시작 시점이 아니라 실제 쿼리 실행 시점까지 DB connection 획득을 늦추는 역할을 합니다. 단독으로 read/write routing을 해주는 것은 아니고, 보통 AbstractRoutingDataSource 같은 라우팅 DataSource와 함께 구성될 때 의미가 있습니다. 사용 여부가 불확실한 프로젝트에서는 “개념적으로는 이렇게 이해한다, 실제 적용 여부는 설정 확인이 필요하다”라고 답변하는 편이 안전합니다.

### S3와 DB 정합성

DB와 S3는 하나의 DB 트랜잭션으로 묶을 수 없기 때문에, 한쪽은 성공하고 다른 쪽은 실패하는 상황이 생길 수 있습니다. 예를 들어 S3 업로드는 성공했지만 DB 상태 업데이트가 실패하면 orphan object가 남을 수 있습니다. 이때는 object key, metadata version, 상태값, 실패 로그, 재처리 기준을 통해 eventual consistency 관점으로 맞춰야 합니다.

### CSV 인코딩과 UTF-8 BOM

CSV는 단순 텍스트 파일이라 파일 자체에 인코딩 정보가 명확하지 않은 경우가 많습니다. Excel은 환경에 따라 UTF-8 BOM, CP949 등을 다르게 해석할 수 있어 한글이나 다국어 설명이 깨질 수 있습니다. 다운로드 시 Content-Type과 charset을 명확히 하고, 업로드 시 허용 인코딩과 운영자 가이드를 정리하는 것이 중요합니다.

### 대용량 파일 업로드 메모리 처리

대용량 파일을 MultipartFile byte array나 전체 workbook 형태로 한 번에 올리면 heap 사용량이 커지고 OOM 위험이 생깁니다. streaming 처리, 임시 파일 저장, 파일 크기 제한, batch 단위 파싱, 실패 위치 기록을 함께 고려해야 합니다. 압축 파일은 압축 해제 후 크기 폭증, 파일 개수 제한, zip slip 같은 경로 조작도 확인해야 합니다.

### 외부 API timeout, retry, idempotency

외부 API는 네트워크 지연, timeout, 5xx, 응답 지연이 발생할 수 있으므로 connect timeout과 read timeout을 분리해서 봐야 합니다. retry는 일시 장애에 도움이 되지만 중복 호출 부작용이 있으면 위험합니다. 그래서 request id, idempotency key, 상태값 기반 재처리처럼 같은 요청이 반복되어도 결과가 꼬이지 않도록 설계하는 것이 중요합니다.

### Circuit Breaker와 Fail Fast

Circuit Breaker는 외부 시스템 장애가 계속될 때 호출을 계속 보내지 않고 일정 시간 차단해 장애 전파를 줄이는 패턴입니다. Fail Fast는 실패 가능성이 높은 작업을 오래 붙잡지 않고 빠르게 실패 처리하는 방식입니다. 외부 검증 API처럼 외부 의존성이 있는 흐름에서는 timeout, retry, circuit breaker, fallback 정책을 함께 생각해야 합니다.

### Idempotency와 중복 실행 방지

Idempotency는 같은 요청이나 배치가 여러 번 실행되어도 결과가 한 번 실행한 것과 같게 유지되는 성질입니다. 배치 중복 실행은 중복 insert, 상태 중복 전환, 통계 중복 집계 문제를 만들 수 있습니다. 실행 lock으로 중복 실행을 막거나, unique key와 upsert, 처리 이력, object key 기준으로 멱등하게 만드는 방식을 고려할 수 있습니다.
