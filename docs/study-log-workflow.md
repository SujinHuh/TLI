# 학습 기록 작성 흐름

이 문서는 AI 에이전트와 함께 TLI 학습 기록을 작성하고 GitHub에 올릴 때 따르는 작업 흐름을 정의한다.

브랜치, 커밋, PR 제목과 본문, 게시 승인 이후의 Git 절차는 `docs/study-pr-format.md`를 단일 출처로 사용한다.

## 기본 원칙

- 학습 기록 파일은 Markdown 형식으로 작성한다.
- 날짜별 학습 기록은 `daily/`에 남기고, 다시 보기 좋은 개념 정리본은 `concepts/`에 별도로 남긴다.
- 면접 준비 자료는 `interviews/company/회사명/`에 남기고, 관련 개념은 필요하면 `concepts/`에도 별도로 정리한다.
- `daily/`는 그날 공부한 원본 흐름, 완료한 내용, 공부 시간, 회고를 남기는 공간이다.
- `concepts/`는 나중에 다시 보기 좋게 정리한 개념 노트를 남기는 공간이다.
- `interviews/company/회사명/`은 특정 회사 면접을 위한 업무 흐름, 예상 질문, 공부용 HTML을 남기는 공간이다.
- 사용자가 최종 검수 후 승인하기 전에는 `daily/`, `concepts/`, `interviews/` 파일을 생성하거나 수정하지 않고, commit, push 또는 PR 생성도 하지 않는다.
- 승인 전 모든 초안은 저장소 파일이 아니라 채팅으로만 제시한다.
- 독립 검수는 서브 에이전트가 수행하고, 검수된 최종본의 확인과 게시 승인은 사용자가 한다.
- 검수된 최신 최종본이 제시된 뒤 사용자가 이 문서의 최종 게시 승인 문구 중 하나를 실제 명령으로 사용하면, AI 에이전트가 승인된 파일에 한해 `git add`, `git commit`, 작업 브랜치 `git push`, PR 생성까지 진행한다.
- 단, Codex 실행 환경의 샌드박스 권한 확인창은 문서 규칙으로 생략할 수 없으며, 필요한 경우 사용자가 직접 승인한다.
- `daily`와 `concepts`를 문서화하기 전에 별도 검수 기준 문서를 통해 원문 대조를 수행한다.
- 검수 기준 문서는 작성자와 분리된 별도 검수 역할(서브 에이전트)이 반드시 수행한다.
- 서브 에이전트는 읽기 전용 검수자이며 파일 수정, commit, push, PR 생성을 하지 않는다. 실제 검수를 수행할 수 없으면 게시를 중단하고 그 사실을 사용자에게 알린다.

## 트리거 문구

사용자가 아래 문구를 말하면 학습 기록 초안 작성 흐름을 시작한다.

- "오늘 공부 끝"

공부를 시작하거나 공부할 계획을 말한 것은 기록 작성 트리거가 아니다. 이때는 대화에서 계획과 시작 시각만 확인하고 파일을 만들거나 수정하지 않는다.

사용자가 아래 문구를 말하면 검수된 최신 최종본의 게시를 승인한 것으로 본다.

- "이대로 Git에 올려줘"
- "최종 Git에 올려줘"
- "완료 Git"
- "Git에 올려줘"
- "Git에 push 해줘"

위 문구는 검수된 최신 최종본과 게시할 경로를 가리키는 실제 명령으로 사용된 경우에만 승인으로 처리한다. 질문, 인용, 예시, 규칙 논의 과정에서 문구를 언급한 것은 게시 승인으로 처리하지 않는다.

최종 게시 승인은 `docs/study-pr-format.md`에 따른 작업 브랜치 push와 PR 생성까지를 의미한다. PR merge와 배포는 포함하지 않는다.

최신 최종본이 아직 제시되지 않은 상태에서 "Git에 올려줘"라는 말만 나오면 게시하지 않는다. `오늘 공부 끝` 단계부터 초안 작성, 회고 반영, 서브 에이전트 검수를 먼저 진행한다.

사용자가 아래 문구를 말하면 면접 준비 정리 흐름을 함께 시작한다.

- "면접준비"
- "면접"

단, 사용자가 단순히 면접 이야기를 하는 것이 아니라 면접 대비 자료를 정리하거나 공부 자료로 남기려는 맥락일 때 적용한다.

## 공부 중 개념 질문 답변 기준

사용자가 공부 중 모르는 개념을 질문하면, AI 에이전트는 이 저장소의 `docs/`, `daily/`, `concepts/` 문서를 먼저 참고해 답변한다.

답변은 항상 아래 두 가지 버전으로 나누어 작성한다.

1. `쉬운 ver (15살이 이해할 수 있는 ver)`
   - 비유와 일상 예시를 사용해 먼저 감을 잡을 수 있게 설명한다.
   - 어려운 용어를 먼저 나열하지 않는다.
   - 핵심 문장은 짧게 정리한다.

2. `개발자 ver`
   - 실제 백엔드, 시스템 설계, Spring, DB, 인프라 관점에서 설명한다.
   - 정의, 동작 흐름, 사용 이유, 주의할 점을 포함한다.
   - 면접 답변으로 말할 수 있을 정도의 표현으로 정리한다.

답변 마지막에는 작성자와 분리된 별도 검수 역할(서브 에이전트)이 아래 관점으로 검수한 결과를 함께 보여준다.

- 쉬운 설명이 원래 개념을 왜곡하지 않았는지
- 개발자 설명에 위험한 오개념이 없는지
- 사용자의 질문 의도에 답했는지
- `daily/` 또는 `concepts/`에 이미 있는 내용과 충돌하지 않는지

검수 결과는 길게 쓰지 않고, 문제가 없으면 `검수 결과: 문제 없음`처럼 짧게 남긴다.

## 작성 순서

1. 사용자가 "오늘 공부 끝"이라고 요청한다.
2. AI 에이전트가 Daily 초안을 채팅으로 먼저 제시한다. 이 단계에서는 저장소 파일을 만들거나 수정하지 않는다.
3. AI 에이전트가 학습 내용 중 Concepts 후보를 함께 제안한다.
4. 사용자가 Daily의 회고를 작성하거나 수정한다.
5. 사용자가 Concepts 후보 중 실제로 남길 문서를 선택한다.
6. AI 에이전트가 회고 원문과 사용자의 선택을 반영한 최종 Daily 및 Concepts 초안을 채팅으로 작성한다.
7. 별도 검수 역할(서브 에이전트)이 검수 기준에 따라 원본 대화와 초안을 대조한 뒤 문제점을 정리한다.
8. 작성자가 그 검수 결과를 반영해 초안을 수정하고 다시 보여준다.
9. 사용자가 검수된 최신 최종본을 확인한다.
10. 사용자가 이 문서의 최종 게시 승인 문구 중 하나를 실제 명령으로 사용하면 AI 에이전트가 승인된 파일만 생성하거나 수정하고, 정확한 경로만 `git add`한 뒤 staged diff를 확인하여 `docs/study-pr-format.md`에 따라 commit, 작업 브랜치 push, PR 생성을 진행한다.

## 면접 준비 작성 순서

사용자 요청에 "면접준비" 또는 "면접"이 포함되고, 면접 대비 자료를 정리하는 맥락이면 아래 순서를 따른다.

1. AI 에이전트가 회사명과 면접 주제를 확인한다.
2. 회사명이 확인되면 `interviews/company/회사명/` 경로를 기본 저장 위치로 잡는다.
3. 업무 흐름, 프로젝트 경험, 예상 질문, 관련 개념을 분리해 초안을 만든다.
4. 면접 답변에 필요한 개념은 질문 안의 `관련 개념`으로 연결하고, 반복해서 복습할 가치가 있으면 `concepts/` 후보로도 제안한다.
5. 예상 질문 문서는 `docs/study-html-format.md`의 구조를 따른다.
6. Markdown 원본은 `interviews/company/회사명/interview-questions.md`로 작성한다.
7. 업무 흐름 정리가 필요하면 `interviews/company/회사명/workflow.md` 또는 주제별 이름으로 작성한다.
8. 공부하기 쉽게 볼 수 있는 HTML은 `interviews/company/회사명/interview.html`로 만든다.
9. HTML에는 관련 개념 anchor 이동, 꼬리 질문 토글, 원본 Markdown 경로 표시를 포함한다.
10. 마무리 전에는 읽기 전용 서브 에이전트가 항상 최종 검수한다.
11. 검수 결과 문제가 있으면 작성자가 수정한 뒤 사용자에게 다시 보여준다.
12. 사용자가 검수된 최신 최종본을 확인한 뒤 이 문서의 최종 게시 승인 문구 중 하나를 실제 명령으로 사용하면 AI 에이전트가 승인된 파일 생성과 `git add`, `git commit`, 작업 브랜치 `git push`, PR 생성을 진행한다. PR merge와 배포는 각각 별도 요청이 있을 때만 진행한다.

## 면접 준비 저장 구조

면접 준비 자료는 아래 구조를 기본으로 한다.

```text
interviews/company/회사명/
├── workflow.md
├── interview-questions.md
└── interview.html
```

주제가 명확히 나뉘면 `workflow.md` 대신 더 구체적인 파일명을 사용할 수 있다.

```text
interviews/company/spade-company/
├── workflow-data-act.md
├── interview-questions.md
└── interview.html
```

면접 준비 과정에서 따로 복습할 가치가 큰 기술 개념은 `concepts/`에 별도 문서로 분리할 수 있다.

## Daily 작성 기준

- `daily/`는 그날의 학습 흐름을 간단하게 기록한다.
- `daily/`에는 목표, 완료한 내용, 공부 시간, 회고를 중심으로 작성한다.
- 사용자가 공부하려고 계획했지만 실제로 진행하지 못한 내용은 완료한 학습으로 쓰지 않는다. 필요하면 `계획했지만 실제 학습까지 진행하지 못함`처럼 명확히 표시한다.
- 회고는 사용자가 직접 작성한다.
- AI 에이전트는 회고를 대신 확정하지 않는다.
- 사용자가 명시적으로 편집을 요청하고 수정본으로 교체하도록 승인하지 않는 한, 회고는 맞춤법, 띄어쓰기, 문장부호, 줄바꿈, 어휘, 표현 순서를 포함해 원문 그대로 보존한다.
- 사용자가 회고 편집을 요청하면 원문과 편집 제안본을 구분해 보여주고, 교체 승인을 받은 뒤 반영한다.
- 사용자가 원하면 AI 에이전트는 회고 작성을 돕기 위한 질문이나 힌트를 제공할 수 있다.
- 관련 concepts가 있으면 `관련 Concepts` 섹션에 링크한다.
- 원문 의미가 바뀌지 않았는지 확인하려면 `docs/study-log-verification.md` 기준으로 검수한다.

## 책별 Concepts 자동 연결 기준

- 사용자가 특정 책을 공부한다고 말한 뒤 그 책과 관련된 개념을 질문하면, 답변과 학습 기록은 해당 책의 Concepts 디렉터리를 우선 연결한다.
- 예를 들어 `가상면접`, `가상 면접`, `대규모 시스템 설계`, `안정 해시`, `처리율 제한` 흐름에서 나온 질문은 `concepts/system-design-interview/` 아래 장별 정리를 후보 경로로 제안한다.
- 예를 들어 `운영체제`, `공룡책`, `Operating System Concepts`, `프로세스`, `스레드`, `CPU 스케줄링`, `동기화`, `데드락`, `메모리`, `파일 시스템` 흐름에서 나온 질문은 `concepts/operating-system/` 아래 정리를 후보 경로로 제안한다.
- Daily의 `관련 Concepts`에는 사용자가 그날 실제로 공부하거나 질문한 책/장/개념 문서를 연결한다.
- 단순히 공부 계획만 말하고 실제 학습이나 개념 질문이 없었던 주제는 완료 학습으로 확정하지 않는다. 필요하면 목표나 미진행 메모로만 남긴다.
- 새 책이나 장이 처음 등장하면 `concepts/책-또는-주제/README.md`와 장별 문서를 후보로 제안하고, 사용자가 선택한 경우에만 생성한다.

## Concepts 작성 기준

- `concepts/`는 다시 보기 좋은 개념 정리본으로 자세하게 작성한다.
- `concepts/`에는 개념의 정의, 핵심 원리, 예시, 주의할 점, 관련 daily 링크를 포함한다.
- 모든 학습 내용을 반드시 concepts에 분리하지 않는다.
- 개념으로 따로 복습할 가치가 있는 내용만 concepts에 정리한다.
- `concepts/` 작성 여부는 사용자가 최종 결정한다.
- AI 에이전트는 concepts 후보를 제안할 수 있다.
- 사용자가 concepts 작성을 명시적으로 요청했거나 concepts 후보 중 남길 문서를 선택한 경우에만 concepts 문서를 생성한다.
- 사용자가 "concepts는 생략해줘"라고 하면 daily만 작성한다.

## Concepts 후보 기준

아래에 해당하는 내용은 concepts 후보가 될 수 있다.

- 나중에 다시 찾아볼 가능성이 높은 개념
- 한 번에 이해하기 어렵거나 반복해서 헷갈리는 개념
- 면접, 실무, 프로젝트에서 다시 사용할 가능성이 높은 개념
- daily 기록 안에만 두기에는 설명이 길어지는 개념
- 여러 daily 기록에서 반복해서 등장하는 개념
- 정의, 동작 원리, 예시, 주의할 점을 따로 정리할 가치가 있는 개념

아래에 해당하는 내용은 굳이 concepts로 분리하지 않는다.

- 단순 감상이나 회고
- 하루 동안만 필요한 일회성 메모
- 너무 짧아서 daily 안에 남겨도 충분한 내용
- 아직 개념으로 정리할 만큼 이해가 쌓이지 않은 내용
- 사용자가 concepts로 남기지 않겠다고 판단한 내용

## Concepts 후보 검수

- concepts 후보를 정할 때도 원문 대화와 초안의 의미가 달라지지 않았는지 `docs/study-log-verification.md` 기준으로 검수한다.

## 상호 참조 기준

`daily/`와 `concepts/`를 함께 작성한 경우 양쪽 문서에 서로를 참조하는 링크를 남긴다.

Daily 문서에는 관련 concepts를 남긴다.

```md
## 🔗 관련 Concepts
- [API Gateway](../../concepts/infra/api-gateway.md)
```

Concepts 문서에는 관련 daily를 남긴다.

```md
## 관련 Daily
- [2026-05-25(월) API Gateway 흐름 정리](../../daily/2026/2026-05-25(월)%20API%20Gateway%20흐름%20정리.md)
```

## 공부 시간 기록 기준

- 공부 시간은 기본적으로 AI 에이전트와 해당 학습 주제 대화를 시작한 시각부터 기록 요청 시점까지로 계산한다.
- 시간이 불명확한 경우 사용자가 말한 시간을 우선한다.
- 사용자가 별도로 공부 시간을 알려주면 해당 시간을 우선 기록한다.
- 대화 시각으로 계산한 공부 시간에는 휴식 시간이 포함될 수 있으므로 `대화 기준 추정`임을 밝히고 최종 확정을 받는다.
- 사용자가 저녁 공부 흐름에서 `8시`, `8시 40분`처럼 말하면 오전으로 단정하지 않고 문맥상 `20:00`, `20:40`인지 확인하거나, 마감 시각과 자연스럽게 이어지는 24시간 표기로 기록한다.

## 최종 검수 기준

- 독립 검수는 서브 에이전트가 수행하고, 검수된 최종본의 확인과 게시 승인은 사용자가 한다.
- 검수된 최신 최종본이 제시된 뒤 사용자가 이 문서의 최종 게시 승인 문구 중 하나를 실제 명령으로 사용한 경우에만 승인된 파일을 생성하거나 수정하고 `git add`, `git commit`, 작업 브랜치 `git push`, PR 생성까지 진행한다.
- Codex 샌드박스 권한 확인창이 뜨는 경우에는 사용자가 직접 승인해야 한다.
- 사용자가 명시적으로 요청하거나 선택한 내용만 최종 기록으로 남긴다.
- 하루에 여러 주제를 공부했더라도 하나의 날짜 파일 안에 자연스럽게 묶어 기록한다.
- Git 승인 범위는 사용자가 확인한 파일로 제한한다. 관련 없는 기존 변경과 승인되지 않은 untracked 파일은 stage하지 않는다.
- 정확한 경로만 stage하고 commit 전에 `git status`와 staged diff를 확인한다.
- `main`에는 직접 push하지 않고 `docs/study-pr-format.md`에 정의된 작업 브랜치와 PR 형식을 사용한다.
- PR merge와 배포는 Git 게시 승인에 포함하지 않으며 각각 별도의 명시적 요청이 있을 때만 진행한다.
